# Десять профилей коммутаторов: состав и результаты проверки

Дата: 13.11.2026. Исходная версия: master `aec3e60`.

Подготовлены десять отдельных диагностических профилей согласованных моделей.
Они лежат в `examples/profiles/Проверка 10 моделей`, вместе с переносимым
справочником и инструкцией. Файлы названы точно как профили в интерфейсе.
Четыре базовых производственных профиля не изменены.

## Что проверяет набор

Набор предназначен для проверки создания и редактирования профилей, выбора
изделия, раннего чтения CPU ID, выдачи номера, самопроверки, парной передачи
данных, состава отчёта и его доставки. Это диагностическая проверка:
в серверном тексте передаётся `Тип проверки=true=diagnostic`.

За основу взяты именованные этапы, подготовка при первом запуске, настройки
стенда, протокол отчёта, монитор пинга и аварийные ветви базового 8x2Pro.
Для старых PSW используется `/test.shtml`, для Pro — LuCI. Точные допуски
ADC, силового PoE, нагревателей, цикла АКБ и минимальные версии прошивок
другой модели не переносились. Прошивка и запись MAC отсутствуют.
Этот набор не заменяет утверждённую производственную методику десяти изделий.

## Модели и согласование данных

Серверный тип каждой строки совпадает с названием модели. Во всех профилях
включены **Серийные номера из справочника**, фиксированный номер отключён.
Адрес сервера берётся из общих настроек. Единственный запрос `getSerialNum`
использует `devType` выбранной карточки и фактически прочитанный `cpu_id`.

| --- | --- | --- | --- | --- | --- |
| PSW-1G4F | 004 | 400001–465535 | C0:11:A6:04 | 2 / 1 RJ45–SFP | 4 |
| PSW-2G4F | 005 | 500001–565535 | C0:11:A6:05 | 2 / 1 SFP–SFP | 5 |
| PSW-2G6F+ | 006 | 600000–665535 | C0:11:A6:06 | 3 / 1 SFP–SFP | 6 |
| PSW-2G8F+ | 007 | 700001–765535 | C0:11:A6:07 | 4 / 1 SFP–SFP | 7 |
| PSW-2G4F-Box | 021 | 2100001–2165535 | C0:11:A6:15 | 2 / 1 SFP–SFP | 5 или 21 |
| PSW-2G6F+Box | 025 | 2500001–2565535 | C0:11:A6:19 | 3 / 1 SFP–SFP | 6 или 25 |

| PSW+Box 8x2Pro | 033 | 3300001–3365535 | C0:11:A6:21 | 4 / 1 SFP–SFP | 0 или 33 |

У PSW-2G6F+ сохранена существующая нижняя граница `600000`; она отличается
от начинающихся с 1 остальных серий. База короткого номера — код × 100000.
MAC рассчитывается из короткой части 0–65535. Расчётный MAC выводится
отдельно от реально прочитанного; расчёт не означает запись в устройство.

Для Box/Ex разрешён код базовой платы либо код исполнения: Qt допускает
`model_num` или `model_num_mac_print`. Соответствие каждой прошивки этим
кодам требует проверки на реальном изделии. Значение `dev_type=0` взято
из существующего Pro-профиля; оно не различает два исполнения Pro.
Перед запуском Pro необходимо сверить выбранную модель с изделием.
Серверный тип не вычисляется из этого нулевого кода.

Комплектация в наборе — 0. Для 021 это Fibox, для 025 и 026 — Fibox + PWR180,
подпись шкафа Fibox. Другой шкаф выбирается в **Параметры** профиля;
состав вариантов редактируется в **Справочник изделий**.
Для остальных карточек неподтверждённые подписи шкафа не добавлялись.

## Карта этапов

| Этап | Действие и источник | Отказ |
| --- | --- | --- |
| 01. Подготовка | При первом запуске AC1/AC2=0, PS-3 slave 23, регистры 1200/1201; очистка ARP как в 8x2Pro. | Ошибка записи останавливает; ошибка ARP при снятом флажке остаётся предупреждением. |
| 02. Питание | AC2=0, AC1=1. | Остановка и аварийная ветка. |
| 03. Загрузка и тип | Ждать CPU ID, прочитать dev_type, проверить его регулярным выражением. Таймаут каждого чтения 250 с, период 5 с. | Серийный номер ещё не запрашивался. |
| 04. Номер | GET `getSerialNum`, тип из справочника, CPU ID из устройства; без фиксированного номера и автоматического повторного запроса. | Чужая серия, выход за диапазон, пустой ID или ошибка сервера останавливают. |
| 05. Selftest | `init_ok=1`; у 032 дополнительно `ups_det=1`. Повторно прочитанный CPU ID должен совпадать с ID запроса номера. | Остановка; номер остаётся связан с CPU ID текущего запроса. |
| 06. DataTest | Попарно все указанные медные порты, затем гигабитные аплинки; оба направления, 5 с, потери ≤1%, недобор TX ≤2%. | Остановка; пара и IP остаются в причине ошибки. |
| 07. Расчёт MAC | Каталожные база и префикс; в устройство ничего не записывается. | Неверный номер или MAC-настройки останавливают. |
| 08. Выключение | AC1/AC2=0; попытка выключить второй выход продолжается и при отказе первого. | Неуспешные операции сохраняются в результате. |
| 09. Отчёт | Общий выбранный состав, локальная копия, один POST. | Отказ доставки имеет отдельный статус, повтор автоматически не выполняется. |
| 10. Этикетка | Отключена. При включении одна этикетка, общий принтер/ZPL, модель и комплектация из справочника. | Реальный MAC должен соответствовать номеру. Подстановка рассчитанного MAC не выполняется. |
| Аварийное выключение | Отдельный runOnFailure-подтест верхнего уровня, AC1/AC2=0. | Обе записи получают попытку выполнения. |
| Отчёт при ошибке | После аварийного выключения, только при Execution.SendFailureReport; уже Sent не дублируется. | Без допустимого номера отчёт не уходит. |

Самопроверка CPU ID выполняется до полной проверки `init_ok`. Поэтому
неуспешное устройство, которое уже отдало ID, может получить собственный
номер и отчёт об отказе. Это не переносит запрос номера в нагревательную
ветку базового производственного профиля: исходный параллельный граф сохранён.

## Подключение DataTest

Медные пары: `.2 ↔ .3`, `.4 ↔ .5`; у 6F также `.6 ↔ .7`, у 8F также
`.10 ↔ .11`. Все адреса находятся в `192.168.0.0/24`. Адрес DUT — `.1`.
Для гигабитной пары во всех профилях используются `.8 ↔ .9`.
У 1G4F один конец этой пары подключается к отдельному гигабитному RJ45,
другой — к SFP; у остальных обе стороны к SFP. Настройки карт и кабели
не подтверждены удалённым прогоном; их нужно сверить перед запуском.
Проверка не определяет физический разъём только по IP-адресу.

В диагностическом оборудовании оставлен только PS-3 slave 23.
EL60, SIMBAT, IO-2 и нагреватели этим набором не управляются и не проверяются.
Перед диагностикой стенд должен быть завершённым после предыдущего прогона.

## Серверный отчёт

Используется обычный формат коммутаторов, а не формат RTL:
`POST /api/Api.svc/result.json`, multipart/form-data с текстовым файлом
`result.json` в части `updatefile`. Содержимое файла — строки
`название=true|false=значение\r\n`, не объект JSON.

Обязательные поля: `test_result`, `stand_id`, ровно один полный `serial_num`,
при наличии сессии — `session`. Выбранные поля: тип проверки, dev_type,
CPU ID, selftest, версии, фактический и расчётный MAC отдельными строками,
короткая часть номера, совпадение CPU ID, исход каждой пары DataTest,
доступные link/PoE и сведения о плате/контроллерах. Для 032 добавлены
обнаружение UPS и напряжение АКБ. Измерение АКБ здесь не является циклом
испытания резервного питания.

Отсутствующее показание не заменяется нулём или успешным значением. Список
редактируется через **Состав отчёта…**; `includeAllVariables=false` и
`includeAutomaticEntries=false` предотвращают включение всех служебных
переменных. Изменение состава не скрывает общий отказ изделия.

В ходе работы исправлен `BuildTestReportStep`: при отказе причина остановки
добавляется и тогда, когда выбранная булева строка уже неуспешна. До этого
в отчёте мог быть только `Передача данных: …=false=0`, без пояснения.
Теперь добавляется `Причина остановки=false=…` с подробностями отказа.

Также исправлен допуск аварийной отправки в `TestViewModel`:
`FailureReportPolicy` разрешает отчёт при уже выданном номере без требования
служебного номера в карточке. Раньше общий флаг аварийной ветви включался
для коммутатора только при наличии служебного номера, поэтому после выдачи
номера девять моделей этого набора всё ещё могли остаться без отчёта об отказе.
Правила частичного запуска, ручной подготовки и отмены сохранены; для RTL
сохранён отдельный маршрут по служебному идентификатору.

Если номер уже выдан, другая серия, другой номер той же серии или подмена
`serial_num` в готовом тексте блокируются до POST. Локальная копия обычного
допустимого отчёта сохраняется до HTTP-запроса; сессия в локальной копии
скрывается. Неопределённый исход запроса номера не вызывает автоматической
повторной выдачи. Ошибка HTTP-доставки отражается в `ReportDelivery.Status`,
а годность устройства — отдельно в `BuildReport.DevicePassed`.

### Отказ до номера

В карточке 032 подтверждён служебный номер `3200001`. Аварийный отчёт
без выданного номера отправляется на него с `test_result=0`.
У остальных девяти моделей служебная запись не подтверждена: ранний отказ
останется в журнале запуска, серверный отчёт не формируется. Добавлять
случайный номер первого реального изделия вместо служебной записи нельзя.
После подтверждения серверной записи её можно задать в карточке модели,
поле **Номер для аварийного отчёта**, без изменения кода или графа.

## Автоматическая проверка

`SwitchQualificationProfileTests` проверяет каждую из десяти моделей:

1. Загрузку реальным GraphSerializer, компиляцию GraphCompiler, повторное
   сохранение/чтение без потери связей, типы нод и параметры отчётных ветвей.
2. Допустимые dev_type, отказ на другом типе, совпадение и подмену CPU ID.
3. Раздельное чтение CPU ID/типа без выполнения полного selftest и реальный
   разбор синтетической XML-страницы с `init_ok=0` и `init_ok=1`.
4. Обе границы серии, соседние недопустимые номера, чужую серию,
   отсутствие CPU ID без HTTP-запроса, devType и кодирование имени модели.
5. Выполнение скомпилированных штатной и аварийной отчётных ветвей:
   успех, отказ устройства, HTTP 503, отказ до номера, отсутствие Stand ID.
   Ошибка формирования штатного отчёта останавливает ветвь, не проходит
   через обходной переход к успешному завершению.
6. Полный serial_num, отсутствие служебных данных, CRLF, формат multipart,
   совпадение локальной копии с текстом, разделение годности и доставки,
   запрет повторной отправки уже принятого отчёта и подмены номера.
7. Команды необязательной печати: отказ при чужом MAC, затем полный номер,
   код модели и короткая часть в штрихкоде, действительный MAC и общий принтер.
8. Реальную политику запуска аварийного отчёта, которую вызывает TestViewModel:
   номер уже выдан/ещё не выдан, служебная запись есть/нет, частичный запуск,
   обычная и автоматическая подготовка, отмена, завершение и маршрут RTL.

HTTP выдачи и доставки перехвачен в памяти. XML, измерения и результаты
DataTest в этих тестах синтетические. Сам DataTest, электрическая схема,
браузерный доступ к DUT и физическая печать не имитируются как состоявшийся
аппаратный прогон. Тесты не запрашивали настоящие номера и не отправляли
синтетические положительные результаты на производственный сервер.

ProfileLayout измеряет каждую ноду в обеих темах, включая все вложенные
графы; после записи отдельно перечитывает JSON и проверяет отступы.
Всего в наборе 130 графов и 621 нода. Результаты итоговых прогонов и
машиночитаемые артефакты приложены в комплекте `output/qualification-2026-11-13`.

Итог: **313 тестов прошли, 0 неуспешных и 0 пропущенных** в двух отдельных
прогонах: 249 проверок отчётов/серийных номеров/справочника и 64 проверки
интерфейса/аварийного завершения. Из них 110 сценариев относятся непосредственно
к новому набору. Все десять новых профилей прошли открытие вложенных редакторов
без изменения сохранённых параметров. ProfileLayout: **130 графов, 621 нода,
0 конфликтов**, отдельное повторное чтение — также 0 конфликтов.
Четыре базовых профиля побайтно совпали с `aec3e60`; SHA-256 сохранены.

Среда: macOS ARM64, .NET SDK 8.0.424, target net8.0. В одном смешанном
прогоне произошла ошибка инициализации шрифта Inter; итоговый отдельный
UI-прогон прошёл полностью. Windows-проверка этим не заменяется.

[Машиночитаемый отчёт по всем моделям](validation/switch-profiles-2026-11-13.json)
содержит пять сценариев каждой модели, тексты отчётов, захваченные multipart
POST, команды необязательной этикетки, SHA-256 профилей и счётчики TRX.
В архиве также есть исходные TRX, отдельные примеры и снимки редактора.

## Что проверить вручную

1. Выбрать папку набора по README, увидеть десять моделей, проверить карточку
   и выбранную комплектацию, подключить PS-3 и сетевые карты.
2. Для каждого изделия сверить фактический dev_type и модель на корпусе.
   Для Pro значение 0 само по себе не определяет исполнение.
3. На первом запуске проверить подготовку, затем чтение CPU ID, серверный
   тип и возвращённый номер. Номер должен попадать в строку таблицы выше.
4. Проверить selftest и все пары DataTest. Сохранить журнал запуска.
5. Открыть локальный `reports/result-*.txt`: полный номер, diagnostic,
   только выбранные строки. Сверить ту же запись на сервере и статус Sent.
6. Выключить ненужную строку в **Состав отчёта…**, включить другую,
   сохранить профиль и повторить: номер остаётся обязательным.
7. Проверить контролируемый отказ после выдачи номера: итог 0, подробная
   причина, тот же номер, питание выключено. Отдельно — недоступный сервер:
   копия сохранена, статус Failed, исправность DUT не подменяется ошибкой HTTP.
8. У 032 проверить ранний отказ: служебный номер 3200001. Для остальных
   до подтверждения служебной записи ожидается журнал без серверного отчёта.

На момент подготовки АПК‑03 и Вышенская отображались offline. Windows-прогон,
приём производственным сервером и десять физических устройств не проверены;
копии приложения на АПК‑03 не создавались. Windows-релиз и публикация
в beta-папку этим заданием не выполнялись.

## Источники и воспроизводимость

- Базовый `profiles/PSW+UPS-Box 8x2Pro · Параллельная проверка с SFP · 11.11.26.json`:
  структура подтестов, PS-3, ARP, интервалы и протоколы.
- Базовый `profiles/PSW-2G6F+ · Полная проверка · 11.11.26.json`:
  старый HTTP selftest и отдельный протокол коммутаторов без Pro.
- `reference/serials/equipment-models.json`, редакция 11.11.26:
  подтверждённые серверные серии, MAC, этикетки, шкафы.
- `psw_stand-dev/TestThread.cpp`, `get_selftest_result`: проверка
  `model_num`/`model_num_mac_print`; `psw_stand-dev/test.cpp`, получение
  номера и расчёт MAC; `Network/net_database.cpp`, параметры серверного GET.
  Исторические исходники не менялись.
- [Руководство PSW-1G4F v13, разделы 2 и 4](https://tfortis.ru/assets/files/re/psw-1g4f_v13_re.pdf):
  четыре Fast Ethernet и два отдельных гигабитных порта RJ45/SFP.
- [Официальный перечень моделей и портов](https://tfortis.ru/assets/files/price/prajs-tfortis-01.10.2025_sajt.pdf):
  семейства 6F/8F и два SFP; производственные допуски из прайса не выводились.

Генерация и обе проверки размещения:

```sh
python3 tools/generate_switch_qualification_profiles.py
```

Команда заново создаёт только этот набор, затем запускает ProfileLayout
`--write` и отдельный `--check`. Ручные изменения этих десяти исходных
файлов при генерации будут заменены; четыре базовых профиля не затрагиваются.

Для повторения тестов используйте фильтр `SwitchQualificationProfileTests`.
Путь для сохранения образцов задаёт `TFORTIS_QUALIFICATION_EVIDENCE`.
Названия `QUALIFICATION-SIMULATION` и `qualification-fixture` в образцах
помечают тестовые данные; это не журналы физических изделий.
