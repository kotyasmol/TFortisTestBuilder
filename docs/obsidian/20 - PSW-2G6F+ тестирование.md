# PSW-2G6F+: тестирование

Это **старый коммутатор без Pro**. Исполняемый профиль —
`profiles/PSW_2G6F_plus_full_algorithm.json`; страница устройства —
`http://192.168.0.1/test.shtml`. Здесь описан текущий граф TestBuilder,
а не все возможности старого Qt. Подробнее о расхождениях: [описание
миграции](../PSW_2G6F_plus_migration.md).

## Порядок штатного теста

Верхний уровень профиля оформлен как `Start` → именованные `Subtest` →
`End`, с отдельными аварийными подтестами. Цикл проверки 12 линий PoE
находится внутри «4. Проверка напряжения 12 линий PoE»; DataTest, печать
четырёх этикеток и финальный диалог также имеют собственные подтесты.
Внутри сохранены существующие ноды и параметры; новых типов нод нет.

| Этап | Что делает граф | Условие перехода |
| --- | --- | --- |
| Подготовка питания и PoE | Выключает AC1/AC2; обнуляет нагрузки, задаёт двум каналам каждого EL60v5 по 13 Вт, выдерживает 10 с. | Modbus-записи подтверждены. |
| Запуск DUT | Включает AC1, ждёт 20 с, чистит ARP, получает `/test.shtml`. | `init_ok=1`, `dev_type=6`, ADC/SFP/PoE по условиям ниже. |
| Версия ПО | Нода `Update PSW Firmware` сравнивает `Dut.firmvare_vers` с целью 0.2.13. | Равная или более новая версия проходит без загрузки; при старой версии выполняется веб-обновление. |
| Серийный номер | Запрос номера по CPU ID устройства. | Только серверный номер 600000..665535; далее используется повторно. |
| Линии PoE | На slave 1, 3, 5, 7, 9, 11 читает линии B (`1403`) и A (`1402`) после пауз; каждая должна быть 53–56 В. | До трёх live-чтений на линию. |
| Sensor1 | Сбрасывает IO-2 OUT1/OUT2 (`1500/1501=0`), читает исходную страницу, пишет `1500=1`, ждёт `Dut.sensor_1=1`, затем пишет `1500=0`. | Контакт должен замкнуться по новой веб-странице за 60 с. |
| DataTest | Три медные пары `.2/.3`, `.4/.5`, `.6/.7` по 100 Мбит/с и SFP `.8/.9` по 1000 Мбит/с, оба направления. | По 5 с на направление; проверяются потери и скорость передачи. |
| MAC | Использует ранний серийник, строит MAC `C0:11:A6:06:HH:LL`, отправляет UDP-команду `CONFIG/mw`, выдерживает 7 с, выключает AC1 на 10 с, включает, снова читает selftest. | `DutAfterMac.default_mac` совпадает с вычисленным MAC. |
| Этикетка и отчёт | Печатает четыре этикетки, собирает финальный selftest и отчёт, отправляет отчёт после подтверждения оператора. | Успешное выполнение нод. |
| Завершение | Выключает AC1/AC2 и PoE-нагрузки. | Все записи завершены. |

При ошибке отдельный cleanup-граф сбрасывает IO-2 OUT1/OUT2, питание и
PoE-нагрузки. Если серийника ещё нет, аварийная ветка пробует получить его по CPU ID при
`Dut.dev_type=6`. Отчёт строится только с серверным номером 600000..665535
и отправляется после подтверждения оператора; CPU ID номер не заменяет.
Sensor0 и Sensor2 намеренно не проверяются; автоматического DFU в графе нет.

Вкладка сетевой конфигурации может предложить распределение по текущему
линку: шесть карт 100 Мбит/с на `.2–.7`, две карты 1 Гбит/с на `.8–.9`,
две отключённые карты на резервные `.10–.11`. Скорость не указывает номер
физического порта внутри группы; перед применением нужно сверить пары кабелей.

## Аппаратный selftest PSW-2G6F+ (2026-09-29)

У `Selftest Check` добавлен флаг `psw2G6FHardwareChecks` (в редакторе:
«PSW-2G6F+: ADC, SFP и PoE»). Включён при первом запуске и после записи MAC;
по умолчанию выключен, другие модели не затрагивает. Проверяются свежие
значения XML, а не оставшиеся переменные прошлого снимка.

| Проверка | Условие |
| --- | --- |
| ADC 2.5 В | Сырой код 2895..3305. |
| ADC 1.2 В | `adc_1_2 - (adc_2_5 - 3100) * 0.48` в 1364..1627. |
| ADC 1.5 В | `adc_1_5 - (adc_2_5 - 3100) * 0.6` в 1717..2021. |
| Дополнительные ADC 1.0/1.8 В | При наличии ненулевого поля: 1128..1352 / 2071..2393. Это внутренние напряжения платы, не Sensor0/2. |
| SFP7 и SFP8 | PRESENT и SignalDetect ненулевые. ID≠3 — предупреждение I2C, без отказа изделия, как в Qt. |
| Статусы PoE DUT | `poe_a_1_state`..`poe_a_3_state` ненулевые, как в фактическом цикле Qt при `port_num=6`. |
| Силовые линии PoE | Все 12 A/B проверяются отдельно по EL60: 53000..56000 мВ. |

Границы включительные; некорректные числа, NaN и бесконечность отвергаются.
Обязательные ADC 1.2/1.5/2.5 В не могут быть пропущены из-за отсутствия/нуля.
Для каждой аппаратной проверки в отчёт записывается результат и значение;
отказ влияет на итог изделия. Нет обязательной проверки `hw_vers`: старый
модельный файл не включает `hw_check` и не задаёт требуемую ревизию.

Ошибки Qt намеренно не воспроизводятся: отсутствие обязательных ADC не
считается успехом; отказ ADC 2.5 В действительно останавливает тест; SFP7/8
не исключаются из-за ошибочного ограничения `i < port_num`. Неверный SFP ID
остаётся диагностикой, как в Qt. Ошибочную
формулу ADC 1.1 В из общего кода Qt не переносили: текущая модель этого поля
не выдаёт. Напряжения PoE оцениваются по корректным пределам EL60, а не по
невыполнимому условию Qt `> max && < min`.

PoE выполняется до Sensor1: B → 200 мс → A → 200 мс, до трёх чтений каждой
линии с паузой 600 мс перед чтением. Нижний предел A=0 и пауза 5 с перед B
из рабочего профиля заменены по запросу на перенос алгоритма.

## Результат изделия и доставка отчёта

`BuildReport.DevicePassed` — итог проверок изделия, `ReportDelivery.Status` —
`Pending`, `Sending`, `Sent` или `Failed`. Недоступность сервера не превращает
исправный DUT в брак: нода отправки возвращает False, но в данном профиле оба
выхода ведут к завершению отчётной ветки и выключению стенда. Итоговая строка
и заключительный диалог явно показывают, отправлен ли отчёт.

Локальная копия сохраняется перед обращением к серверу, в том числе при
неверном адресе сервера. Ошибка записи копии также обрабатывается нодой.
Отмена подтверждения оставляет статус «сформирован, но не отправлен».
Cleanup-подтесты получают отдельные лимиты: 60 с на аппаратное выключение,
5 минут на ветку с подтверждением оператора и получением номера/отправкой;
таймаут одной ветки не лишает следующую её времени.

DFU (Device Firmware Upgrade) — низкоуровневая загрузка/восстановление прошивки
микроконтроллера по USB через `dfu-util`. В Qt это отдельная кнопка, а не шаг
обычного теста PSW-2G6F+. В текущем цикле используется веб-обновление до 0.2.13;
Sensor0/Sensor2 и отдельный DFU-инструмент не добавлены.

## Как работает прошивка

В текущем профиле `targetVersion=0.2.13`, `forceUpdate=false`. Код версии
из selftest — шестнадцатеричный: `208` означает 0.2.8 (decimal 520),
`20c` означает 0.2.12 (decimal 524), `20d` — 0.2.13 (decimal 525).
Если версия уже равна цели или новее,
нода записывает в лог причину пропуска и не отправляет запросов прошивки.
Для ручного допуска отката с более новой версии параметр `forceUpdate`
можно включить в ноде; равная версии цель всё равно пропускается.

Если загрузка необходима, нода последовательно:

1. Проверяет, что на компьютере стенда есть непустой
   `C:/FortTelecom/Launcher/TFortisStandNew/firmwares/sw407/sw407-0.2.13-05.09.2025.img`.
   SHA-256 по решению оператора не проверяется.
2. Отправляет `GET /clear.shtml` и ждёт 10 с.
3. Отправляет файл multipart-запросом `POST /mngt/update.shtml` в формате
   старого Qt-загрузчика и ждёт 10 с после ответа.
4. Отправляет `GET /mngt/update.shtml?Update=Update`, ждёт 40 с на
   перезапуск DUT.
5. Снова читает `/test.shtml` и требует новую версию не ниже 0.2.13.

Лог `[FW]` показывает исходную и целевую версии, решение о пропуске,
размер образа, HTTP-коды, итоговый URL и начало с концом текстового ответа,
длительность каждого запроса, паузы, результат
повторного selftest и этап отказа. Успешный HTTP-ответ на POST сам по себе
не доказывает смену версии; подтверждение даёт только новая страница.

## Текущее наблюдение по Sensor1

В прогоне `test-run_20260923_190751` с прошивкой 0.2.8 (`208`) при
`IO-2:1500=0` selftest показывал `sensor_1=1`. После подтверждённой записи
`1500=1` пять снимков показали `sensor_1=0`; `sensor_0=0` и `sensor_2=1`
не менялись. Это обратная полярность относительно старого Qt-алгоритма,
ожидающего `sensor_1=1` после `1500=1`. Возврат целевой версии на 0.2.13
позволил позднее проверить поведение (см. прогон 2026-09-25 ниже). Условие Sensor1 не инвертировано.

В прогоне `test-run_20260923_192357` запросы для образа 0.2.13 вернули
HTTP 200, но повторный selftest всё ещё показал `208` (0.2.8). Тест
остановился до Sensor1. Ответы веб-страницы в этом логе обрезаны на первых
240 символах, поэтому причина отказа устройства из них не видна. Новые логи
сохраняют начало и конец ответа для проверки сообщения об ошибке.

В прогоне `test-run_20260925_144217` версия `20d` подтверждена, а Sensor1
сменился с `0` на `1` и прошёл. Первая пара DataTest `.2/.3` прошла в обе
стороны без потерь. Для следующей пары карта `.5` имела статус `Down`, для
пары `.6/.7` карта `.6` имела статус `Down`, а SFP-карта `.8` согласовала
100 вместо требуемых 1000 Мбит/с. Это состояния линка Windows до передачи
пакетов. Кроме того, на slave 9 линия PoE A (`1402`) дала 600 мВ, но
загруженный на стенде граф проверял её по диапазону `0..56000` мВ. В
репозиторном профиле обе линии проверяются по `53000..56000` мВ. Нужно
загрузить актуальный профиль или вернуть эту нижнюю границу вручную; иначе
тест пропускает напряжение ниже нормы.

## Отличие от Pro

У этой модели `/test.shtml`, UDP-запись MAC, 12 линий PoE и одна SFP-пара.
Профиль Pro использует другую страницу, другой способ записи MAC и другие
этапы: [[21 - PSW+UPS-Box 8x2Pro тестирование]].

## Проверка изменения 2026-09-29

267 автотестов проекта прошли (включая 98 связанных с изменением): корректный снимок платы, неисправные и
отсутствующие ADC/SFP/PoE, границы ADC с поправкой, отсутствие ложного допуска
по старому контексту, сериализация и компиляция профиля, ранний SN и аварийный
отчёт с подставным HTTP-сервисом, ошибки сервера и локального сохранения.
Отправки в производственную базу в этих тестах нет. Новый полный аппаратный
прогон с ужесточёнными условиями ещё не выполнен: DUT недоступен по
`192.168.0.1/test.shtml` во время этой проверки.
