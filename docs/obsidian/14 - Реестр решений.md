# Реестр решений

Здесь фиксируются решения, которые меняют архитектуру, UX, формат данных или
рабочий процесс. Код и тематические заметки остаются источником деталей;
реестр отвечает на вопросы «что выбрали», «почему» и «что из этого следует».

## Правило ведения

- Новый номер: `ADR-XXX`; статус — `Предложено`, `Принято`, `Заменено` или `Отменено`.
- В запись попадает только решение, подтвержденное владельцем проекта или реализованное в коде.
- Если решение изменено, старая запись не переписывается: в ней ставится ссылка на заменяющую.
- Для каждой принятой записи обновляются тематическая заметка и [[13 - Карта актуальности]].

## ADR-001 — Ручная композиция общих сервисов

| Поле | Значение |
|---|---|
| Статус | Принято (существующая архитектура) |
| Дата | Историческое, зафиксировано 2026-08-17 |
| Область | Архитектура приложения |

`MainWindowViewModel` вручную создаёт общие `ModbusService`, `SlaveManager`,
`TestViewModel`, `ModbusMonitoringViewModel` и `SettingsViewModel`; DI-контейнер
не используется. Это уменьшает стартовую сложность, но при добавлении общих
сервисов нужно явно контролировать их владение и освобождение ресурсов.

Подробности: [[02 - Архитектура проекта]].

| Поле | Значение |
|---|---|

`NodeViewModel` содержит UI-параметры и коннекторы, а `ITestStep` выполняет

## ADR-003 — Сохранять обратную совместимость JSON-профилей

| Поле | Значение |
|---|---|
| Статус | Принято (существующая архитектура) |
| Дата | Историческое, зафиксировано 2026-08-17 |
| Область | Профили тестов |

Существующие `type` и имена коннекторов не меняются без миграции. Новые поля
делаются nullable, при загрузке имеют дефолты, а legacy-имена получают aliases.
Это снижает риск потери уже созданных производственных профилей.

Подробности: [[06 - JSON профили]], [[11 - Расширение проекта]].

## ADR-004 — Modbus-мониторинг и runtime используют одну шину последовательно

| Поле | Значение |
|---|---|
| Статус | Принято (существующая архитектура) |
| Дата | Историческое, зафиксировано 2026-08-17 |
| Область | Modbus RTU |

Все обращения `ModbusService` синхронизируются `_ioLock`, а минимальная пауза
между запросами составляет 150 мс. Проверочные ноды обычно читают значения из
`RegisterState`; запись регистра работает напрямую через сервис. Решение
защищает один COM-порт от параллельных запросов, но требует учитывать свежесть
мониторинга при проектировании тестов.

Подробности: [[07 - Modbus и мониторинг]].

## ADR-005 — Master-detail для вкладки Modbus

| Поле | Значение |
|---|---|
| Статус | Принято и реализовано |
| Дата | 2026-08-17 |
| Область | UX мониторинга Modbus |

Вместо развёрнутой таблицы в каждой карточке устройства используется компактный
список slave слева и единая таблица регистров выбранного устройства в центре.
Добавлены поиск по адресу/названию, фильтр категории и фильтр writable-регистров.

Причина: крупные карты регистров и несколько устройств создавали длинный общий
скролл и затрудняли поиск нужного значения. Последствие: одновременно видна
одна полная карта регистра; для сравнения нескольких устройств потребуется
отдельный режим в будущем.

Подробности: [[03 - Работа с приложением]], [[07 - Modbus и мониторинг]].

## ADR-006 — Хранить основной рабочий профиль под Git

| Поле | Значение |
|---|---|
| Статус | Принято и реализовано |
| Дата | 2026-08-21 |
| Область | Рабочий процесс профилей |

Основной профиль `PSW_UPS_Box_8x2Pro_full_algorithm_polling.json` хранится в
корневой папке `profiles` и изменяется из приложения по исходному пути.
`AppSettings` автоматически выбирает эту папку, если сохраненный каталог пуст
или недоступен. Для сборок вне репозитория профиль копируется рядом с exe.

Причина: JSON больше не нужно вручную переносить между компьютером разработки
и стендом; изменения доставляются через обычный Git workflow. Следствие:
сохранение загруженного рабочего профиля создает видимый Git diff, который
нужно осознанно закоммитить вместе с изменениями сценария.

Подробности: [[01 - Быстрый старт]], [[03 - Работа с приложением]],
[[10 - Настройки логирование тесты]].
