# Реестр решений

Здесь фиксируются решения, которые меняют архитектуру, UX, формат данных или
рабочий процесс. Код и тематические заметки остаются источником деталей;
реестр отвечает на вопросы «что выбрали», «почему» и «что из этого следует».

## Правило ведения

- Новый номер: `ADR-XXX`; статус — `Предложено`, `Принято`, `Заменено` или `Отменено`.
- В запись попадает только решение, подтвержденное владельцем проекта или реализованное в коде.
- Если решение изменено, старая запись не переписывается: в ней ставится ссылка на заменяющую.
- Для каждой принятой записи обновляются тематическая заметка и [[13 - Карта актуальности]].

## ADR-001 — Ручная композиция общих сервисов

| Поле | Значение |
|---|---|
| Статус | Принято (существующая архитектура) |
| Дата | Историческое, зафиксировано 2026-08-17 |
| Область | Архитектура приложения |

`MainWindowViewModel` вручную создаёт общие `ModbusService`, `SlaveManager`,
`TestViewModel`, `ModbusMonitoringViewModel` и `SettingsViewModel`; DI-контейнер
не используется. Это уменьшает стартовую сложность, но при добавлении общих
сервисов нужно явно контролировать их владение и освобождение ресурсов.

Подробности: [[02 - Архитектура проекта]].

## ADR-003 — Сохранять обратную совместимость JSON-профилей

| Поле | Значение |
|---|---|

Существующие `type` и имена коннекторов не меняются без миграции. Новые поля
делаются nullable, при загрузке имеют дефолты, а legacy-имена получают aliases.
Это снижает риск потери уже созданных производственных профилей.

## ADR-004 — Modbus-мониторинг и runtime используют одну шину последовательно

| Поле | Значение |
|---|---|
| Статус | Принято (существующая архитектура) |
| Дата | Историческое, зафиксировано 2026-08-17 |
| Область | Modbus RTU |

Все обращения `ModbusService` синхронизируются `_ioLock`, а минимальная пауза
между запросами составляет 150 мс. Проверочные ноды обычно читают значения из
`RegisterState`; запись регистра работает напрямую через сервис. Решение
защищает один COM-порт от параллельных запросов, но требует учитывать свежесть
мониторинга при проектировании тестов.

Подробности: [[07 - Modbus и мониторинг]].

## ADR-005 — Master-detail для вкладки Modbus

| Поле | Значение |
|---|---|
| Статус | Принято и реализовано |
| Дата | 2026-08-17 |
| Область | UX мониторинга Modbus |

Вместо развёрнутой таблицы в каждой карточке устройства используется компактный
список slave слева и единая таблица регистров выбранного устройства в центре.
Добавлены поиск по адресу/названию, фильтр категории и фильтр writable-регистров.

Причина: крупные карты регистров и несколько устройств создавали длинный общий
скролл и затрудняли поиск нужного значения. Последствие: одновременно видна
одна полная карта регистра; для сравнения нескольких устройств потребуется
отдельный режим в будущем.

Подробности: [[03 - Работа с приложением]], [[07 - Modbus и мониторинг]].

## ADR-006 — Хранить основной рабочий профиль под Git

| Поле | Значение |
|---|---|
| Статус | Принято и реализовано |
| Дата | 2026-08-21 |
| Область | Рабочий процесс профилей |

Основной профиль `PSW_UPS_Box_8x2Pro_full_algorithm_polling.json` хранится в
корневой папке `profiles` и изменяется из приложения по исходному пути.
`AppSettings` автоматически выбирает эту папку, если сохраненный каталог пуст
или недоступен. Для сборок вне репозитория профиль копируется рядом с exe.

Причина: JSON больше не нужно вручную переносить между компьютером разработки
и стендом; изменения доставляются через обычный Git workflow. Следствие:
сохранение загруженного рабочего профиля создает видимый Git diff, который
нужно осознанно закоммитить вместе с изменениями сценария.

Подробности: [[01 - Быстрый старт]], [[03 - Работа с приложением]],
[[10 - Настройки логирование тесты]].

## ADR-007 — Повторить однопроходный алгоритм legacy Selftest

| Поле | Значение |
|---|---|
| Статус | Принято, реализовано и подтверждено на стенде |
| Дата | 2026-08-21 |
| Область | Selftest устройства |

Каждая попытка `Selftest Check` повторяет последовательность исходной Selenium-утилиты:
один headless-браузер открывает URL с query-параметрами, ждет загрузку страницы,
выдерживает 10 секунд и один раз читает `PageSource`. После этого браузер закрывается.
Перед браузером выполняется параллельная ICMP/TCP-проверка доступности DUT. Если
устройство ещё не отвечает, после `PollIntervalMs` повторяется только эта лёгкая
проверка. Если XML еще нет уже после браузерной попытки, цикл также продолжается.
Общий лимит рабочего профиля составляет 180 секунд, интервал — 5 секунд.

POST-авторизация и HTTP fallback исключены. Для Pro используется LuCI;
добавленные позднее профили старого PSW явно читают `/test.shtml` тем же
браузерным способом. Процесс браузера и его дерево теперь контролируются
общим координатором; актуальная реализация — [[09 - HTTP сеть отчеты печать]].
Решение принято, чтобы убрать отличия одной попытки от ранее
работавшей производственной реализации и проверить её поведение независимо
от более сложной логики получения страницы.

Стендовая проверка 2026-08-21 подтвердила решение: ранние попытки выполнялись во время
загрузки DUT, а одна из последующих получила selftest и успешно завершила ноду.

Подробности: [[05 - Справочник нод]], [[09 - HTTP сеть отчеты печать]],
[[18 - Selftest и загрузка DUT]].

## ADR-008 — Сеть настраивается отдельно от исполняемого графа

| Поле | Значение |
|---|---|
| Статус | Уточнено текущей реализацией 2026-10-28 |
| Первоначальная дата | 2026-08-21 |
| Область | Сеть стенда и DataTest |

Конфигуратор сетевых адаптеров как нода удалён. DataTest только проверяет
заданные пары и не меняет адреса ОС во время прогона.

Первоначальное ограничение «приложение вообще не вызывает netsh» больше
не действует: отдельная вкладка «Сеть» позволяет инженеру назначать
адреса и переименовывать адаптеры. План, подписи и привязки хранятся локально,
пары DataTest — в профиле. Маска, число адресов и скорости редактируются.
Изменение настроек и применение к ОС — отдельные действия; применение
блокируется на время теста. Подробности — [[09 - HTTP сеть отчеты печать]].

## ADR-009 — Data Test выполняет пары последовательно и вне UI-потока

| Поле | Значение |
|---|---|
| Статус | Принято и реализовано |
| Дата | 2026-08-21 |
| Область | Data Test и отзывчивость приложения |

Все строки `PortsText` проверяются строго последовательно. Открытие pcap-карт,
прогрев и генерация трафика для активной пары выполняются в рабочем потоке,
чтобы синхронные вызовы SharpPcap не блокировали Avalonia UI. Непрерывная пачка
ограничена 512 пакетами, после чего генератор уступает процессор. Между парами
используется настраиваемая пауза `InterPairDelayMs`, для рабочего профиля — 5 секунд.

Причина: при `1000 Mbps` и размере пакета 1514 байт генератор выполняет около
82,5 тысячи синхронных отправок в секунду. Длинный тест на слабой стендовой машине
мог монополизировать UI-поток и внешне полностью зависать. Изменение сохраняет
гигабитную цель и критерий `tx deficit`: если машина физически не успевает
сгенерировать поток, тест завершится измеряемой ошибкой, а не зависанием интерфейса.

Подробности: [[05 - Справочник нод]], [[09 - HTTP сеть отчеты печать]].

## ADR-010 — Selftest-снимки и универсальное чтение динамики

| Поле | Значение |
|---|---|
| Статус | Принято и реализовано |
| Дата | 2026-09-01 |
| Область | DUT API, UPS-тест и палитра нод |

Полная тестовая страница загружается один раз для аппаратного снимка. Исходные
`ups_det`, `akb_voltage` и `ups_rez` проверяются прямо из него. После управляющего действия
рабочий UPS-профиль обновляет весь снимок через `Wait Variable Until` в режиме
`SelftestSnapshot`. Скалярный `HttpGet` остается универсальной альтернативой для прошивок,
где endpoint реально существует.

В UPS-тесте `ups_det` означает наличие платы, а `akb_voltage` и исходный `ups_rez`
берутся из того же selftest-снимка. Динамический `ups_rez` означает текущий источник
питания и после отключения/возврата AC проверяется повторными снимками до `1`/`0`.
Таймаут перехода является провалом.

Специализированные `Get UPS Status`, `Get UPS Voltage`, `Get IRP Status` и
legacy poll actions на дату принятия решения продолжали десериализоваться.
Дополнение 2026-10-01: эти ноды и режимы полностью удалены по запросу;
импорт старого профиля выдаёт ошибку с подсказкой перехода на универсальные ноды.

Подробности: [[05 - Справочник нод]], [[06 - JSON профили]],
[[09 - HTTP сеть отчеты печать]], [[19 - Поля тестовой страницы DUT]].
