# Selftest и загрузка DUT

Эта заметка фиксирует подтвержденное на рабочем стенде поведение `Selftest Check`.
Ее цель — не допустить возврата к вариантам, которые уже оказались нерабочими.

## Главное правило

> После подачи питания нода до трёх минут проверяет готовность коммутатора каждые
> пять секунд. Пока DUT не отвечает по ICMP или TCP-порту страницы, браузер не
> запускается. После появления устройства browser-попытка открывает исходный URL
> и ждёт тестовую страницу в пределах того же общего срока.

## Подтвержденные факты стенда

- Веб-интерфейс и динамический selftest могут появиться раньше, но это не гарантировано.
- Ручной сценарий «подать питание, дождаться устройства и открыть браузер» работает.
- Пока DUT загружается, не нужно многократно создавать Chrome: достаточно лёгкой
  проверки ICMP/TCP с интервалом пять секунд.
- Когда сеть уже доступна, браузер всё ещё может вернуть страницу без `<selftest>`
  или другой непригодный DOM. Нода должна продолжать ожидание.
- После реализации внешнего цикла до 300 секунд selftest успешно прошел на реальном стенде
  2026-08-21. Это историческая проверка; текущий согласованный лимит — 180 секунд.
- Исправление сетевых карт не заменяет ожидание загрузки. Маршрут и готовность DUT — разные
  причины; их нужно диагностировать отдельно.

## Почему legacy-программа вводит в заблуждение

Старая отдельная C#-утилита выполняла только одну попытку:

1. создавала `ChromeDriver`;
2. открывала URL deviceinfo;
3. ждала 10 секунд;
4. читала один `driver.PageSource`;
5. искала `<selftest>` и `default_mac`.

Этот код сам по себе не умеет ждать загрузку коммутатора. Исторически
утилита либо запускалась внешней C++-программой в более поздний момент, либо внешний
сценарий обеспечивал повтор. Поэтому копировать однопроходность утилиты на уровень всей
ноды нельзя.

## Правильный алгоритм

Общий цикл:

```text
deadline = 3 минуты после запуска ноды

пока deadline не истек:
    параллельно проверить ICMP и TCP-порт исходного URL

    если DUT ещё недоступен:
        подождать PollIntervalMs
        продолжить цикл без запуска браузера

    запустить одну legacy-браузерную попытку по исходному URL
    дождаться document.readyState == complete
    подождать еще 10 секунд
    один раз получить PageSource

    если найден <selftest> с default_mac:
        разобрать XML и завершить ноду успешно

    закрыть браузер
    подождать PollIntervalMs

только после deadline завершить ноду ошибкой
```

Рабочие значения:

| Параметр | Значение | Зачем |
|---|---:|---|
| Общий `TimeoutMs` | `180000` мс | Общий срок ожидания запуска DUT и появления тестовой страницы. |
| Максимум проверки готовности | `1000` мс | Не задерживает следующий пятисекундный цикл надолго. |
| Максимум одной попытки | `30000` мс | Зависшая загрузка не должна занять весь общий timeout. |
| Ожидание после загрузки страницы | `10000` мс | Повторяет `Thread.Sleep(10000)` legacy-утилиты. |
| `PollIntervalMs` | `5000` мс | Пауза между проверками готовности/страницы. |

Каждая browser-попытка выполняет штатный алгоритм одного URL, одной DOM-выгрузки
и 10-секундного ожидания. Chrome запускается с чистым профилем в фоновой задаче;
DevTools явно выполняет `Page.navigate` по исходному URL. После ошибки процесс
завершается, временный профиль удаляется, а внешний цикл продолжает работу.
Отдельного состояния worker, блокирующего следующий опрос, нет.

Все четыре `Selftest Check` в рабочем профиле имеют `timeoutMs: 180000` и
`pollIntervalMs: 5000`. Runtime поднимает старые DUT timeout до `160000` мс
включительно до `180000` мс.

## Что намеренно не используется

- Нет отдельной POST-авторизации: она не решала ожидание загрузки DUT.
- Нет обычного `HttpClient` fallback: он не воспроизводит JavaScript DOM страницы.
- Нет запроса `/test.shtml`: актуальная страница берется только по исходному URL ноды.
- Нет переключения на другой URL между попытками.
- Нет окончательного провала после первого DOM без selftest.

Эти варианты нельзя возвращать без нового воспроизводимого стендового доказательства.

## Ожидаемые логи

Пока DUT загружается, следующие строки являются нормальными:

```text
Selftest waits for DUT web endpoint (probe N, timeout 1000 ms).
Selftest next DUT availability probe in 5000 ms.
```

Когда DUT уже отвечает, но XML ещё не появился, ожидаются строки:

```text
Selftest page is not ready yet (attempt N, url ...): ...
Selftest next browser attempt in 5000 ms.
```

Они не означают завершение теста. Окончательный провал фиксируется только строкой
`[ERROR] Selftest failed` после исчерпания общего timeout.

При успехе после одной из попыток появляются результаты разбора и:

```text
[OK] Selftest passed: ...
```

## Если проблема появится снова

В прогоне 2026-09-09 первичный selftest получил 82 поля с 11-й попытки;
после записи MAC и перезапуска окно целиком зависло на браузерной попытке.
Пользователь подтвердил ручную остановку отладки: строки `TaskCanceledException`
и финальный `0xffffffff` сами по себе не доказывают необработанное исключение.
В коде обнаруживались синхронные операции браузера и cleanup вне прежнего
таймера. Попытка обернуть весь жизненный цикл в отдельный runner дала регрессию:
ожидание DUT перестало работать штатно. По обратной связи пользователя этот
runner удалён, а подтверждённый стендом алгоритм восстановлен. Точное место
первоначального зависания без stack trace по-прежнему не установлено.

В этом же прогоне все три UDP-команды MAC получили `ConnectionReset`,
native `10054`; перезапуск и ARP очистка прошли. Значение MAC после перезапуска
не было прочитано до ручной остановки. Это отдельная проблема недоступности
UDP-обработчика, а не следствие браузерного зависания.

1. Проверить, что в первой строке ноды указан эффективный timeout `180000 ms`.
2. Пока DUT выключен, убедиться в появлении `next DUT availability probe in 5000 ms`
   без запуска новых процессов Chrome.
3. После появления DUT должна быть строка `DUT web endpoint is reachable ...; opening browser`.
4. Если автоматическая попытка не получает XML, вручную открыть тот же URL и
   сопоставить момент с логом ноды.
5. Отдельно выполнить `Find-NetRoute -RemoteIPAddress 192.168.0.1` и
   `Test-NetConnection 192.168.0.1 -Port 80`, если страница не открывается вообще.
6. Сохранить лог от первой попытки до итогового результата; не диагностировать проблему
   только по одной промежуточной строке `page is not ready yet`.

## Защита от регрессии

Unit-тесты фиксируют инварианты:

- до доступности DUT браузер не запускается;
- после страницы без XML нода повторяет тот же исходный URL;
- нода не подменяет его на `/test.shtml`;
- рабочий профиль хранит `timeoutMs: 180000` и `pollIntervalMs: 5000`.

Команда проверки:

```powershell
dotnet test TestBuilder.Tests/TestBuilder.Tests.csproj --no-restore
```

Состав XML и значения всех известных полей тестовой страницы описаны отдельно в
