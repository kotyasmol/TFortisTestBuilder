# Selftest и загрузка DUT

Эта заметка фиксирует подтвержденное на рабочем стенде поведение `Selftest Check`.
Ее цель — не допустить возврата к вариантам, которые уже оказались нерабочими.

## Главное правило

> Одна браузерная попытка повторяет legacy Selenium-утилиту, но сама нода обязана
> повторять такие попытки до пяти минут. Отсутствие `<selftest>` в первые четыре
> минуты после подачи питания является нормальным состоянием загрузки DUT, а не
> окончательной ошибкой теста.

## Подтвержденные факты стенда

- Коммутатор после подачи питания может запускаться до четырех минут.
- Веб-интерфейс и динамический selftest могут появиться раньше, но это не гарантировано.
- Пока DUT загружается, браузер может вернуть страницу без `<selftest>`, ошибку соединения
  или другой непригодный DOM. Нода должна продолжать ожидание.
- После реализации внешнего цикла до 300 секунд selftest успешно прошел на реальном стенде
  2026-08-21.
- Исправление сетевых карт не заменяет ожидание загрузки. Маршрут и готовность DUT — разные
  причины; их нужно диагностировать отдельно.

## Почему legacy-программа вводит в заблуждение

Старая отдельная C#-утилита выполняла только одну попытку:

1. создавала `ChromeDriver`;
2. открывала URL deviceinfo;
3. ждала 10 секунд;
4. читала один `driver.PageSource`;
5. искала `<selftest>` и `default_mac`.

Этот код сам по себе не умеет ждать четырехминутную загрузку коммутатора. Исторически
утилита либо запускалась внешней C++-программой в более поздний момент, либо внешний
сценарий обеспечивал повтор. Поэтому копировать однопроходность утилиты на уровень всей
ноды нельзя.

## Правильный алгоритм

Общий цикл:

```text
deadline = 5 минут после запуска ноды

пока deadline не истек:
    запустить одну legacy-браузерную попытку по исходному URL
    дождаться document.readyState == complete
    подождать еще 10 секунд
    один раз получить PageSource

    если найден <selftest> с default_mac:
        разобрать XML и завершить ноду успешно

    закрыть браузер
    подождать PollIntervalMs

только после deadline завершить ноду ошибкой
```

Рабочие значения:

| Параметр | Значение | Зачем |
|---|---:|---|
| Общий `TimeoutMs` | `300000` мс | Четыре минуты загрузки DUT плюс запас на последнюю попытку. |
| Максимум одной попытки | `30000` мс | Зависшая загрузка не должна занять весь общий timeout. |
| Ожидание после загрузки страницы | `10000` мс | Повторяет `Thread.Sleep(10000)` legacy-утилиты. |
| `PollIntervalMs` | `5000` мс | Пауза между полными браузерными попытками. |

Все пять `Selftest Check` в рабочем профиле имеют `timeoutMs: 300000`. Runtime также
автоматически поднимает старые DUT timeout до 240000 мс включительно до 300000 мс.

## Что намеренно не используется

- Нет отдельной POST-авторизации: она не решала ожидание загрузки DUT.
- Нет обычного `HttpClient` fallback: он не воспроизводит JavaScript DOM страницы.
- Нет запроса `/test.shtml`: актуальная страница берется только по исходному URL ноды.
- Нет переключения на другой URL между попытками.
- Нет окончательного провала после первого DOM без selftest.

Эти варианты нельзя возвращать без нового воспроизводимого стендового доказательства.

## Ожидаемые логи

Пока DUT загружается, следующие строки являются нормальными:

```text
Selftest page is not ready yet (attempt N, url ...): ...
Selftest next browser attempt in 5000 ms.
```

Они не означают завершение теста. Окончательный провал фиксируется только строкой
`[ERROR] Selftest failed` после исчерпания общего timeout.

При успехе после одной из попыток появляются результаты разбора и:

```text
[OK] Selftest passed: ...
```

## Если проблема появится снова

1. Проверить, что в первой строке ноды указан эффективный timeout `300000 ms`.
2. Убедиться, что между предупреждениями есть `Selftest next browser attempt...`, то есть
   внешний цикл не удален.
3. Засечь время от подачи питания: до четырех минут отсутствие страницы допустимо.
4. После четырех минут вручную открыть тот же `192.168.0.1` и проверить готовность DUT.
5. Отдельно выполнить `Find-NetRoute -RemoteIPAddress 192.168.0.1` и
   `Test-NetConnection 192.168.0.1 -Port 80`, если страница не открывается вообще.
6. Сохранить лог от первой попытки до итогового результата; не диагностировать проблему
   только по одной промежуточной строке `page is not ready yet`.

## Защита от регрессии

Unit-тесты фиксируют два инварианта:

- после страницы без XML нода повторяет тот же исходный URL;
- нода не подменяет его на `/test.shtml`.

Команда проверки:

```powershell
dotnet test TestBuilder.Tests/TestBuilder.Tests.csproj --no-restore
```
