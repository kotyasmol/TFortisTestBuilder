# Сборка и публикация обновления

Повторяемая инструкция для Codex в любом диалоге проекта: Windows x64 ZIP,
перенос на Вышенскую и публикация в корпоративную beta-папку. История запусков —
[[26 - Выпуск и диагностика 2026-11-02]] и [[27 - Публикация 1.0.2-beta 2026-11-09]].
Их номера версий, device ID, количество файлов и маркер нельзя считать текущими.

## Запросы для нового диалога

Только архив:

> Используй $tfortis-release. Собери свежий Windows-комплект из текущей ветки
> TFortisTestBuilder. Возьми версию из проекта, включи четыре стандартных
> профиля, выполни проверки и дай ZIP. На сервер пока не загружай.

Сборка и публикация:

> Используй $tfortis-release. Собери текущую версию TFortisTestBuilder и загрузи
> в корпоративную beta-папку через Вышенскую. Сделай и проверь новую резервную
> копию, проверь весь комплект, маркер лаунчера обнови последним. Рабочие профили
> и настройки сотрудников сохрани. Результат запиши в документацию.

Если skill не отображается:

> Прочитай AGENTS.md и docs/obsidian/28 - Сборка и публикация обновления.md
> в /Users/kotyasmesh/Documents/tfortis и выполни сборку и публикацию по ним.

Можно дополнительно указать версию, ветку/commit и состав профилей. Просьба
только о сборке не включает публикацию. Для уже явно запрошенной публикации
не требуется повторное подтверждение перед каждым шагом.

## 1. Исходники и состав

Прочитать AGENTS.md, [[00 - Главная]] и BUILD.md. Проверить `git status --short --branch`,
`git log -5 --oneline`, `git remote -v` и Version в `TestBuilder/TestBuilder.csproj`.
Использовать выбранную пользователем ревизию. «Текущая» означает фактический
checkout, а не автоматически master. Не делать reset/stash и не перезаписывать
пользовательские изменения ради упаковки. При параллельных изменениях нужна
стабильная отдельная копия выбранного состояния.

Если рабочая копия изменена, определить состав заказанной сборки. Не коммитить
посторонние правки ради чистого статуса; `sourceDirty` должен быть честным.
Без запроса нового номера брать версию из csproj. Каждый результат размещать
в новом каталоге, даже если версия та же.

Обычный комплект включает `PSW+UPS-Box 8x2Pro · Параллельная проверка с SFP · 10.11.json`,
`PSW-2G6F+ · Полная проверка · 10.11.json`, `RTL-SW · Проверка платы · 10.11.json`
и `RTL-POE · Проверка платы · 10.11.json`.
Другой явный выбор пользователя имеет приоритет. Упаковка не должна менять
SFP, скорости, координаты или схемы. При необходимой правке профиля действуют
правила ProfileLayout. Наличие SFP в шаблоне не подтверждает подключение стенда.

## 2. Windows-комплект

На машине сборки нужны .NET SDK и Python. Выполнить
`python3 scripts/test_package_windows_release.py`.
Для браузера выбрать прежний **полный** комплект с манифестом и Browser;
упаковщик проверяет закреплённую версию, состав и SHA-256. Произвольная папка
Chrome не подходит. Альтернатива — `--browser-zip` с архивом и хешем из
`packaging/windows/browser.json`.

Пример bash/zsh из корня проекта; наличие `release_browser` проверить:

```sh
release_browser='artifacts/windows-20261019/TFortisTestBuilder-2026.10.19.16-win-x64'
release_stamp="$(TZ=Asia/Yekaterinburg date +%Y%m%d-%H%M%S)"
release_output="artifacts/windows-release-${release_stamp}"
python3 scripts/package_windows_release.py \
  --browser-bundle "$release_browser" \
  --output "$release_output"
```

Без `--version` версия берётся из csproj; отдельный заказанный номер передаётся
этим параметром. stdout/stderr сохранить в журнал. Для долгой команды дождаться
завершения через возвращённый session ID, а не считать отсутствие строк успехом.

Упаковщик обязательно запускает ProfileUiIntegrityTests, RussianInterfaceTests
и DataTestModeTests до publish. Не обходить отказ ручным publish/пропуском тестов.
Число тестов может измениться — записывать фактическое.

Результат — каталог, ZIP и `.zip.sha256`. Сверить версию, commit, sourceDirty,
время, профили, `profileUiIntegrityChecks.passed`, состав и хеши. В комплекте
нужны EXE, .NET, Chrome, WinSCP, `profiles/standard` и `reference`.
Рабочие JSON в корне `profiles`, `testbuilder.settings`, личные логи и
сессии создаются на рабочих местах.
При запросе только ZIP дать архив и результаты. Publish на Mac не подтверждает
запуск на Windows. Следующие шаги относятся к запрошенной публикации.

## 3. Вышенская и сеть

Найти online-устройство `vyshenskaya` через Remote Desktop Commander. Если оно
offline, продолжить локальную подготовку; оператору нужно включить компьютер
и Desktop Commander. Проверить DNS `test.ft.local`, TCP 445, UNC-папку,
её `release-manifest.json` и `version.txt`.

При таймауте и активном AmneziaVPN попросить оператора отключить VPN и повторить
проверку: 9 ноября это восстановило доступ. Не менять маршруты вслепую.
Таймаут соединения не является отказом пароля. Использовать доступное SMB-
подключение; учётные данные запрашивать только при фактической необходимости.
Пароли не хранить в документации, скриптах репозитория и журнале публикации.

Если инструмент вернул PID, читать результат этого процесса. Если вернул
незавершённый `call_id`, использовать `get_tool_result`. Не повторять команду
копирования/записи, пока исходный вызов ещё выполняется.

## 4. Перенос на Windows

Обычный способ — передать ZIP разрешённым каналом, сверить SHA-256 и распаковать
в **новую** папку. Из-за внешней папки ZIP источником служит внутренний каталог,
где непосредственно находится `TestBuilder.exe`.

### Если большого ZIP на Windows нет

При наличии прежнего полного комплекта можно передать разницу через Remote
Desktop Commander. Открытый HTTP-сервер для раздачи не требуется.

1. Найти прежний локальный манифест и соответствующий полный каталог на Windows.
2. По новому манифесту выбрать отсутствующие/изменившиеся по SHA-256 файлы.
   Создать ZIP этих файлов плюс нового `release-manifest.json`; сохранить его
   размер и SHA-256.
3. Читать ZIP блоками, например по 65536 байт, каждый кодировать base64 отдельно.
   Через remote `write_file` записывать отдельные `part000.b64`, `part001.b64`…
   Число частей вычислять из размера. Проверять длину/отсутствие усечения при
   чтении. Не выводить base64 в чат; данные можно передавать между инструментами
   внутри `functions.exec`. После сбоя проверять уже записанную часть.
4. На Windows декодировать **каждую часть отдельно** и последовательно записать
   байты в ZIP. Склеивать base64-строки с padding нельзя. Проверить полный
   размер и SHA-256 ZIP до распаковки.
5. Проверить пути ZIP/манифеста: только относительные файлы внутри назначения,
   без `..`, абсолютных путей и выхода через ссылки. Распаковать разницу отдельно.
6. Создать новый пустой каталог полного комплекта. Для каждого файла нового
   манифеста взять переданную версию либо неизменившийся файл прежней копии.
   Сверить исходный хеш, скопировать, сверить хеш назначения. Не копировать
   целиком старые настройки, рабочие профили и прочие лишние файлы.
7. Скопировать новый манифест и сверить отдельно: он не входит в собственный
   список `files`. Проверить весь новый комплект, а не только переданную разницу.

При формировании shell-команд правильно экранировать значения; JSON.stringify
не является shell quoting. Финальный ZIP на Mac и его манифест не изменять.

Запустить Check-Installation из полного каталога. Скрипт не включает оборудование
и не печатает. Коды: 0 — без замечаний, 1 — ошибка, 2 — замечания рабочего места.
Для кода 2 прочитать конкретные предупреждения. При ошибках комплекта не
публиковать. `installation-check.txt` не входит в релизный манифест.

## 5. Резервная копия

Создать новую папку на рабочем столе, например
`TFortis_Server_Backup_before_<версия>_<дата-время>`, проверить свободное место.
Скопировать **всю** серверную папку, включая version.txt, манифест, профили,
настройки и файлы вне манифеста. Сверить SHA-256 каждого источника и копии;
рядом сохранить отдельный inventory путей и хешей. Старую копию не перезаписывать.
При любом отказе или несовпадении остановить публикацию.

В Windows PowerShell 5.1 читать JSON-массив присваиванием
`$inventory = Get-Content ... -Raw -Encoding UTF8 | ConvertFrom-Json`.
Обёртка `@(Get-Content ... | ConvertFrom-Json)` может дать массив из одного
элемента, внутри которого находится весь inventory. Перед сравнением количества
проверить структуру результата; такое расхождение само по себе не доказывает
изменение файлов сервера.

Создание соседней staging-папки в Launcher_Beta может быть запрещено при наличии
записи внутри TFortis_Stand_Builder. Тогда использовать проверенный локальный
комплект и обновление существующей папки; не расширять права на весь ресурс.

## 6. Загрузка на сервер

Обновлять согласованную beta-папку. Dev АПК03 и другие программы лаунчера сюда
не входят. Перед заменой исключить запуск программы в период копирования;
не завершать чужой активный тест. Порядок действий:

1. Повторно сравнить состав, хеши и маркер сервера с inventory копии. Если
   появились изменения, остановиться до записи и выяснить их источник.
2. Прочитать текущий version.txt как целое `N`, подготовить `N+1`, но пока
   не записывать. Если формат изменился, выяснить действующий контракт.
   Не использовать фиксированное число из исторической заметки.
3. Копировать файлы по новому манифесту непосредственно в серверную папку.
   Совпадающие по SHA-256 можно пропустить. Проверять каждый записанный файл.
4. Удалять устаревшие файлы только если они входили в прежний манифест,
   отсутствуют в новом, совпадают с прежними хешами и есть в проверенной копии.
   Изменённые/неизвестные файлы сохранять. version.txt обрабатывается отдельно.
5. Повторно проверить полный набор нового манифеста на сервере.
6. Записать release-manifest.json и отдельно сверить его хеш.
7. **Последним** записать `N+1` в version.txt и прочитать обратно. Сохранить
   результат: версия, commit, число файлов, маркеры, копия, время, удалённые
   и сохранённые изменённые файлы.

Это обновление существующей папки, не атомарная замена всего каталога. При
сбое после частичной записи сервер может содержать смесь файлов: не повышать
маркер и не заявлять, что старая версия осталась нетронутой.

### Ошибка и откат

До активации восстановить изменённые файлы из проверенной копии, проверить
inventory и исходный маркер. Новые файлы удалять только если они созданы этой
попыткой и сохранили ожидаемые хеши; чужие изменения не затрагивать. Если
восстановление нельзя подтвердить, сообщить точное состояние и путь копии.

После активации откат — отдельная публикация прежнего проверенного комплекта
с новым маркером. Простое уменьшение номера не доказывает получение файлов
клиентами. Откат выполнять по запросу либо как необходимое восстановление
неудавшейся текущей публикации, а не из-за любого предупреждения рабочего места.

## 7. Профили, клиент и результат

Релиз поставляет `profiles/standard`, `reference` и `testbuilder.defaults.json`.
Приложение копирует отсутствующие стандартные профили в корень `profiles`,
даже если стандартный путь сохранён явно. Существующий одноимённый JSON
сохраняется. Чтобы доставить изменённый стандартный профиль рядом со старым,
обновить название профиля и использовать его как имя JSON. Для отдельно
настроенной папки доступен импорт. Подробности в [[06 - JSON профили]].

Пользователь перезапускает beta-лаунчер, выбирает программу и сверяет фактическую
версию. Если клиентский запуск входит в задачу и доступен, проверить его без
начала аппаратного теста. Аргументы лаунчера: `session user HelpTypeInLauncher`;
сетевой пароль вместо сессии не подходит.

Разделять подтверждения: сборка, тесты, Windows-комплект, сервер, скачивание
клиентом и аппаратный прогон. Одно не доказывает другое. Питание, прошивка,
печать и производственный отчёт не нужны для проверки установки.

Сохранить версию/ветку/commit, sourceDirty, профили, ZIP и SHA-256, реальные
тесты, резервную копию, путь сервера, маркеры, результат Windows и оставшийся
шаг. Обновить [[13 - Карта актуальности]], [[17 - Журнал проверок]] и ссылку
из [[00 - Главная]]. Пароли и действующие сессии не включать.
В финальном ответе дать результат, путь/архив, проверку, копию и следующий шаг.
