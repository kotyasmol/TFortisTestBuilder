# Справочник нод

Эта страница описывает все ноды, существующие в проекте на 2026-06-30: 28 видимых нод палитры, 2 технические ноды вложенного графа `For Slaves` и их runtime-шаги.

## Как читать справочник

Для каждой ноды указаны:

- `UI title` - заголовок в приложении.
- `JSON type` - значение поля `type` при сохранении.
- `ViewModel` - визуальная модель ноды.
- `Step` - runtime-логика, которую создает `GraphCompiler`.
- `Входы/выходы` - коннекторы и переходы.
- `Параметры` - редактируемые поля и дефолты.
- `Результат` - какие `StepResult` возвращает шаг.
- `Контекст` - какие переменные пишет или читает `TestContext`.
- `Особенности` - важные ограничения.

## Общие правила переходов

| Результат шага | Что делает `TestExecutor` |
|---|---|
| `Next` | Берет `TestNode.Next`. |
| `True` | Берет `TestNode.OnTrue`. |
| `False` | Берет `TestNode.OnFalse`; если его нет, граф завершается как `Failed`. |
| `Stop` | Завершает текущий граф как `Completed`. |

Большинство условных нод имеют `True` и `False`. Линейные ноды имеют один выход и возвращают `Next`.

|---|---|

| JSON type | `Subtest` |
| ViewModel | `SubtestNodeViewModel` |
| Step | `SubtestStep` |
| Палитра | `Структура` |

**Коннекторы:** вход `In`, выходы `Success`, `Error`.

**Параметры:**

| Параметр | Дефолт | Назначение |
|---|---|---|
| `Name` | `Подтест` | Название ноды и вложенного графа. |
| `Description` | пусто | Описание подтеста. |
| `IsEnabled` | `true` | Если `false`, тело не выполняется. |
| `StopOnError` | `true` | Если тело провалилось, бросать исключение вместо обычного `False`. |
| `RunOnFailure` | `false` | Запускать тело как аварийный cleanup после провала, остановки или исключения основного графа. |

**Вложенный граф:** `BodyGraph` с обычными `Start` и `End`. `BodyGraph.UsesBodyBoundaryNodes = false`.

**Поведение:**

- выключенный подтест возвращает `True`;
- успешное тело возвращает `True`;
- failed тело при `StopOnError = false` возвращает `False`;
- failed тело при `StopOnError = true` бросает `InvalidOperationException`.

**Контекст:** использует тот же `TestContext`, что и родительский граф. Переменные и `RegisterState` общие.

**UI-прогресс:** во время выполнения `SubtestNodeViewModel` показывает прогресс вида `N/M: Title`.

**Cleanup:** `RunOnFailure` не запускает подтест сам по себе во время обычного прохода
графа. После неуспешного завершения основного запуска `RunGraphAsync` отдельно
выполняет все включенные `Subtest` с этим флагом и дает им общий timeout 60 секунд.

## Цикл For

| Поле | Значение |
|---|---|
| UI title | `Цикл For` |
| JSON type | `For Slaves` |
| ViewModel | `ForEachSlaveNodeViewModel` |
| Step | `ForEachSlaveStep` |
| Палитра | `Структура` |

**Коннекторы:** вход `In`, выходы `True`, `False`.

**Параметры:**

| Параметр | Дефолт | Назначение |
|---|---|---|
| `FromSlaveId` | `1` | Первый slave ID. |
| `ToSlaveId` | `20` | Последний slave ID. |
| `Step` | `1` | Шаг инкремента. Если `0`, runtime заменяет на `1`. |
| `StopOnError` | `true` | Остановить цикл при провале вложенного графа. |

**Вложенный граф:** `BodyGraph` с `Body Start` и `Body End`. `UsesBodyBoundaryNodes = true`.

**Поведение:**

1. Проверяет, что `FromSlaveId <= ToSlaveId`.
2. Для каждого slave задает `context.CurrentSlaveId`.
3. Пишет переменную `slaveId`.
4. Запускает вложенный граф.
5. При ошибке и `StopOnError = true` возвращает `False`.
6. При завершении всех итераций возвращает `Next`.

**Переходы:** `GraphCompiler` мапит успешный выход `True` не в `OnTrue`, а в `Next`. Ошибочный `False` идет в `OnFalse`.

**Особенности:** нода предназначена именно для диапазона Modbus slave ID. Для произвольного списка или цикла по условию нужна отдельная нода.

## Selftest Check

| Поле | Значение |
|---|---|
| UI title | `Selftest Check` |
| JSON type | `Selftest Check` |
| ViewModel | `SelfTestCheckNodeViewModel` |
| Step | `SelfTestCheckStep` |
| Палитра | `Проверки` |

**Коннекторы:** вход `In`, выходы `True`, `False`.

**Параметры:**

| Параметр | Дефолт |
|---|---|
| `Url` | `http://192.168.0.1/cgi-bin/luci/admin/statistics/deviceinfo?luci_username=admin&luci_password=admin` |
| `TimeoutMs` | `300000` |
| `PollIntervalMs` | `5000` |
| `OutputPrefix` | `Dut` |
| `ValidationRules` | `init_ok=1..1`, `dev_type=0..65535`, `firmvare_vers=0..65535`, `boot_vers=0..65535` |
| `FailOnError` | `true` |

**Поведение:**

1. До истечения `TimeoutMs` повторяет браузерные попытки только по исходному `Url`.
2. Каждая попытка запускает один headless Chrome/Edge с URL, включая query-параметры
   `luci_username` и `luci_password`.
3. Ждет `document.readyState == complete`, аналогично возврату из Selenium `GoToUrl`.
4. После загрузки всегда ждет еще 10 секунд, как legacy-утилита с
   `Thread.Sleep(waitSeconds * 1000)`.
5. Один раз читает `document.documentElement.outerHTML`, аналог `driver.PageSource`,
   после чего закрывает браузер этой попытки.
6. Из снимка DOM извлекает `<selftest>...</selftest>` или совместимый
   `<settings>...</settings>` и проверяет наличие `default_mac`.
7. Если XML еще нет, ждет `PollIntervalMs` и запускает следующую такую же попытку.
8. При успехе сохраняет raw XML в `SelfTestRaw` внутри `TestContext` и парсит XML.
9. Все leaf-поля пишет в `context.Variables` с префиксом `OutputPrefix` и добавляет
   legacy-алиасы для `link_N`, `poe_*`, `sfp_*`.
10. Проверяет `ValidationRules` и логирует каждое правило отдельной строкой: факт,
   ожидаемый диапазон, `OK` или причина провала.
11. Возвращает `True` при успехе, `False` при окончательном timeout или ошибке.

**Контекст:**

- `SelfTest.Url`
- `SelfTest.StatusCode`
- `SelfTest.ElapsedMs`
- `SelfTest.Attempts`
- `SelfTest.PollIntervalMs`
- `SelfTestRaw`
- `SelfTest.ParsedFieldCount`
- `SelfTest.CheckedRuleCount`
- `SelfTest.FailedRuleCount`
- `SelfTest.ValidationSummary`
- `SelfTest.Ok`
- `SelfTest.Error`
- `${OutputPrefix}.${field}`

**Особенности:** при `FailOnError = true` ошибка ставит `context.HasCriticalError = true`.
Одна попытка повторяет legacy-утилиту, но нода запускает такие попытки до готовности DUT.
Обычный HTTP fallback и запрос `/test.shtml` не используются: все попытки идут одним
и тем же способом по исходному URL.
Для стандартных DUT URL старые значения `TimeoutMs` до `240000` автоматически
расширяются до `300000`, чтобы четырехминутный старт коммутатора не завершал ноду раньше времени.
Это поведение подтверждено на реальном стенде и считается обязательным инвариантом;
история проблемы и диагностический чек-лист находятся в [[18 - Selftest и загрузка DUT]].
Полный словарь полей страницы, включая семейства `link_*`, `poe_*`, `sfp_*`,
поля питания и служебные переменные ноды, находится в [[19 - Поля тестовой страницы DUT]].
Извлечение понимает HTML-, URL- и JS-экранированный XML, чтобы читать данные,
которые видны в DOM/DevTools, но не отображаются в интерфейсе LuCI.
Если в XML есть дублирующиеся leaf-поля, значение верхнего уровня `<selftest>`/`<settings>`
имеет приоритет над одноименным полем из вложенного блока.
Файл `selftest.txt` больше не создается: это был legacy-артефакт старой консольной
утилиты, а актуальное приложение хранит selftest только в контексте выполнения.

**Важно:** `FailOnError` не меняет `StepResult`. При любой ошибке selftest-нода возвращает `False`; флаг нужен для итогового `test_result` в `Build Test Report`.

## Run Data Test

| Поле | Значение |
|---|---|
| UI title | `Run Data Test` |
| JSON type | `Run Data Test` |
| ViewModel | `RunDataTestNodeViewModel` |
| Step | `RunDataTestStep` |
| Палитра | `HTTP и сеть` |

**Коннекторы:** вход `In`, выходы `True`, `False`.

**Параметры:**

| Параметр | Дефолт |
|---|---|
| `Mode` | `SoftwarePcap` |
| `ExpectedPackets` | `10000` |
| `PacketSizeBytes` | `1514` |
| `UdpPort` | `43962` |
| `MaxPortTestTimeMs` | `15000` |
| `TargetBandwidthMbps` | `100` |
| `DurationMs` | `5000` |
| `WarmupMs` | `500` |
| `InterPairDelayMs` | `5000` |
| `AllowedLossPercent` | `1.0` |
| `AllowedTxDeficitPercent` | `2.0` |
| `Bidirectional` | `true` |
| `PortsText` | пять пар `192.168.0.2–192.168.0.11` |
| `OutputVariableName` | `DataTest` |
| `FailOnError` | `true` |

**PortsText:** одна строка на пару портов:

```text
Name,InIp,OutIp
Name,InIp,OutIp,TargetBandwidthMbps
```

**Поведение:**

- поддерживает режимы `SoftwarePcap`, `Pcap`, `Software`, `TYPE_SOFT_GEN`;
- получает список pcap-устройств через SharpPcap;
- ищет сетевые адаптеры по `InIp` и `OutIp`;
- строит Ethernet/IP/UDP packet заданного размера;
- маркирует пакеты случайным ID запуска и последовательным номером, поэтому
  фоновые/запоздавшие/дублированные пакеты не искажают RX;
- делает warmup и очищает хвост захвата до измерения;
- проверяет пары строго последовательно, по одной;
- по умолчанию проверяет каждую пару в обоих направлениях;
- выполняет pcap-отправку в рабочем потоке, не блокируя UI;
- на Windows/Npcap использует синхронизированную kernel send queue частями по
  500 мс; при отсутствии native send queue использует paced `SendPacket` fallback;
- выдерживает `InterPairDelayMs` перед следующей парой;
- считает только уникальные пакеты текущего запуска через точный BPF по MAC,
  IP и UDP port;
- учитывает физический overhead Ethernet: preamble/SFD, FCS и inter-packet gap;
- отдельно проверяет `loss` по `AllowedLossPercent` и способность генератора
  выдержать target по `AllowedTxDeficitPercent`;
- считывает drops Npcap: при drop результат считается инфраструктурно
  недостоверным и один раз повторяется; реальная потеря DUT автоматически не
  маскируется повтором;
- `MaxPortTestTimeMs` ограничивает длительность направления.

`TargetBandwidthMbps` и override в `PortsText` нормализуются в диапазон
`1..100`. Старые профили со значением `1000` при загрузке мигрируют на `100`.
`ExpectedPackets = 10000` оставлен как legacy JSON-поле; фактический `expected`
для каждого направления вычисляется из target, duration и размера кадра на линии.

**Контекст:**

- `${OutputVariableName}.Mode`
- `${OutputVariableName}.ExpectedPackets`
- `${OutputVariableName}.PacketSizeBytes`
- `${OutputVariableName}.UdpPort`
- `${OutputVariableName}.TargetBandwidthMbps`
- `${OutputVariableName}.DurationMs`
- `${OutputVariableName}.WarmupMs`
- `${OutputVariableName}.InterPairDelayMs`
- `${OutputVariableName}.AllowedLossPercent`
- `${OutputVariableName}.AllowedTxDeficitPercent`
- `${OutputVariableName}.Bidirectional`
- `${OutputVariableName}.Passed`
- `${OutputVariableName}.Error`
- `${OutputVariableName}.PortN.*`

Для каждой пары сохраняются агрегированные worst-case поля и детальные
`${OutputVariableName}.PortN.Forward.*` / `.Reverse.*`: `ActualTxMbps`,
`ActualRxMbps`, `LossPercent`, `TxDeficitPercent`, link speed, capture drops,
duplicates, send engine, число попыток и текст ошибки.

**Особенности:** требует Npcap/WinPcap и доступ к адаптерам.
Рабочий стенд использует постоянную ручную конфигурацию `/24`: порт `0` —
`192.168.0.2`, …, порт `9` — `192.168.0.11`. Приложение эти адреса не меняет.

| `IntervalMs` | `5000` |

**PollAction:**

| Значение | Endpoint | Тип ответа |
|---|---|---|
| `HttpReachable` | поле `Endpoint`; допускается полный URL | не разбирает body, сохраняет `true` при HTTP 2xx |
| `SelftestSnapshot` | путь тестовой страницы или полный URL | повторный selftest-снимок; `ResponseType` не используется |
| `HttpGet` | поле `Endpoint`; допускается полный URL | поле `ResponseType` |
| `None` | нет запроса | только проверка уже существующей переменной |
| `GetUpsStatus` | `/api/getUpsStatus` | int; legacy JSON |

сначала удаляет старую `VariableName`. `HttpReachable` не интерпретирует body:
любой HTTP 2xx сохраняет Boolean `true`, сетевой сбой и не-2xx повторяются.
`HttpGet` читает одно типизированное значение, а `SelftestSnapshot` заново
загружает и парсит все поля DUT. После poll целевая переменная сравнивается с
`ExpectedValue`. При несовпадении нода ждёт `IntervalMs` и повторяет до

регистрозависимый fallback отдельной ноды.

**Контекст:** `WaitVariable.*` и `LastCheck.*`; HTTP poll пишет URL, status,
elapsed, raw response, output variable, response type, success и error.

**Особенности:** поддерживает только `Number`, `String`, `Boolean`; другие типы сравнения fallback-ятся к строковому сравнению.
