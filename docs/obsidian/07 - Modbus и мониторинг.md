# Modbus и мониторинг

## Текущий порядок подключения — 2026-10-27, уточнение

1. «Подключиться» занимает первый доступный COM-порт, который удалось открыть.
   Чтения Modbus и поиск оборудования при этом не выполняются.
2. Открытие профиля останавливает предыдущий монитор, применяет параметры RTU
   к уже открытому порту без его освобождения и проверяет hardware профиля:
   идентификацию всех устройств и первое чтение карты регистров.
3. Только после успешной проверки выполняются ноды «При открытии профиля».
4. Основной тест запускается вручную после успешной подготовки. Кнопка запуска
   не повторяет неудавшуюся подготовку; для повтора профиль открывают заново.

Несовпадение оборудования сохраняет открытый порт, но блокирует подготовку и тест.
Другие COM-порты при выборе профиля не перебираются. Профиль с Modbus-операциями
без hardware нужно дополнить в редакторе оборудования. Автономные профили
по-прежнему не требуют Modbus. При подключении с уже открытым профилем его
проверка и подготовка выполняются сразу после открытия порта.

«Настройки → Параметры открытия COM-порта…» задаёт только параметры линии
для первоначального открытия. Ранее описанные ниже сканирование при подключении,
закрытие порта при смене профиля и повтор подготовки кнопкой запуска отменены.


## Настраиваемый поиск — 2026-10-27

«Настройки → Настроить поиск стенда…» задаёт RTU, список slave 1–247,
паузу и выбранные записи каталога. Поиск использует IdentificationAddress
и допустимые значения каждой записи, затем читает её карту регистров.
Нет обязательного slave 1, регистра 0 или switch по встроенным типам.
Чётные адреса и пользовательское оборудование поддерживаются.
Неоднозначный тип или отсутствующая выбранная запись дают ошибку.
При наличии hardware используются параметры профиля.


## 2026-10-27 — подключение до выбора профиля

По последнему уточнению пользователя порядок возвращён: «Подключиться» →
автопоиск COM-порта и известных устройств → выбор профиля. До выбора профиля
используются редактируемые настройки Discovery и выбранные записи каталога.
Наличие COM-порта само по себе не считается обнаружением стенда.

После выбора профиля подключённый порт автоматически переоткрывается с его
параметрами RTU; проверяется весь состав `hardware`, затем запускаются мониторинг
и подготовка профиля. Другой порт при этой проверке не подбирается. При ошибке
профиль остаётся открытым, соединение сбрасывается, журнал показывает причину.
Выбор профиля до подключения также допустим; тогда поиск использует его карту.
Старые профили без `hardware` могут подключаться через сканирование известных типов.
Каталог оборудования и сохранённые в профиле ожидания остаются без изменений.
Номер COM в профиле не нужен.


## Отменённый порядок от 2026-10-27 — сначала профиль

Основное подключение доступно только после загрузки профиля с `hardware`.
Программа перебирает доступные COM-порты и проверяет все `Devices`: slave ID,
Holding-регистр `IdentificationAddress` и `IdentificationValue` (если задан),
затем полный первый опрос `Registers`. Частичный состав, неправильный тип или
неполный ответ не считаются успешным подключением. В журнале есть адрес slave,
имя, регистр, ожидаемое и полученное значения. Профили без идентификатора
проверяются по доступности всей заданной карты данных.

Номер COM стенда не выбирается и не требуется в профиле. Старые `hardware.PortName`
и `AppSettings.StandPort` не ограничивают поиск основного подключения; поле JSON
сохранено для совместимости. Явные порты консолей исключаются из поиска.
При выборе другого профиля прежний монитор останавливается и порт закрывается.
Автоматического подключения при смене профиля нет: оператор нажимает «Подключить».
После успешной проверки запускаются мониторинг и подготовка при открытии профиля.

Редактор «Оборудование» задаёт параметры RTU, устройства, ожидаемый тип и карты
регистров. Старый профиль без `hardware` открывается для редактирования, но для
подключения нужно заполнить оборудование и сохранить профиль. Автономные профили
без Modbus по-прежнему можно выполнять без подключения.

В поставляемых Pro-профилях задано 11 устройств: EL-60v5 (тип 4) на нечётных
slave 1–15, SIMBAT-24/48 (тип 9 или 10) на 17, IO-2 (тип 5) на 21, PS-3 (тип 8) на 23.
По уточнению пользователя на slave 17 допустимы оба SIMBAT: 24 и 48.
PSW-2G6F+ ожидает шесть EL-60v5 на 1–11, IO-2 на 21 и PS-3 на 23.
Все типы читаются из Holding 0. Карты скопированы из встроенных шаблонов в JSON,
поэтому профиль содержит полный контракт и может редактироваться отдельно.
Существующие RTL-профили уже содержат типы 104/105 и карты данных.

## COM-порт виден при выключенном стенде — 2026-10-19

Подтверждено пользователем на RTL-SW: при выключенной кнопке «ВКЛ» COM-порт
остаётся в списке ОС, но контроллер стенда не отвечает. Программа перебирает
порты и сообщает «стенд не найден». Наличие COM-порта подтверждает видимость
USB-адаптера, но не питание и доступность контроллера. Первое действие:
включить стенд кнопкой «ВКЛ», затем повторить «Подключить».
Сообщённый случай «сначала профиль, затем подключение» объяснялся выключенным
питанием; программный дефект подключения в этом случае не подтверждён.

## Подключение DUT после питания — 2026-10-19

`SerialConsoleSession.ConnectAsync` ждёт USB-UART по настройкам профиля,
исключает порт Modbus, повторяет поиск/открытие раз в секунду при отсутствии
или временной недоступности. Несколько совпадений дают ошибку без выбора
случайного порта. Операция не пишет ни команд, ни перевода строки; следующий
обмен использует открытый порт. Таймаут и отмена освобождают блокировку.
Сессия закрывается при завершении прогона. В RTL-SW время ожидания порта
120000 мс — редактируемое значение профиля, добавленное в TestBuilder,
а не константа исходной программы.


## Обновление 2026-10-14: конфигурируемые RTU-устройства

Режим без `hardware` использует сканирование известных типов и скорость 9600 8N1.
С 2026-10-19 он также распознаёт RTL-SW/PoE по встроенным картам (типы 104/105).
При наличии `hardware` используются его параметры и только перечисленные slave;
`SlaveManager.ConfigureAsync` проверяет необязательную идентификацию и начальный опрос,
затем атомарно публикует ConfiguredSlaveModel. Типа устройства в C# добавлять не нужно.
COM стенда берётся из локальных настроек; пустое поле оставляет перебор портов.

2026-10-19: в поставляемых RTL-SW/PoE пауза после фонового чтения — 1000 мс,
как в `SwStandMonitorLoop`/`PoeStandMonitorLoop` RTL_v2, вместо прежних 500 мс.
SW читается одним блоком 2300..2385, PoE — 2400..2511. Ожидания К5/VCC
проверяют кэш; их интервалы не создают отдельные запросы на шину. Вкладка
Modbus при управляемом мониторинге не запускает второй цикл. Факт перегрузки
физической шины без аппаратной трассы не установлен.

`ReadAreaAsync`: Holding/Input/Coil/Discrete (FC3/4/1/2). `WriteAreaAsync`: Holding/Coil
(FC6/5, Coil только 0/1). Адреса — смещения протокола с нуля. Значения — uint16 или биты.
ConfiguredSlaveModel группирует соседние адреса внутри области для фонового обмена;
отдельной ноды группового чтения нет. Пропуски адресов не включаются в запрос.

RegisterState индексируется (slave, area, address), хранит время начала опроса.
После команды записи или консоли граф ждёт опроса, начатого после воздействия.
Неполный/ошибочный ответ удаляет значения slave. Для новых карт значение старше
max(10 с, 3 периода опроса) недостоверно. Wait Until учитывает свой таймаут и при
ожидании свежего значения. StopAsync отменяет и дожидается опроса до отключения порта.

Вкладка Modbus переиспользует действующий монитор и карту, не сканирует АПК-03 поверх
профиля платы. Ручные записи заблокированы во время прогона/подключения.
Готовый профиль можно выбрать при подключённом стенде: прежний монитор
останавливается и порт закрывается перед загрузкой, затем оператор подключается
к оборудованию выбранного профиля кнопкой «Подключить». Во время переключения и теста выбор заблокирован.
Редактирование карты и создание пустого профиля требуют отключения.

При остановке `ConfiguredSlaveModel` пропускает отменённое обновление,
которое уже попало в очередь UI. Проверка с выбрасыванием исключения отмены
выполняется после `await InvokeAsync`, в задаче опроса, и обрабатывается
`RegisterMonitor`. Внутри UI-callback исключение отмены не создаётся.
Это исключает остановку отладчика на штатной отмене внутри обновления таблицы
при выборе другого профиля; старые значения не публикуются.


Modbus-слой отвечает за связь с тестовым стендом, сканирование slave-устройств, чтение/запись Holding Registers и обновление `RegisterState`, который используют регистровые ноды.

## Подключение

`TestViewModel.ConnectAsync()`:

1. Ставит статус `Поиск COM-портов...`.
2. Требует загруженный профиль с оборудованием и перебирает доступные COM-порты,
   кроме явно заданных портов консолей. Номер COM из старого профиля игнорируется.
3. Для каждого кандидата вызывает:

```csharp
_modbusService.ConnectAsync(port, 9600, Parity.None, 8, StopBits.One)
```

При наличии `hardware` параметры линии берутся из его карты вместо значений выше.

4. Для старых профилей проверяет порт через `_modbusService.CheckPortAsync()`.
   Для профиля с `hardware` выполняет идентификацию заданного slave и первый
   опрос его регистров по карте профиля.
5. Если порт не открылся, тип slave не совпал, сканирование не нашло устройств
   или опрос завершился ошибкой, отключается и пробует следующий порт.
6. После успешного порта:
   - сохраняет `SelectedPort`;
   - ставит `IsConnected = true`;
   - запускает `StartMonitoringAsync()`;
   - синхронизирует `SlaveRegistry`;
   - пишет статус и лог.

## Проверка порта

При исключении в попытке подключения/сканирования `TestViewModel` сохраняет
полный стек только в диагностический файл, останавливает монитор,
отключает порт и сбрасывает `IsConnected`, `IsMonitoringActive` и состояние
`SlaveRegistry`, прежде чем пробовать следующий порт. Раньше исключение
терялось, а после ошибки сканирования UI мог оставаться «подключённым».
При автопоиске неудачный кандидат даёт нейтральное сообщение «стенд не обнаружен;
поиск продолжается». Красная итоговая ошибка появляется, только если ни один
порт не подошёл. При ручном выборе порта выводится короткое предупреждение.
Исключения выполнения графа и завершающих действий также не выводятся в UI
со стеком. Путь диагностического файла описан в [[10 - Настройки логирование тесты]].

`ModbusService.CheckPortAsync()` для старых профилей делает пробное чтение:

```csharp
ReadRegistersAsync(1, 0, 1)
```

Успех - если вернулся массив длиной `1`.

Для профилей RTL-SW/RTL-PoE карта оборудования задаёт идентификацию на slave 1,
Holding-регистр 0 и ожидаемые значения 104/105 соответственно. RTL_v2 выполняет
такой же поиск по доступным COM-портам, затем проверяет регистр серийного номера
стенда (SW: 2300, PoE: 2400). В TestBuilder первый опрос карты включает этот
регистр. Открытый COM-порт без найденных устройств больше не оставляет
`IsConnected=true`: раньше это также блокировало выбор профиля после неудачного
подключения. Подробности попыток открытия порта остаются в журнале.

## Сканирование slave

`SlaveManager.ScanAsync()` проходит slave ID:

```text
1, 3, 5, ..., 35
```

Для каждого читает регистр `0`. Значение регистра выбирает модель:

| Значение регистра 0 | Модель | DeviceType |
|---:|---|---|
| `1` | `El60Model` | `EL-60` |
| `2` | `PS1Model` | `PS-1` |
| `3` | `PS2Model` | `PS-2` |
| `4` | `El60v5Model` | `EL-60v5` |
| `5` | `IO2Model` | `IO-2` |
| `6` | `StandRpsModel` | `Stand Rps` |
| `7` | `StandPwr180Model` | `PWR-Tester` |
| `8` | `Ps3Model` | `PS-3` |
| `9` | `Simbat24Model` | `SIMBAT` |
| `10` | `Simbat48Model` | `SIMBAT` |
| `104` | `ConfiguredSlaveModel` | `RTL-SW` |
| `105` | `ConfiguredSlaveModel` | `RTL-POE` |

Для типов вне прежних моделей 1..10 сканер ищет совпадение в `HardwarePresets`
по `IdentificationAddress=0` и `IdentificationValue`. Это тот же ресурс
`Assets/hardware-presets.json`, который использует редактор оборудования.
Перед добавлением в список сканер проверяет полное чтение карты; неполный
ответ отклоняется. Типы без модели и без шаблона не попадают в список устройств.

Проверка исходного протокола RTL_v2: `SerialPortStandDiscoveryService.cs`,
`StandModbusAttachService.cs`, `SwRegisterMap.cs` и `docs/hardware/modbus.md`
в репозитории https://github.com/kotyasmol/RTL_v2 (проверено 2026-10-19).

## ModbusService

`ModbusService` хранит:

- `_serialPort`;
- `_master`;
- `_connectionSettings`;
- `_ioLock`;
- `_lastRequestTimeUtc`;
- `_watchers`;
- `IsConnected`;
- `LastError`.

### Последовательный доступ к шине

Все операции чтения/записи проходят через `_ioLock`. Это важно, потому что один COM-порт не должен получать параллельные запросы.

Между запросами выдерживается `_minRequestGap = 150 ms`.

### Чтение

```csharp
ReadRegistersAsync(byte slaveId, ushort address, ushort count)
```

Выполняет `ReadHoldingRegistersAsync`, затем вызывает `NotifyWatchers`.

### Запись

```csharp
WriteRegisterAsync(byte slaveId, ushort address, ushort value, bool verify = true)
```

Выполняет `WriteSingleRegisterAsync`. Если `verify = true`, ждет bus gap, читает регистр обратно и сравнивает значение.

Важно: `ModbusWriteStep` передает `verify: false`, потому что у него есть собственная логика read-back verification с тремя попытками.

## Auto reconnect

`ExecuteWithRecoveryAsync` ловит критические ошибки:

- `IOException`;
- `UnauthorizedAccessException`;
- `InvalidOperationException`;
- `ObjectDisposedException`.

При критической ошибке:

1. `IsConnected = false`.
2. Посылается `ReconnectStatusChanged`.
3. Текущее соединение освобождается.
4. До 60 секунд раз в 1 секунду проверяется наличие прежнего COM-порта.
5. При появлении порта соединение открывается заново.
6. Операция повторяется.
7. Если восстановиться не удалось, бросается `IOException`.

`TestViewModel.OnReconnectStatusChanged()` показывает `ModbusReconnectDialog`.

## RegisterMonitor

`RegisterMonitor` запускается после успешного сканирования.

Цикл:

1. Берет snapshot slave-устройств.
2. Последовательно вызывает `slave.PollAsync()`.
3. Для каждого `RegisterItem` обновляет `RegisterState`.
4. Ждет `PollInterval`, по умолчанию 1000 мс.

После 5 последовательных ошибок:

- пишет ошибку;
- вызывает `ConnectionLost`;
- останавливает мониторинг.

`TestViewModel.OnConnectionLost()` пишет предупреждение и говорит пользователю, что восстановление произойдет при следующей Modbus-операции.

При отключении через UI `DisconnectAsync()` останавливает мониторинг, закрывает Modbus-соединение, сбрасывает `IsConnected`/`IsMonitoringActive` и сообщает `SlaveRegistry`, что стенд больше недоступен.

## RegisterState

`RegisterState` - тонкая обертка над:

```csharp
ConcurrentDictionary<RegisterKey, int>
```

Ключ:

```csharp
public readonly record struct RegisterKey(byte SlaveId, int Address);
```

API:

| Метод | Назначение |
|---|---|
| `Update(byte slaveId, int address, int value)` | Обновить последнее значение. |
| `TryGet(byte slaveId, int address, out int value)` | Прочитать последнее значение. |

## Важное следствие для нод

Эти ноды по умолчанию работают по `RegisterState`; с `LiveRead=true`
они выполняют прямое Modbus-чтение:

- `Check Register Range`;
- `Wait Until`.

Для чтения через `RegisterState` должны выполняться условия:

- приложение подключено к стенду;
- slave найден сканером;
- `RegisterMonitor` успел опросить нужный регистр;
- адрес присутствует в `RegisterItems` модели или был обновлен другим шагом.

`Write Register` отличается: он пишет напрямую через `IModbusService`.

## SlaveRegistry

`SlaveRegistry` нужен для UI-ноды, чтобы при подключении показывать:

- список slave в ComboBox;
- список регистров выбранного slave.

С 2026-10-22 список регистров и подсказки в редакторе доступны и без связи:
используется карта оборудования профиля, а при её отсутствии — встроенный
справочник. Это отдельные метаданные, не виртуальные найденные slave и не
значения мониторинга. Вложенные ноды наследуют карту корневого графа.
Подробнее — [[08 - Модели устройств и регистры#Автономная справка в нодах]].

`NodeViewModel` подписан на `SlaveRegistry.PropertyChanged`. При изменении `IsConnected` вызывает `SyncSlaves()` и дает дочерним нодам восстановить выбранные `SelectedSlave`/`SelectedRegister`.

## Вкладка Modbus

`ModbusMonitoringViewModel` также умеет запускать свой polling loop для вкладки `Modbus`. Он каждую секунду вызывает `PollAsync()` у всех slave.

Это отдельный UI-механизм просмотра регистров. Основной runtime-граф при запуске использует `RegisterMonitor`, созданный в `TestViewModel`.

## Практические рекомендации

### Подключения профиля и DUT — 2026-10-19

`HardwareConfiguration.PortName` задаёт порт RTU. Карта содержит параметры
линии, период опроса, slave-адреса, идентификацию и регистры. Можно добавить
новое устройство через «Пустое устройство» без новой C#-модели. Поддерживается
одна линия RTU с несколькими slave и отдельные текстовые UART-консоли.

`ConsoleDevices` не входят в список Modbus-slave. Их порты открываются при
выполнении использующей их ноды, поэтому DUT не обязан отвечать при подключении
стенда. Скорость, чётность, биты, кодировка, окончание команды и DTR/RTS берутся
из JSON. При смене устройства/параметров `SerialConsoleSession` переоткрывает порт;
все обмены проходят последовательно. Старые внедряемые транспорты не могут
молча игнорировать нестандартные параметры: совместимый метод их отклоняет.

В RTL-SW консоль `dut` имеет 115200/8N1, UTF-8, LF; её порт выбирается
пользователем. Все команды DUT ссылаются на `dut`. Подача питания и повтор
SW_VERS остаются в графе. У RTL-PoE и шаблона цвета — только Modbus.

### Работа с регистрами

- Перед запуском графа дождаться статуса `Найдено устройств: N`.
- Для регистровых проверок сначала убедиться, что нужный slave виден на вкладке `Modbus`.
- Для сценариев внутри `For Slaves` включать `UseCurrentSlaveId`.
- Для свежего значения включать `LiveRead` у существующих register-check нод;
  `Check Register Range` также поддерживает `ReadAttempts` и `ReadIntervalMs`.
