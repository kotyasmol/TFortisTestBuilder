# Modbus и мониторинг

## Подключение

Текущий путь: `TestViewModel.ToggleConnectionAsync` → `ConnectAsync` →
`ModbusService.ConnectAsync`. Выбор порта и проверка оборудования — разные этапы.

1. `SerialPort.GetPortNames()` возвращает имена портов ОС.
2. Непустой `AppSettings.StandPort` оставляет только совпадающее имя (без учёта
   регистра и внешних пробелов). Если его нет или открыть его не удалось,
   переключения на другой порт нет.
3. При пустом `standPort` имена сортируются лексикографически без учёта регистра:
   например, COM1, COM10, COM2, COM3. Программа перебирает их до первого успешного
   `SerialPort.Open()` и создания Modbus master.
4. Параметры открытия берутся из `AppSettings.Discovery`: по умолчанию 9600/8N1.
   Они редактируются через «Настройки → Параметры открытия COM-порта…».
5. Успешное открытие сохраняет `SelectedPort`, устанавливает `IsConnected`
   и пишет «Открыт COM-порт …». Modbus-запросов на этом этапе нет.

Доступность означает, что ОС и драйвер разрешили открыть порт. Она не доказывает
наличие, питание или исправность стенда. COM3 — сохранённый выбор рабочего места
APK-03-07 на 2026-10-28, не значение по умолчанию приложения; в новом settings
поле пустое. Порт может существовать и открываться при выключенном контроллере.

Текущий вызов `GetStandPortCandidates(null, …)` не исключает порты консолей:
профиль ещё может быть не выбран. Если на ПК несколько интерфейсов, нужный
порт стенда следует задать в локальных настройках. Консольные правила описаны ниже.

## Проверка оборудования профиля

Открытие профиля при подключённом порту:

1. `SelectProfileAsync` останавливает и дожидается прежнего RegisterMonitor,
   очищает найденные устройства и кэш, загружает новый граф.
2. `ValidateConnectedProfileAsync` проверяет `hardware` и через ConfigureLineAsync
   меняет RTU-параметры уже открытого порта, не освобождая его.
3. `SlaveManager.ConfigureAsync` для каждого Devices проверяет идентификацию
   и выполняет первое полное чтение его карты. Только после успеха всей карты
   публикуется новый список ConfiguredSlaveModel.
4. `StartMonitoringAsync` включает фоновый монитор с PollIntervalMs профиля.
5. `PrepareOpenedProfileAsync` выполняет начальные ноды «При открытии профиля».
   Основная проверка изделия запускается отдельной ручной командой.

Если профиль выбрали до подключения, проверка и подготовка выполняются после
открытия порта. Если оборудование не подходит, другие порты не перебираются;
граф остаётся открытым, подготовка и запуск заблокированы. При ошибке проверки
соединение остаётся открытым, если сам транспорт сохранил работоспособность.
Причина с адресом slave и ожидаемыми/полученными данными записывается в журнал.
Повтор подготовки — через повторное открытие профиля или новое подключение.

Наличие Devices в hardware требует успешной проверки даже у графа без
Modbus-шагов. Граф с активными регистровыми нодами без hardware не запускается:
карту нужно заполнить в «Оборудование». Автономные графы без RTU-оборудования
и Modbus-операций работают без COM. Тело выключенного подтеста не создаёт
требование Modbus, но заданный состав hardware проверяется целиком.

## Идентификация и карты

DeviceDefinition содержит имя, SlaveId 1–247, IdentificationAddress,
необязательное одиночное IdentificationValue либо непустой IdentificationValues,
и 1–4096 регистров. Одновременно одиночное значение и список запрещены.
Идентификация читается из Holding; отсутствие обоих полей означает проверку
чтением всей заданной карты. Частичный ответ считается ошибкой.

RegisterDefinition: Address, Name, Area, Writable, Unit, Category.
Области Holding/Input/Coil/Discrete используют FC3/4/1/2; запись Holding/Coil —
FC6/5, Coil принимает 0/1. Адреса — протокольные смещения с нуля.
ConfiguredSlaveModel объединяет соседние адреса одной области в блоки,
не захватывая пропуски. Не нужна новая ветка C# для каждой модели.

Каталог: `EquipmentLibrary` объединяет `Assets/hardware-presets.json` и
пользовательские записи. Редактор копирует выбранные определения в профиль;
изменение каталога не меняет уже сохранённые карты. См. [[08 - Модели устройств и регистры]].

В Pro-профилях восемь EL-60v5 на нечётных slave 1–15, SIMBAT-24/48 на 17,
IO-2 на 21 и PS-3 на 23. PSW-2G6F+ использует шесть EL-60v5 на 1–11,
IO-2 на 21 и PS-3 на 23. RTL-SW/PoE — ожидаемые типы 104/105 на slave 1.
Это данные конкретных JSON, не обязательный состав для любого стенда.

## Отдельное сканирование

`SlaveManager.ScanAsync` сохранён для диагностического сканирования. Он не
вызывается кнопкой подключения основного редактора. `ModbusMonitoringViewModel`
использует его только когда нет управляемой профилем карты/монитора.

Сканер получает DiscoverySettings и EquipmentLibrary: настраиваемый список
адресов, задержку и выбранные TemplateIds. Значения по умолчанию — нечётные
1–35 и 150 мс. Null TemplateIds выбирает встроенный каталог, пустой список
запрещён. Для каждого адреса сканер группирует шаблоны по IdentificationAddress,
читает идентификатор и сверяет допустимые значения. Неоднозначное совпадение
даёт ошибку; подходящий тип должен пройти полный опрос карты. Результат —
ConfiguredSlaveModel. Старого switch по типам 1–10 в текущем ScanAsync нет.

`ModbusService.CheckPortAsync` делает чтение slave 1 / Holding 0 / один регистр,
но в текущем приложении вызывающих мест нет. Его наличие в интерфейсе не
означает, что каждый порт проверяется таким чтением.

## Последовательный доступ и восстановление

Общий ModbusService создаёт MainWindowViewModel. Основной граф, кнопки профиля,
монитор и ручные операции используют одну шину. `_ioLock` сериализует обмен,
минимальный промежуток между запросами — 150 мс. Последовательность нескольких
записей/ожиданий от этого не становится атомарной; ограничения параллельных
графов описаны в [[23 - Параллельное выполнение проверок]].

WriteRegisterAsync при verify читает результат обратно. ModbusWriteStep
отключает эту встроенную проверку и выполняет собственный read-back с повторами.
Критические IOException, UnauthorizedAccessException, InvalidOperationException,
ObjectDisposedException запускают восстановление того же порта: до минуты,
проверка появления раз в секунду, повтор прерванной операции после открытия.
Если восстановление не удалось, возвращается IOException. Другой COM не выбирается.

Потеря связи сбрасывает готовность профиля; во время теста инициирует остановку
и завершающие действия. Автоматическое восстановление транспорта не является
повторной подготовкой профиля. NeedsStandInspection после неудавшегося cleanup
снимает инженер после отключения и ручной проверки. См. [[04 - Графы и выполнение]].

## RegisterMonitor и RegisterState

Монитор после ConfigureAsync последовательно опрашивает snapshot устройств,
записывает значения в RegisterState и ждёт PollInterval (по умолчанию 1000 мс).
В текущих RTL-профилях SW читает 2300..2385, PoE — 2400..2511.
Каждый удачный опрос сбрасывает общий счётчик ошибок; пять ошибок подряд
вызывают ConnectionLost и остановку монитора. Ошибка опроса удаляет кэш slave.
StopAsync отменяет цикл и дожидается его выхода; позднее отменённое обновление
не публикуется в UI или кэш.

RegisterState хранит `ConcurrentDictionary<RegisterKey, Sample>`:
ключ — SlaveId, Address, Area; Sample содержит значение и время начала опроса
по Stopwatch. Update принимает необязательные area/startedAt, TryGet — area
и границу notBefore. Есть Invalidate(slave) и Clear().

Свежесть задаёт контекст выполнения: чтения после воздействия должны начаться
после записи/консольной команды; для карты профиля действует предел возраста
max(10 секунд, три периода опроса). Сам RegisterState не удаляет записи таймером.
Check Register Range и Wait Until по умолчанию используют кэш, LiveRead делает
прямой запрос. Для кэша адрес должен присутствовать в опрашиваемой карте или
быть обновлён шагом; ожидание свежести входит в timeout шага.

## Регистры в интерфейсе

«Регистры» показывает список устройств, таблицу, поиск по адресу/названию,
категории, фильтр записи и журнал. Двойной щелчок по RW-регистру открывает
WriteRegisterDialog. Ручные записи запрещены во время теста, подключения
и выполнения кнопок профиля. Управляемый монитор не дублируется вторым циклом;
для самостоятельного диагностического просмотра VM имеет отдельный polling loop.
Фон RO/RW и текст обновляются при смене темы.

SlaveRegistry передаёт UI найденные slave и состояние соединения. Для выбора
регистров в нодах без стенда используются отдельно метаданные hardware профиля
и локальный справочник. Они не имитируют найденные устройства или измерения.
Ноды вложенных графов получают карту корня.

## Консоль DUT

hardware.ConsoleDevices задаёт отдельные UART-устройства: Id, имя, порт или
правила поиска, RTU-параметры, кодировку, окончание команды, DTR/RTS. Они не входят
в Modbus Devices. Явный порт имеет приоритет; описание USB и пара VID/PID —
альтернативные фильтры. Несколько совпадений дают ошибку. Из поиска консоли
исключается фактически занятый порт Modbus.

SerialConsoleSession открывает порт при выполнении ноды, поэтому DUT может
появиться после подачи питания. ConnectOnly ждёт появления/открытия без записи
команды или чтения ответа; повтор поиска — раз в секунду до TimeoutMs или отмены.
Следующая нода использует ту же сессию. При смене параметров порт переоткрывается,
при завершении компилятора/прогона закрывается. До запуска проверяются настройки
и ссылки, а не физическое присутствие будущего USB-UART.

В RTL-SW консоль dut использует 115200/8N1, UTF-8, LF и поиск CH340;
ожидание 120000 мс хранится в ноде профиля. Legacy-ноды без DeviceId используют
собственные portName/baudRate и резерв AppSettings.ConsolePort.
