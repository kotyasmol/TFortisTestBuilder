## Типы этикеток и приоритет при печати — 2026-11-24

Основной редактор — «Этикетки → Типы этикеток» внутри главного окна.
Геометрия редактируется на копии; общий отступ сверху сдвигает все Y одинаково,
размеры в мм округляются к целым точкам текущего dpi. Высота и модуль относятся
к первому видимому штрихкоду. SN/Barcode используют прежний общий formatter.
LabelTypeStore.Resolve: явное Assignments модели → сохранённый универсальный
тип состава → прежняя привязка модели/ID/копия ноды. ForModel сохраняет
настоящий код/серию/вариант. LabelDataBindings может заменить отображаемые
имя/код/шкаф константой или переменной; SN/MAC — переменной проверки.
Серия, согласованность номеров и соответствие MAC проверяются как прежде.
Источники разрешаются перед чтением SN; пропущенная переменная даёт отказ,
задание принтеру не отправляется. История хранит уже разрешённые данные.
WorkstationTemplates применяет те же типы к ручной печати и пробным карточкам.
Ручная печать сохраняет разрешённый шаблон; история и UseLastTestLabel обходят
новый каталог и CopyUpgraded. Проба редактора использует его несохранённый
черновик и ровно одно задание; системные настройки принтера не меняются.
Ручная печать выбирает назначенный тип по изделию, позволяет выбрать свою
карточку и использует введённые SN/MAC; переменные проверки не читает.
Каталог читается перед новой печатью. Повреждённый файл блокирует её,
но не повтор точного сохранённого снимка. Перенос описан в label-types,
label-transfer и docs/catalog-to-prod.md.


## Настраиваемое содержимое этикетки — 2026-11-24

Общий `LabelDataFormat` используется сырой командой и визуальным макетом,
предпросмотром и печатью. `SerialTextFormat` и `BarcodeFormat` независимы;
`{{SerialText}}` подключает строку SN к правилу, `{{Barcode}}`/`{{ZplBarcode}}`
подключают штрихкод. Полный номер для получения/отчёта не изменяется.
В диагностике PrintLabel сохраняются `FullSerial`, `SerialShort`, фактические
`SerialText`, `Barcode` и массив `Barcodes` из разобранной команды.

Штатные ZPL: `SerialTextFormat={{ShortSerial}}`,
`BarcodeFormat={{DeviceCode:3}}{{ShortSerial}}`; `3200428` → `00428` /
`03200428`, `600428` → `00428` / `00600428`. ForModel подставляет реальный тип,
смещение, диапазон, комплектацию и шкаф, сохраняя пользовательские правила
и количество цифр. У узнаваемого штатного EPL при привязке к модели с LabelCode текст получает
`SerialTail:5`, штрихкод — `DeviceCode:3` + `SerialTail:5`: RTL-SW `31300428`
даёт текст `00428` и код `31300428`. Общий EPL без модели сохраняет полный
номер. Явные правила имеют приоритет; неприменимый ShortSerial в шаблоне
без разбора серии отклоняется вместо печати нуля.

В Code 128 ведущий ноль допустим. Новый код из 8 цифр использует подмножество
C без переключения на B: 158 точек при модуле 2, 198 с двумя тихими полями
по 20 точек. Штатная позиция X=562, Y=117, высота 34. Геометрия других полей
сохранена. Проверка цифрового изображения независимым ZXing не подтверждает
качество бумаги, настройки/ограничения производственного сканера или принтера.

LabelDataSettingsView сохраняет копию модели только при явном изменении
поля; отложенные события TextChanged/SelectionChanged при открытии не
перезаписывают null/неявную разрядность. Обычные SN/штрихкоды подключаются
к новым правилам при изменении, собственные формулы элементов остаются.
Перед обрезанием видимого номера RTL сверяется тип платы в полном SN;
ручная печать EPL модели с SerialSeries также проверяет её диапазон.
Повтор ручной печати и последнего теста копирует сохранённый шаблон без
CopyUpgraded: старый отпечаток остаётся воспроизводимым после смены поставки.

## Встроенное добавление пар в план — 2026-11-23

NetworkPortBatchEditor — общая форма добавления портов/пар. В режиме пар
количество умножается на два и передаётся NetworkPortBatch.AppendTo; пары
включены всегда, скорость одинаковая в обеих строках. Максимум 512 пар за
вызов следует из MaximumBatchSize=1024 портов, общий размер не ограничен им.
Основные/временные диапазоны, маска, имена и целые числа проверяются до записи.
Источник копируется; ошибки не оставляют часть новых строк.

NetworkSetupView открывает форму внутри NetworkPairEditorHost. Снимок плана
проверяется перед SaveAddressPlan: изменение другой командой отклоняет устаревшую
форму. Повторный клик не создаёт вторую форму. SaveAddressPlan сохраняет
прежние привязки/applied-владение и возвращает ссылки при ошибке записи;
форма остаётся для повторной попытки. После успеха поиск/фильтр очищаются,
выделяется первый новый порт. Формат NetworkPlan не менялся.

NetworkPlanWindow показывает ту же форму вместо своей таблицы без нового окна.
Результат возвращается в черновик вместе с маской; запись только по
«Сохранить план». Прежний NetworkPortBatchWindow остаётся тонким хостом
общей формы для групп отдельных портов. Ни одна ветка не вызывает системное
назначение IPv4 и не правит пары существующей ноды DataTest.

## Динамический пустой план и назначение карты — 2026-11-23

BenchNetworkPlan.Addresses больше не создаёт Range(2,10). Отсутствующие
настройки/поле Addresses дают пустой список; JSON с сохранёнными строками
не дополняется. Validate допускает пустой список как отсутствие настройки,
но BuildDataTestPairs и ValidateAssignments блокируют запуск/применение.
CreateNextAddress использует стартовые предложения .2 и сохраняет прежний
алгоритм маски, пропуска сети/broadcast и всех занятых колонок. Это предложения,
а не дополнительные строки. Массовое добавление задаёт пользователь.

NetworkAdapterSettingsViewModel строит выбор из фактического черновика, обновляет
сводку при AddPort/RemovePort. После удаления последнего порта план можно
сохранить. NetworkSetupViewModel.SaveAddressPlan удаляет только привязки
исчезнувших IP; AppliedDataTestAdapterIds сохраняет владение ранее применёнными
адресами до явной операции Windows. Ошибка записи возвращает все три ссылки.
Если удалений нет, прежние привязки/владение сохраняются без замены.

В UI явные «Тестовые порты и пары…», пустое состояние, создание/удаление порта
у карты и удаление всех строк в редакторе. Изменение не переписывает пары
сохранённых профилей. Исторический DefaultPortsText в сериализаторе старых
DataTest-профилей сохранён для совместимости; он не задаёт сетевой план.
Справка включает отдельные определение и сценарий с нуля.

## Инвентаризация и настройка отдельных адаптеров — 2026-11-23

DataTestNetworkConfigurator.GetComputerAdapters перечисляет Ethernet,
GigabitEthernet и Wireless80211 из NetworkInterface; GetAdapters сохраняет
прежний проводной контракт для генератора и проб. BenchAdapter дополнен
описанием, типом, маской, шлюзом, IPv4 DNS и nullable DHCP. ID интерфейса
остаётся основой назначения; отображаемое имя можно изменить. VPN/tunnel и
loopback не включаются; Ethernet-интерфейс виртуального адаптера ОС может
отображаться как Ethernet.

NetworkSetupViewModel держит отдельные ComputerAdapters/VisibleComputerAdapters
и TestAdapters только для выбора проводных карт плана. При обновлении VM строк
сохраняются по ID. Число главных строк равно инвентаризации ОС, логические Rows
не меняются автоматически. NetworkAdapterSettingsViewModel редактирует копию
плана; сохранение проверяет карту заново, сохраняет NetworkPlan/DataTestAdapterIds
одной SaveChecked и возвращает прежние ссылки при сбое записи.
AppliedDataTestAdapterIds не заменяется новыми назначениями; при null сохраняется
прежняя карта DataTestAdapterIds как база владения адресами. Операция
настройки ОС выставляет общий IsBusy и блокирует запуск/пробы; закрытие окна
запрещено до завершения команды.

NetworkAdapterIpv4Configuration проверяет адрес/маску/шлюз/DNS до вызовов ОС;
NetworkAdapterOperations проверяет Windows/admin, существование стабильного ID,
локальный дубликат IPv4 и повторно проверяет ID/имя перед каждой командой.
Команды передаются в netsh через ProcessStartInfo.ArgumentList без shell.
Статический IPv4 заменяет прежние IPv4 этой карты; DHCP и DNS выбираются
независимо, IPv6 не меняется. После успеха данные перечитываются из ОС.
При частичном выполнении ошибка явно сообщает число выполненных команд;
автоматического отката системных IP/DNS нет. Черновик окна остаётся для
исправления, «Обновить данные» явно перечитывает фактические значения.

Синтаксис IPv4/DNS проверен по [официальной справке Microsoft netsh interface](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-interface).
На macOS список читается из ОС, прямые изменения выключены, есть переход в
системную сеть. Windows-команды в текущей проверке исполняются имитатором;
реальное назначение IP/DNS на Windows в этом изменении не проверялось.

## Изоляция и адаптация макетов — 2026-11-21

Сохранение LabelTemplatesWindow пишет только catalog/label-templates.json,
не перезаписывает AppSettings.LabelTemplates. Общие lookup, Legacy и выбор
формата при смене модели читают LabelTemplateCatalog.ConfiguredTemplates,

текстового элемента меняется только при точном совпадении с прежним названием.
Undo возвращает исходный макет. Данные Barcode и произвольные скрипты не меняются.
См. FreshUserJourneyTests и полный отчёт проверки нового рабочего места.

## Редактор элементов и проверка штрихкода — 2026-11-21

LabelLayoutDefinition — дополнительная структура Text/Barcode/Box, которую
LabelPrintContent.Render превращает в ZPL/EPL с теми же нормализованными SN/MAC,
что получает PrintLabelStep. Импорт raw-команд явный; неподдерживаемые поля
отклоняются. ZPL-текст кодируется UTF-8 через ^FH; значение не превращается в
команду. В EPL выбирается подходящий дискретный шрифт, неподдерживаемый Unicode
отклоняется. У Code 128 целый модуль и поля 10×module. Предпросмотр может показать
выход за бумагу для исправления; runtime проверяет границы до отправки байтов.

LabelLayoutEditorViewModel хранит копию, координаты в точках с вводом мм,
данные примера, диагностику и сравнение со сканером. Canvas поддерживает мышь,
ручку изменения размера и клавиши. Штрихкод меняет модуль, а не растягивает
полосы. Перемещение, источники полного/короткого номера, составного кода и
прочих полей сохраняются в layout. Предпросмотр и печать используют один
генератор команды; LabelPreviewElement.EncodedData показывает реальную строку.
PrintLabel.Barcode содержит фактический первый код, PrintLabel.Barcodes — все;
они очищаются перед новой попыткой. Цифровое считывание проверяет ZXing.Net
0.16.11 только в тестах; библиотека не добавлена в приложение.

Пробная печать редактора использует отдельный контекст и один экземпляр, не
затрагивает DUT, отчёт или историю полного теста. Во время печати выставляется
IsLabelToolBusy, запуск графа/кнопок заблокирован; закрытие отменяет операцию.
PNG сохраняет образец 1 px/dot с рамкой 2 px; шрифты приблизительны. Этот
цифровой образец не подтверждает качество реального отпечатка и головки.

LabelTemplateStore читает переносимые каталоги с приоритетом локального над
поставкой. Повреждённый каталог не подменяется прежними данными для печати:
страница показывает ошибку, runtime отклоняет загрузку. Каталог, несовместимый
со старой программой, содержит маркер, предотвращающий печать старой команды.
Явные снимки профилей/последнего теста независимы от последующей правки каталога.

Сверено с первичными руководствами:

## Панель ICMP-пинга — 2026-10-30

`PingMonitorSettings` хранится в профиле и не связан с IP из AppSettings или
нод selftest/DataTest. Пользователь задаёт адрес, период, таймаут и отображение.
Панель не использует TCP/HTTP как замену ICMP и не влияет на результат графа.

`Services/Network/IcmpPingProbe` использует `System.Net.NetworkInformation.Ping`.
DNS-разрешение и ответ ограничены общим таймаутом и токеном отмены.
Успешный ICMP-ответ содержит RTT; отсутствие ответа и ошибка выполнения
(например DNS/разрешений) отображаются раздельно. Для DNS используется первый
разрешённый адрес. Процесс `ping -t` приложение не запускает.

`PingMonitorViewModel` ведёт один последовательный цикл. Период считается между
началами запросов; если запрос длится дольше периода, следующий начинается после
его завершения. Параллельных запросов и очереди пропущенных периодов нет.
При смене адреса/параметров старый цикл отменяется, новый ждёт его завершения.
Номер поколения отбрасывает поздний ответ старого профиля. Показания сбрасываются
при смене профиля, выключении и остановке опроса; изменение только видимости
не прерывает текущий цикл.

Монитор включается жизненным циклом главного окна и выключается при Dispose VM.
Обучение и редакторы графов кнопок не запускают пинг. Опрос не требует COM
и продолжается во время подготовки, теста, паузы и переключения рабочих режимов.
Его результаты не добавляются в поток логов теста.

объектов адаптеров. Очистка строки и отсутствие карты сохраняются при обновлении.
Занятая карта обменивается с прежней картой строки; валидатор проверяет результат
до применения. Взаимная блокировка настройки сети и запуска/подготовки теста
проходит через `TestViewModel.IsNetworkSetupBusy`. Нижний статус показывает
прогресс применения; после результата обновляется фактическое состояние.
Каждая команда netsh ограничена 30 секундами; при тайм-ауте процесс завершается
и показывается ошибка. При смене подсети проверка использует последние применённые
привязки. Новые привязки отмечаются применёнными после проверки адресов и маски.
До записи приложение запоминает DHCP или статические IPv4 с масками. При сбое
или ошибке сохранения настройки затронутых карт восстанавливаются. Если восстановление
не подтверждено, сообщение перечисляет карты с ошибкой. Для назначения выбираются
карты стенда без шлюза IPv4. Закрытие окна во время настройки блокируется.

## Обновление 2026-10-14: платы и защита отчётов

Платы используют существующие Build/Send Test Report и серверный клиент TB.
FTServiceUtils не подключён. В новых профилях указаны серверные типы RTL-SW и RTL-POE;
производственный сервер с этими параметрами пока не проверен. Серийные номера не подменяются
выдуманными значениями. Отчёт после отказа отправляется лишь при наличии SerialNumber,
после снятия питания, и не дублирует уже отправленный отчёт. Ранний отказ SW без номера
остаётся в журнале. Измерения диапазонов можно явно включить через ReportName.

Этикетка платы: прежний EPL 30×10 мм/300 dpi, полный serial+Code128, одна копия явно.
В SW включена, в PoE выключена (в исходнике не была обязательным финальным этапом).
Есть отдельный профиль ручной печати. ZPL-макеты коммутаторов сохранены.

Локальная копия отчёта теперь скрывает поле session; исходный wire payload не меняется.
HTTP redirect при отправке выключен, чтобы не перенести сессию на другой адрес.
Из Chrome selftest убраны --no-sandbox и wildcard allowed origins. Локальный TCP CDP
по-прежнему требует отдельного усиления; см. отчёт аудита, не считать это полной защитой.

## Отчёты плат — 2026-11-10

Обе платы используют прямой POST с JSON на `/api/Api.svc/SendTestResultUniverse`.
Контракт проверен по `FTServiceUtils.dll` из RTL_v2. Тело запроса содержит
`result`, `sessId`, `isPswDevice`. В `result` передаются идентификатор
платы, стенд, статусы и выбранные строки проверки.

RTL-SW получает номер через `getSerialNum` с `devType=RTL-SW` и
`cpuId=DEVICE_ID`, передаёт полный номер в отчёте и сверяет ответ с ним.
RTL-POE передаёт MCU ID и пустой номер. При ответе с ненулевым `id` и
положительным `serialNumber` программа сохраняет номер для печати и
дописывает его в локальный отчёт. При неопределённом исходе запроса на выдачу
номера автоматического повтора нет. Сессия отправляется на адрес сервера из
настроек. Штатные отчёты и печать включаются в соответствующих подтестах.

В стандартных профилях включён «Отчёт при отказе» после снятия питания.
Он выполняется при отказе полного прогона, если отчёт ещё не принят сервером.
Когда у платы уже есть номер текущего прогона, используется этот номер.
До выдачи номера клиент отправляет результат `isSuccess=false`,
`isFull=false` с `deviceSerial=null` и служебным `deviceIdent` из
`rtlReport.failureDeviceIdentifier`. Идентификаторы взяты из начальных
результатов RTL_v2. Серверный номер служебной записи дописывается в копию
отчёта и остаётся отдельно от `SerialNumber` платы.

## Совместимость с лаунчером RTL_v2 (2026-10-01)

Проверены `App.xaml.cs` и `Infrastructure/Firmware/DeviceSerialNumberService.cs`
репозитория [RTL_v2](https://github.com/kotyasmol/RTL_v2): аргументы имеют порядок
`sessionId userName`, запрос серийного номера использует `User-Agent: ftstand` и
`Cookie: SGUID=session_id=<sessionId>&login=`. Поле login в cookie остаётся пустым,
как в RTL. Имя отображается в окне и доступно в контексте как `OperatorName`.

`LauncherServerClient` добавляет эти заголовки только к `getSerialNum` на origin
настроенного `AppSettings.ServerBaseUrl`; другой адрес в ноде не получает cookie.
Автоматические redirect у этого отдельного клиента отключены. DUT/selftest
сессию не получают. Передача сессии в legacy-отчёте сохраняется без изменения
протокола: строка `session=true=...`. Тестовые значения сессии не зашиты в код.

У лаунчерного контракта из RTL нет роли, endpoint проверки сессии или загрузки
профилей. Эти возможности не имитируются. Реальная выдача номера/приём отчёта
с новой интеграцией требуют отдельной проверки на корпоративном сервере.

Эта страница описывает инфраструктуру, которой пользуются HTTP-, сетевые, отчетные и печатные ноды.

Модели без `Pro` относятся к старым коммутаторам; модели с `Pro` — к новым.
Для `PSW-2G6F+` selftest запрашивается с `/test.shtml`, MAC записывается по
UDP. Для `PSW+UPS-Box 8x2Pro` selftest читается через LuCI `deviceinfo`, а
MAC записывается через WinSCP. Обе страницы находятся на `192.168.0.1`,
поэтому доступность одного только корневого URL не проверяет нужный endpoint.

## HttpRequestService

`HttpRequestService` реализует `IHttpRequestService`:

```csharp
Task<HttpRequestResult> GetAsync(string url, TimeSpan timeout, CancellationToken cancellationToken)
```

Что делает:

1. Проверяет, что URL не пустой.
2. Проверяет, что URL абсолютный и схема `http` или `https`.
3. Создает linked timeout token.
4. Делает GET через `HttpClient`.
5. Возвращает `HttpRequestResult.Success` или `Failure`.

`HttpRequestResult` содержит:

| Поле | Назначение |
|---|---|
| `IsSuccessStatusCode` | HTTP 2xx. |
| `StatusCode` | Код ответа или `null`. |
| `Body` | Тело ответа. |
| `ErrorMessage` | Нормализованная ошибка. |
| `Elapsed` | Время выполнения. |

## Selftest HTTP

`SelfTestCheckStep` имеет особую логику получения страницы:

- до общего таймаута раз в `PollIntervalMs` проверяет TCP-порт URL;
- пока DUT не отвечает, Chrome/Edge не запускается;
- после появления DUT запускает одну фоновую browser-попытку с чистым профилем
  и передаёт ей исходный URL прямо в строке запуска;
- ждёт завершения загрузки по `document.readyState == complete` и паузу DOM из ноды;
- один раз читает DOM через DevTools Protocol как аналог Selenium `driver.PageSource`
  и закрывает браузер этой попытки;
- если снимок не содержит `<selftest>...</selftest>` или совместимый
  `<settings>...</settings>` с `default_mac`, ждет `PollIntervalMs` и пробует снова.

Пауза DOM по умолчанию составляет 10 секунд, как в старой Selenium-утилите.
В ноде её можно изменить или поставить `0` для чтения сразу после загрузки.
Фактический общий таймаут виден в ноде и логе. Старые профили сохраняют прежний
пересчёт короткого DUT-таймаута до отключения режима «Таймаут старого профиля».
В браузерном режиме нет POST-логина и
обычного HTTP fallback; каждая попытка повторяет именно `Url` ноды. Если
профиль старого коммутатора задал `/test.shtml`, нода открывает его напрямую.
С 2026-10-22 `BrowserAttemptCoordinator` допускает одну браузерную попытку
на всё приложение, включая параллельные графы и повторные запуски. Ожидание
очереди входит в таймаут попытки и отменяется общим токеном.

На Windows `WindowsProcessJob.Start` создаёт Chrome приостановленным, включает
его в Job Object с `KILL_ON_JOB_CLOSE` и только затем продолжает выполнение.
Дочерние процессы принадлежат той же группе. После попытки Chrome получает
`Browser.close` (до 2 секунд), затем оставшиеся процессы группы завершаются
через `TerminateJobObject`; до 3 секунд проверяется `ActiveProcesses == 0`.
Эта проверка выполняется и после выхода главного Chrome. Прежний `taskkill`
по PID родителя удалён: уже вышедший родитель не доказывал завершение детей.
Закрытие job handle также останавливает принадлежащие ему процессы при
закрытии приложения. Посторонние экземпляры браузера не затрагиваются.

Ошибка подтверждения завершения блокирует следующие браузерные запуски
до перезапуска приложения. Отмена тоже ожидает очистку; исключение логгера
не прерывает закрытие. На macOS/Linux сохранено завершение дерева через
`Process.Kill`. Уникальный временный профиль удаляется отдельно в фоне
после очистки. Все браузерные операции идут вне UI.
В логах отдельно отмечаются запуск, DevTools, готовность документа, чтение DOM, выход Chrome
и обнаружение XML; таймаут включает название этапа. Это диагностика Windows-стенда,
а не подтверждение устранения зависания без повторного аппаратного прогона.
Старые сохраненные профили с `TimeoutMs` до `160000` для DUT selftest автоматически получают
эффективный таймаут `180000`. Стартовая проверка рабочего профиля ждёт DUT и
страницу до пяти минут (`300000`), а последующие selftest-проверки — до трёх
минут (`180000`), проверяя готовность каждые пять секунд.
В Windows-комплекте 1.0.0 selftest сначала ищет
`Browser/chrome-win64/chrome.exe` относительно каталога приложения, независимо
от рабочей папки лаунчера. Если встроенного браузера нет, сохраняется поиск
установленных Chrome/Edge. Перемещение папки комплекта не ломает этот поиск.

Для headless Chrome/Edge используется внутреннее чтение DOM через DevTools Protocol после ожидания
загрузки страницы, по смыслу аналогично старому Selenium `driver.PageSource`, но без внешней утилиты.
`PollIntervalMs` задает паузу между полными браузерными попытками.
Извлечение декодирует HTML-, URL- и JS-экранирования, потому что нужный XML может лежать в скрытом DOM/скриптах LuCI.
Проверка `ValidationRules` пишет в лог отдельные строки по каждому параметру и сохраняет
`SelfTest.CheckedRuleCount`, `SelfTest.FailedRuleCount`, `SelfTest.ValidationSummary`.

Операционная причина трёхминутного ожидания, нерабочие альтернативы и порядок диагностики
зафиксированы отдельно: [[18 - Selftest и загрузка DUT]].

До извлечения XML каждая завершённая попытка пишет исходный DOM браузера
(либо тело HTTP-ответа) в обычный журнал на уровне Info: URL, номер попытки,
число символов и полный текст частями по 8192 символа без обрезки.
Пустой ответ отмечается `<empty>`, ошибка чтения выводится отдельно.
Сохраняются также страницы входа, ошибки, скрипты и скрытые элементы,
даже если `selftest`/`settings` отсутствуют. Сообщения входят в файловый
журнал прогона при включённой записи в файл; в UI действует обычное
ограничение истории в 1000 записей.
HTTP-код показывается только если он известен: браузерный DOM не выдаётся за HTTP 200.

Извлечённый XML доступен в `TestContext` текущего запуска как `SelfTestRaw`.
Файл `selftest.txt` больше не создается: он был legacy-артефактом старой консольной утилиты.
Полный перечень исторических XML-полей, формула фактического количества,
legacy-алиасы и служебные ключи описаны в [[19 - Поля тестовой страницы DUT]].

`FailOnError` в selftest-нode не переключает результат на `True`; при ошибке step возвращает `False` всегда. Разница только в том, выставляется ли `context.HasCriticalError`, который потом влияет на поле `test_result` в отчете.

## API устройства

Для новых графов DUT API использует две универсальные ноды:

| Нода | Назначение |
|---|---|
| `Read HTTP Variable` | Один GET, строгий разбор ответа и запись свежего значения. |
| `Wait Variable Until` + `HttpGet` | Повторный GET до совпадения значения или обязательного таймаута. |
| `Wait Variable Until` + `SelftestSnapshot` | Повторный снимок всей тестовой страницы и сравнение целевого поля. |

Обе ноды принимают произвольные `BaseUrl`, `Endpoint`, output variable и
`ResponseType`: `Integer`, `Number`, `Boolean`, `String`. `Endpoint` может быть
относительным путем или полным HTTP/HTTPS URL. Перед запросом старое output
value удаляется, поэтому оставшееся от selftest значение не может пройти как
результат свежего чтения.

Рабочий UPS-алгоритм:

1. На SIMBAT выполняется `slave 17 / 1706 ← 1` с read-back-проверкой.
2. `SelftestSnapshot` ждёт `Dut.akb_voltage` в диапазоне `20..27` В при
   включённом AC1.
3. На PS-3 выполняется `slave 23 / 1200 ← 0` с проверкой: AC1 выключен.
4. Новый снимок снова должен дать `akb_voltage = 20..27` В. Доступная страница
   и нормальное напряжение при выключенном AC1 подтверждают работу от АКБ.
5. AC1 возвращается записью `slave 23 / 1200 ← 1` с проверкой.
6. Третий свежий снимок должен дать `akb_voltage = 20..27` В при работе от сети.
7. Имитатор отключается записью `slave 17 / 1706 ← 0` с read-back-проверкой.

Все три ожидания используют `SelftestSnapshot`, `ComparisonType = Number` и
диапазон `ExpectedValue = 20..27`; request timeout `30000` мс, общий timeout
`160000` мс, интервал `5000` мс и `FailOnTimeout = true`. Фиксированных
задержек нет: старое `Dut.akb_voltage` удаляется, снимается новая страница, а
значение вне диапазона приводит к следующей попытке. После отключения SIMBAT
диапазон не проверяется, потому что требования к напряжению в этом состоянии
не определены.

Предыдущие варианты UPS-графа опирались на артефакты старого оборудования:
тракт PS-3 `1210`, `ups_rez`, `/api/getUpsStatus` и косвенные проверки
`1707/1708`. В актуальном стенде подключением имитатора управляет записываемый
регистр SIMBAT `1706`. Поле `akb_det` на фактической прошивке не меняется при
`1706 = 1`, поэтому признаком исправной батарейной цепи служит
`akb_voltage = 20..27` В. Исторические API-ноды и специализированные poll actions удалены
2026-10-01. Для скалярного API используйте `Read HTTP Variable` или
`Wait Variable Until` + `HttpGet`, явно задавая endpoint и тип ответа.
Автоматического fallback между `/api/isUPS` и `/api/isUps` больше нет;
нужный регистр пути определяется прошивкой DUT. Профили со старыми типами
или режимами отклоняются при импорте без изменения открытого графа.

## Получение серийного номера

В опубликованном 8x2Pro «отчёт 10.11» (маркер 9) этап 06 читает с DUT
только `cpu_id`, затем запрашивает серийный номер с `devType=PSW+UPS-Box 8x2Pro`.
Параметр `devType` берётся из ноды. Поля `deviceModel` и `deviceModelId`
корневого профиля задают отображение и группировку. Изменение модели в
шапке профиля не меняет ни серверный запрос, ни настройки MAC, ни диапазоны.
В Qt серверный запрос также использовал строку `model_name` из конфигурации.
Числовой `dev_type` прошивки — отдельное поле. В этом профиле проверяется
`Dut.dev_type == 0`, хотя серия серийных номеров начинается с `32`.

`GetSerialNumberFromServerStep` строит URL двумя способами.

Если `ServerBaseUrl` похож на полный endpoint:

```text
https://server/api/api.svc/getSerialNum
```

то добавляется только query:

```text
?devType=...&cpuId=...
```

Если `ServerBaseUrl` - хост или базовый URL:

```text
server.local
http://server
```

то строится:

```text
http://server/api/api.svc/getSerialNum?devType=...&cpuId=...
```

Также можно указать `http://server/api` или `http://server/api/Api.svc`: нода
достроит только недостающую часть пути и не создаст ошибочный `/api/api/api.svc`.

Плейсхолдеры `SERVER_BASE_URL`, `http://SERVER_BASE_URL` и `server-address`
не отправляются в DNS как реальные хосты. При создании step из GUI они заменяются
общей настройкой `Server base URL`; если настройка пустая, нода завершается
понятной ошибкой `ServerBaseUrl не задан`.

Если `CpuIdVariableName` задан, нода требует непустую переменную CPU ID до
сетевого запроса. Имя ищется без учета регистра, чтобы `Dut.cpu_id` работал и с
XML-тегом `CPU_ID`. Запрос без `cpuId` остается доступен только при явно пустом
`CpuIdVariableName`, как в низкоуровневом методе старого Qt-стенда.

Перед запуском ноды прежние `SerialNumber`/`NetTest.SerialNumber` удаляются.
Серийный номер считается валидным только как положительное целое число в plain text
или JSON scalar; случайная последовательность цифр в HTML/тексте не принимается.
Для диагностики сохраняются URL, CPU ID, число попыток, последний HTTP status,
elapsed, raw response и текст ошибки.

Производственная ветка намеренно повторяет `TestThread::getSerialNumber` и
`MainWindow::get_serial_num` из `psw_stand-dev`: сразу вызывает `getSerialNum`
с `devType` и `cpuId`. Отдельный legacy endpoint `getExistsSerialNum` не является
частью этой цепочки. Стенд показал, что интерпретация его положительного ответа
как серийного номера коммутатора подставляет CPU ID в `SerialNumber`, поэтому такой
предварительный lookup запрещён.

Серверный `devType` задаётся в ноде «Получение серийного номера». Соседнее
поле «Префикс» проверяет ответ, например `33` для серии `33…`. Оно не
меняет параметр запроса. Если сервер вернул номер другой серии, нода
сообщает ожидаемое и полученное значения и не повторяет запрос выдачи.
Для уже записанного в коммутатор номера в ноде «Формирование отчёта»
укажите переменную, куда его прочитали, и нужный префикс. В `serial_num`
уходит только проверенный полный номер. Если источник пуст или номер
чужой серии, текст отчёта очищается и отправлять нечего. Для графов со
штатной и аварийной ветвями настройте обе ноды формирования отчёта.
Если новый профиль создан копированием 8x2Pro, отдельно проверьте границы
в нодах проверки диапазона и смещение в расчёте MAC. Это параметры графа
и поле «Префикс» их не меняет.

Для стендовой отладки есть явный режим `UseFixedSerialNumber`. В нём серверный
endpoint не вызывается, а в `SerialNumber` и `NetTest.SerialNumber`
записывается `FixedSerialNumber`. В профиле 8x2Pro из маркера 9 режим
выключен, хотя в JSON сохранено значение `3200428`. В этом случае используется
серверный запрос по `Dut.cpu_id`, источник результата — `Server`.
Поле «Префикс» появилось в коммите `46d1328`, после публикации маркера 9.

## Set Pro MAC

`SetProMacStep` заменяет неподходящую для Pro-коммутаторов legacy UDP-команду.
Он запускает предоставленный рабочий `set_mac_pro.bat` с тремя аргументами:

1. полный MAC из `Dut.NewMac`, нормализованный как `AA:BB:CC:DD:EE:FF`;
2. точное имя модели/`boardversion`, в рабочем профиле `PSW+UPS-Box 8x2Pro`;
3. текущий Unix timestamp в секундах.

Bat-файл через `WinSCP.com` подключается к `192.168.0.1` и выполняет команды
прошивки: `fw_setenv ethaddr`, `fw_setenv boardversion`, `macset.sh` и запись
`RTC_TIMESTAMP`. Секреты подключения остаются внутри поставляемого bat-файла и
не переносятся в C# или JSON-профиль.

Нода работает только в Windows. Относительный `BatchPath` ищется в текущей
папке и рядом с `TestBuilder.exe`; абсолютный путь также поддерживается.
Штатный `TestBuilder/set_mac_pro.bat` включён в проект и копируется рядом с exe
как при сборке, так и при publish. Сам bat ищет `WinSCP.com` в соседней папке
`WinSCP`, в `PATH` и в стандартных папках установки. При отсутствии WinSCP он
завершается с понятной ошибкой без интерактивного `pause`.

В `TestBuilder/WinSCP` поставляется официальный portable WinSCP 6.5.7 вместе
с лицензией. Папка целиком копируется в build/publish, поэтому штатный bat сразу
находит `%~dp0WinSCP\WinSCP.com`; установка WinSCP на стендовый ПК не нужна.

stdout/stderr читаются параллельно в OEM-кодировке, а вызов полностью
асинхронный, поэтому ожидание WinSCP не блокирует UI. По таймауту завершается
всё дерево процессов.

Успешным считается только сочетание exit code `0` и маркера `SUCCESSFUL` в
stdout рабочего bat-файла. Ненулевой код, отсутствие маркера, таймаут или
ошибка запуска ведут по `False` при `FailOnError = true`. Диагностика доступна
в `SetMac.Started`, `SetMac.TimedOut`, `SetMac.ExitCode`, `SetMac.StdOut`,
`SetMac.StdErr` и `SetMac.Error`; фактические аргументы — в `SetMac.Mac`,
`SetMac.BoardVersion`, `SetMac.Timestamp`, `SetMac.BatchPath`.

Успех процесса означает, что WinSCP принял команды, но не доказывает сохранение
MAC. Рабочий граф после этого перезапускает DUT, очищает ARP, получает новый
selftest и сравнивает `Dut.default_mac` с `Dut.NewMac`.

## Clear ARP Cache

`ClearArpCacheStep` очищает ARP-кэш Windows перед сетевыми обращениями к DUT.
Это нужно, когда устройство перезагрузилось, сменило MAC или стенд быстро
переключает платы с одинаковыми IP: Windows может помнить старую связку
`IP -> MAC`, и запросы уйдут не на то устройство.

Штатный `arpd.bat` и прямая команда `arp -d *` выполняют одну операцию.
При таком сочетании нода вызывает `arp` один раз и устанавливает
`ArpClear.BatSkippedDuplicate`. Другой сценарий BAT выполняется перед прямой
командой. Относительный BAT ищется также в `AppContext.BaseDirectory`.
Старое значение аргументов `-d` у `arp` нормализуется в `-d *`.
На Windows перехваченные stdout/stderr читаются в OEM-кодировке текущей
системы, а не как UTF-8; русский stderr `arpd.bat` попадает в лог без mojibake.
Непустой stderr считается ошибкой даже при exit code `0`, поэтому отсутствие
прав администратора больше не сопровождается ложным сообщением об успешной
очистке. При `FailOnError = false` ошибка записывается в отчёт. В обычном графе
выполнение идёт по штатному выходу. Во время подготовки ошибка сразу останавливает
граф, в том числе внутри стартового подтеста.

Stdout и stderr читаются одновременно с работой процесса, чтобы заполненный
буфер не блокировал завершение. При отмене или таймауте step завершает дерево
процесса и ограниченно ждёт его выхода и чтения потоков. Отмена пробрасывается
после этой очистки; невозможность завершить процесс считается ошибкой даже
при `FailOnError = false`. Это позволяет дождаться ARP-ветви перед общим
cleanup параллельного графа. Проверки локального процесса — VER-049;
реальный Windows ARP этой проверкой не подтверждён.

## Обновление ПО старого PSW

`UpdatePswFirmwareStep` применяется в профиле PSW-2G6F+ после первой
`/test.shtml`. Сравнивает `Dut.firmvare_vers` с целью `0.2.13` (525);
значение `20c` читается как hex 524 и означает 0.2.12; `208` читается
как hex 520 и означает 0.2.8; целевой код — `20d`. В профиле сейчас
`forceUpdate=false`: версия 0.2.13 или новее пропускает загрузку. При ручном включении этого
параметра разрешается откат с более новой версии; равная всё равно пропускается.
До первого HTTP-запроса проверяются путь, имя и расширение `.img`; SHA-256
по просьбе оператора не проверяется. Затем выполняются
`GET /clear.shtml`, пауза 10 с, multipart POST `/mngt/update.shtml` с полем
`updatefile`, пауза 10 с, `GET /mngt/update.shtml?Update=Update`, пауза 40 с,
повторный selftest и сравнение новой версии с минимумом 0.2.13. При
`forceUpdate=true` требуется точное совпадение. POST использует
multipart-разметку исходного Qt-приложения. При провале шага тест останавливается.
После повторного selftest старая переменная версии удаляется перед чтением,
а фактический код версии записывается в лог.
Ответы загрузки и подтверждения выводятся в `[FW]` с начала и конца HTML:
HTTP 200 без изменения версии не считается успешной прошивкой.
Это протокол старого PSW; к Pro он не применяется. Стендовый лог 2026-09-23
подтвердил установку 0.2.8 (`208`). Подробный порядок и текущий Sensor1:
[[20 - PSW-2G6F+ тестирование]].

## DataTest через SharpPcap

Разбор стендового инцидента и порядок повторной диагностики:
[[22 - Инцидент сетевых карт 2026-09-28]].

Сетевой план рабочего места редактируется во вкладке «Сеть».
Число строк, названия, роли, IPv4, временные адреса, маска, пары и скорости
настраиваются. Исходный план `.2`–`.11` не является обязательным для всех моделей.
Привязка IP → ID адаптера хранится локально; смена имени Windows не меняет ID.

Нода DataTest сама адреса не назначает: использует сохранённую таблицу активных
пар. В интерфейсе ноды можно добавить/исключить пару и задать скорость отдельно.
Копирование из сетевого плана создаёт снимок; последующее изменение плана не
меняет граф. Неактивные пары сохраняются в `DisabledPortsText`.

Назначение IPv4 и переименование адаптеров — отдельные команды интерфейса,
для Windows нужны повышенные права. Перед перестановкой основных IP приложение
применяет уникальные временные адреса из плана. Ошибки показываются с результатом
команды; изменение плана и выбор карты сами по себе не выполняют `netsh`.
Физический линк, кабели и согласованная скорость проверяются отдельно.
Прежнего автоматического правила «шесть 100 Мбит/с + два гигабитных + два резерва»
в текущем редакторе нет. Подробные операции — [[03 - Работа с приложением]].

При DataTest имена, MAC и линк обеих карт выводятся в журнал. Если IP назначен
нескольким картам, тест отказывается выбирать произвольную. Историческая
раскладка APK-03-07 в [[22 - Инцидент сетевых карт 2026-09-28]] описывает тот
прогон и не должна применяться автоматически к другой модели/раскладке.

`RunDataTestStep` делает программный сетевой тест.

2026-11-02: устранена остановка до открытия сетевых карт с ошибкой
«Режим DataTest 'Программный генератор трафика' не поддерживается».
Это порча ключа режима при отображении редактора, а не результат измерения
сети. Runtime, чтение и сохранение JSON восстанавливают известную русскую
подпись в `SoftwarePcap`; UI больше не записывает подпись в Mode.
Подробности и регрессионные проверки — [[06 - JSON профили]].

Поддерживаемые режимы:

- `SoftwarePcap`;
- `Pcap`;
- `Software`;
- `TYPE_SOFT_GEN`.

Все эти значения ведут в одну текущую реализацию software/pcap. Если указать другой режим, step вернет ошибку с рекомендацией использовать `SoftwarePcap`.

Основные этапы:

1. Получить список `CaptureDeviceList.Instance`.
2. Последовательно, по одной строке `PortsText`, найти receive/send сетевые карты по IP.
3. Получить MAC-адреса адаптеров.
4. Построить Ethernet/IP/UDP packet заданного размера с ID запуска и sequence.
5. Открыть receive в promiscuous с буфером 16 МиБ, read timeout 20 мс и snaplen = min(размер кадра, 128). На провод отправляется полный исходный кадр; захват сохраняет заголовки и всю 16-байтную метку. В Windows также задать kernel buffer 16 МиБ и MinToCopy 64 КиБ. В текущем Windows-коде send при любой цели открывается с NoCaptureLocal и фильтром `len = 0`; promiscuous/max responsiveness остаётся для других ОС. Хвост RX ожидается до всех отправленных проб либо 200 мс тишины, максимум 2 с.
6. Поставить capture filter:

```text
ether src {OutMac} and ether dst {InMac}
and udp src port {UdpPort} and udp dst port {UdpPort}
and src host {OutIp} and dst host {InIp}
```

7. Сделать warmup с отдельным ID и дождаться очистки хвоста capture.
8. На прогреве сначала проверить один отправитель; в Windows
   при отказе, недостаточной скорости или неподтверждённом приёме — два.
   Учитываются уникальный RX, время доставки, capture drops и направленные
   ошибки карт. Исправный один отправитель предпочтителен. Потери RX без
   ошибок хоста сами по себе не локализуют неисправность: основной замер
   обязан подтвердить прежние допуски. При цели, равной скорости линка и
   выше 100 Мбит/с, очереди по 10 мс передаются без покадровой синхронизации.
   До старта подготовлены четыре очереди на отправитель (до 40 мс); ещё четыре
   могут ожидать в ограниченном канале и одна — готовиться. Объём не зависит
   от длительности теста. Между очередями используется отдельный Windows
   high-resolution waitable timer и QPC-хвост до 0,25 мс; при недоступном
   таймере — Yield. Опоздание не компенсируется ускоренным выбросом очередей.
   В Windows при цели до 100 Мбит/с `SendPacket` вызывается покадрово,
   интервалы задаёт QPC. Прогрев сначала проверяет один/два отправителя с
   отдельным high-resolution timer и QPC-хвостом 30 мкс, минимальное ожидание
   10 мкс. При отказе этой квалификации по тем же проверкам TX/RX проверяет
   один/два с активным QPC. На неподдерживаемой Windows проба сразу использует
   активное ожидание и возвращает фактический способ. При WarmupMs=0 таймер
   не квалифицируется: остаётся один активный отправитель. После паузы ОС
   просроченные интервалы не отыгрываются пачкой, последний интервал входит
   в измеренное время. Оба потока выполняются вне UI.
   В остальных режимах native-очереди синхронизируют кадры; части по 50 мс
   до 100 Мбит/с и по 20 мс выше. У двух отправителей раздельные handle,
   чётные/нечётные sequence и общие часы. Неполная native-отправка отклоняется
   с количеством кадров/байтов и LastError. Сосед отменяется и завершается
   до закрытия handle. В остальных native-режимах канал ограничен двумя
   ожидающими частями на отправитель.
   Захват и оба блокирующих цикла (подготовка и передача очередей) работают
   на отдельных потоках, вне общего ThreadPool. Сохраняется штатный цикл
   захвата SharpPcap и его StopCapture; преждевременный выход или ошибка
   захвата отклоняют измерение как инфраструктурный сбой.
   При отсутствии native очередей paced `SendPacket` проверяется по фактической
   скорости с заданным допуском дефицита. Отказ прогрева не является измерением DUT.
9. Считать только уникальные sequence текущего ID; отдельно учитывать duplicates,
   unexpected packets и Npcap capture drops.
10. Зафиксировать монотонный старт перед первой отправкой; у двух отправителей
    один старт после подготовки обоих. Конец приёма — последний уникальный RX
    текущего запуска. Для скоростей взять больший интервал: время отправителя
    или время от старта до этого RX. Быстрое принятие очереди драйвером не
    подтверждает скорость доставки. Дубликаты и чужие пакеты не продлевают
    интервал. Без RX остаётся время отправителя, а потеря 100% отклоняет тест.
    Посчитать RX/TX/loss/tx deficit и скорости с учетом 24 байт overhead
    на кадр: preamble/SFD 8, FCS 4, inter-packet gap 12.
11. Сравнить loss с `AllowedLossPercent`, а deficit генератора — с отдельным
    `AllowedTxDeficitPercent`.
12. При неудаче направления (потери, генератор/захват, таймаут) повторить его один раз.
    Учитываются также ошибки/отбрасывания TX отправителя, RX приёмника и
    доступность capture-статистики. RX отправителя и TX приёмника сохраняются
    в диагностике, но не отклоняют проверку противоположного направления.
    Неудача первой попытки остаётся в журнале и описании отчёта даже при
    успешном повторе. Локализация внутри тракта требует аппаратной проверки.
13. Если `Bidirectional = true`, поменять send/receive местами и проверить обратное
    направление. Затем закрыть карты и выдержать `InterPairDelayMs`.

В журнале и отчёте ошибка DataTest указывает имя пары, оба IP и направление
отправки. Короткая отправка, недобор скорости генератора и потери Npcap при
захвате помечаются как недостоверное измерение на стенде. Ошибка каждого
повтора указывает направление и номер попытки.

Пары никогда не запускаются параллельно. Глобальный и парный target ограничены
`100 Mbps` по умолчанию; `AllowGigabit=true` разрешает до `1000 Mbps`.
Legacy `1000` без флага при загрузке профиля по-прежнему мигрирует на `100`.
Для кадра 1514 байт target 100 Mbps соответствует примерно 8127 кадрам/с,
а 1000 Mbps — 81274 кадрам/с с учётом физического overhead Ethernet.
Настройки не меняют скорость NIC/SFP: известный линк ниже target блокирует тест.
Скорость строки пары в ноде имеет приоритет над legacy-полем общей скорости.
План сети — источник для явного импорта, не runtime override. Выбранные 100
Мбит/с не повышаются из-за гигабитного линка или соседней гигабитной пары.
Реальная способность ПК генерировать/принимать гигабит проверяется метриками
TX deficit и capture drops; программные тесты не подтверждают line rate на стенде.

### Значение метрик

| Метрика | Значение |
|---|---|
| `target` | Требуемая скорость на физической Ethernet-линии. |
| `expected` | Сколько кадров должно пройти за `DurationMs` при target. |
| `TX` | Сколько нумерованных кадров генератор подтвердил как отправленные. |
| `RX` | Сколько уникальных кадров этого запуска поймано на карте назначения. |
| `loss` | `(TX - RX) / TX`; потери между отправкой и приёмом проб. Нулевой capture drops сам по себе не локализует потерю в DUT. |
| `tx deficit` | Насколько фактическая TX wire speed ниже target; характеризует генератор/ПК. |
| `tx speed` | TX × полный размер кадра с Ethernet overhead / подтверждённое время передачи. Консервативная программная оценка, не аппаратная отметка на проводе. |
| `rx speed` | Фактическая скорость уникальных принятых кадров на той же временной базе. |

### Уточнения алгоритма по исходникам — 2026-11-18

Сверены `RunDataTestStep`, выбор отправителей, pacer, привязка карт и код
запущенной beta `1614302`. Пары берутся из ноды, копирование сетевого плана
создаёт снимок. До первичной подготовки проверяется однозначность IP → карта
Windows → pcap (GUID, затем уникальный MAC); две стороны одной карты запрещены.
Линк проверяется при выполнении ноды: до включения DUT он может быть Down.
Физическое соответствие кабельных пар автоматически не определяется.

В актуальном коде перед прогревом выполняется MAC-обучение: два прохода
по 60-байтному кадру 0x88B5 в обе стороны, обратная сторона первой, между
проходами 10 мс. В установленной на APK-03-07 beta `1614302` этого ещё нет.
Ещё два отличия подготовленного кода: общие часы двух отправителей запускаются
после готовности обоих; для полной скорости линка выше 100 Мбит/с и замера
длиннее прогрева допускается выбрать лучший полный безошибочный прогрев,
а скорость обязательно подтвердить основным замером с прежними допусками.
Если хотя бы одна проба не полностью отправлена или завершилась исключением,
такой перенос проверки скорости запрещён. На 100-Мбитный режим исключение
короткого прогрева не распространяется. Публикация этого комплекта описана
в [[49 - Единая поставка через лаунчер]] и ещё ожидает доступной Вышенской.

В коде от 18.11 прогрев оценивал только TX/время; с 19.11 при выборе
отправителя учитываются также RX и состояние захвата/карт. У каждой пробы отдельный случайный ID,
его пакеты не входят в основные RX. При `WarmupMs=0` прогрев пропускается
и остаётся один отправитель. Фактический объём рассчитывается из скорости,
длины кадра и времени; старое `ExpectedPackets=10000` только записывается в
контекст и не управляет числом кадров. На 1514 байтах за 5 секунд рассчитываются
40637 или 406372 кадра для 100/1000 Мбит/с соответственно.

Полезная нагрузка заполнена 0x41; первые 16 байт — TFDT, случайный 64-битный
run ID и 32-битный sequence в сетевом порядке байтов. IPv4 checksum вычисляется;
UDP checksum записан как 0. Приём проверяет метку, run ID и диапазон sequence,
уникальность учитывается массивом отметок. Весь остальной payload побайтно
не сравнивается. Нода не записывает pcap автоматически; отдельные файлы и
проверка Wireshark описаны в [[50 - Прямое соединение карт APK-03-07 2026-11-18]].

100-Мбитный Windows-поток и native-очереди отправляют рассчитанное число
кадров; при задержке время может превысить DurationMs, что уменьшит скорость.
Резервный `SharpPcapSendPacket` останавливается также по сроку и может вернуть
неполный TX, который оценивается по тем же метрикам. С 19.11 RX/TX speed
рассчитаны на подтверждённом интервале с учётом конца приёма. В журнале
раздельно указаны send time, confirmed time и средняя загрузка процесса
(process CPU — доля от всех доступных логических CPU за подготовку основного
замера, отправку и ожидание RX; это не общая загрузка Windows).
В переменные направления и каждой попытки добавлены SendElapsedMs,
ConfirmedElapsedMs, CaptureLength и SenderCount.
С 19.11 также записывается UsesPacketTimer. При недоборе скорости основного
замера с пакетным таймером следующий штатный повтор использует активный QPC;
потери без недобора скорости не меняют способ ожидания. Общий лимит двух
замеров, нагрузка и допуски сохраняются. Пробы прогрева не являются отдельными
попытками измерения DUT и в его TX/RX не входят.
Это не измерение задержки, jitter или побайтной целостности всей нагрузки.

Обычная ошибка одной пары не останавливает обход остальных пар внутри ноды;
после всех пар итог Passed требует успеха каждого направления каждой пары.
В парном итоге TX/RX суммируются, скорости берутся минимальные, loss/дефицит —
максимальные по направлениям. С 18.11.2026 DataTestDirectionRetry даёт каждому
направлению две попытки всего: один повтор при превышении потерь, сбое
генератора/захвата или таймауте. Общий лимит не складывается между категориями.
Успешное направление повторно не запускается; допуски и нагрузка не снижаются.
Между попытками 100 мс; каждый RunDirectionAsync заново открывает захват,
выполняет MAC-обучение/прогрев и использует новый ID основного замера.
Ошибки адресов/карт/линка в RunPortPairAsync до измерения не повторяются;
отмена пользователя пробрасывается без повтора.

Промежуточная неудача остаётся в журнале, а при успешном повторе — ещё и в
описании пункта отчёта с отметкой «пройдено со второй попытки». Итоговые
переменные содержат последнюю попытку, без усреднения и суммирования между
попытками. В PortN добавлены RecoveredOnRetry/RetryDetails; Forward/Reverse
содержат RecoveredOnRetry и отдельные Attempt1/Attempt2 с TX/RX, loss, скоростью,
кодом движка и ошибкой. Перед записью очищаются прежние переменные направлений,
чтобы повторное исполнение ноды не оставляло устаревшую Attempt2 или Reverse.
История находится в runtime-контексте, JSON профиля не меняется. Короткая проба
из «Сеть» также выводит описание повтора, если он потребовался.

`MaxPortTestTimeMs` задаёт отмену на каждую попытку направления, включая
прогрев и основное измерение. Отмена обрабатывается в циклах/ожиданиях;
она не означает принудительное прерывание заблокированного native-вызова.
Пауза графа ожидается на границах нод, текущую отправку DataTest она не
приостанавливает. Снятие FailOnError меняет переход на True, сохраняя реальный
Passed=false и неуспешный пункт отчёта. Печать, серверный POST, питание DUT
и ожидание загрузки выполняются другими нодами профиля.

### Старый C++/Qt-генератор: статическая сверка 2026-11-18

Разобрана поставленная копия `psw_stand-dev`, активный код без блоков `#if 0`.
Исходники старой программы не менялись; старый бинарник и оборудование этим
разбором не проверялись. Выводы относятся к этой копии исходников.

В `DataTest/DataTestThread.cpp` есть три режима: программный WinPcap,
аппаратный Беркут по парам и аппаратный шлейф. Для программного режима:

1. Выбранные IP последовательно объединяются в пары.
2. `GenThread` собирает один 1514-байтный Ethernet/IPv4/UDP-кадр с MAC/IP пары,
   портами 0xABBA и нагрузкой A; он не меняется от отправки к отправке.
3. `RcvThread` запускается, через `Sleep(1)` запускается передатчик.
   Барьера, подтверждающего готовность захвата/фильтра, нет.
4. Передатчик непрерывно вызывает `pcap_sendpacket(...,1514)` без pacer,
   заданной скорости или заданного количества; успешный вызов увеличивает TX.
   Ошибка отправки печатается в debug, не прекращая цикл.
5. Приёмник фильтрует `udp port 43962 and ip dst host <адрес>`.
   Каждый `pcap_next_ex > 0` увеличивает RX; длина, payload, источник,
   идентификатор запуска и уникальность номера не проверяются. Sequence/run ID
   в кадре отсутствуют. `recieved_bytes` увеличивается на 1514 для любой записи.
6. Приём завершается при 10000 записях (`TestThread.h:77`). Контроллер ждёт
   `running` либо 15000 итераций `Sleep(1)`; это не монотонный таймер на 15 с.
   Приёмник также считает 100 тайм-аутов pcap, а не 100 потерянных кадров.
7. Статус TEST_OK устанавливается только по `RX >= CAPTURE_LEN`
   (`DataTestThread.cpp:143–154`). TX и рассчитанная скорость не сравниваются
   с порогом. Обратное направление той же пары автоматически не выполняется.

Следствие: реальная передача была, но зелёный результат не доказывал
1 Гбит/с, малый процент потерь или корректность всей нагрузки. Например,
10000 кадров на 100 Мбит/с занимают приблизительно 1,2304 с на линии
и удовлетворяют тому же критерию, что 0,12304 с на гигабите. При TX=100000
и RX=10000 проверка приёма также удовлетворена, хотя доля недоставки 90%.
Это примеры допускаемых кодом результатов, не утверждение об историческом
состоянии изделий. Статистики `pcap_stats`/ошибок NIC в активной software-ветке нет.

Скорость вычисляется из числа полученных кадров, 1472 байт нагрузки и времени
чтения первой/последней записи через QDateTime; в UI умножается на 8 и
показывается как Kbps (`generator.cpp:179–186`). Это не wire speed и не
критерий успеха. Выражение `recieved_pkts * 1472000` даёт 14720000000 при
10000 кадрах, превышая signed 32-bit long Windows до деления на 64-битный
интервал. Поэтому есть дополнительный дефект переполнения вычисления;
точное проявление зависит от компилятора, signed overflow не определяет
надёжного численного результата.

У Беркут TXGEN отдельный дефект в активном `BercutThread.cpp:259,289`:
`error = std::abs(tx-rx) / tx`, все счётчики `long int` (`BercutThread.h:55–58`).
Деление целочисленное, присваивание double происходит после него. При обычных
положительных значениях RX<TX любая ненулевая доставка с потерями менее 100%
может дать error=0. Порог первого направления — 0.1, второго — 0.0002;
оба сравнения в таком случае проходят. Отдельный минимальный C++-пример
подтвердил: TX=1000000 и RX=990000/500000/1000 дают error=0, то есть
реальные 1%/50%/99,9% превращаются в 0. Это проверка арифметики, не запуск
прибора и не доказательство конкретного старого ошибочного отчёта.

Беркут RFC2544 — третья логика: берётся статус Passed и извлечённый процент
Throughput должен быть >=99.8 (`BercutThread.cpp:231–238`). Это обращение
к аппаратному тесту. Но активный `config_rfc2544` задаёт только topology tx a
и rx b, а не скорость линка/полный набор параметров испытания. Параметры
могли оставаться в самом приборе. `txgen rate 100` найден только в исключённом
`#if 0` варианте и не доказывает настройку активного TXGEN. `ports_speed=1000`
в `telnet.cpp:244` выбирает SFP-путь промежуточного коммутатора, не является
измерением 1 Гбит/с. Парсер RFC2544 не устанавливает новый ошибочный статус
для нераспознанного ответа и не сбрасывает состояние на входе — отдельный
риск сохранения результата предыдущего ответа при неполном/неожиданном тексте.

По этой копии кода программный TEST_OK не эквивалентен нашему критерию
«достаточная измеренная скорость + допустимые потери + пригодный захват».
Утверждать, что старый стенд всегда физически работал на гигабите или что
все его результаты были неправильными, исходники не позволяют.

## Сбор отчета

В beta от 10 ноября профиль 8x2Pro «отчёт 10.11» выбирает 50 строк
из образца 111 на данных графа от 09.11. Измерения и этапы этого графа
определяют, какие строки появятся в каждом прогоне.
См. [[32 - Beta с отчётом 8x2Pro 2026-11-10]].

В редакторе корневого профиля «Состав отчёта…» открывает выбор источников,
подписей, формата и порядка строк. Свой состав действует для штатного и
аварийного отчёта, общий итог вычисляется по всем результатам до отбора строк.
Отсутствующие измерения не выводятся. С 13.11 при отказе причина остановки
добавляется всегда, в том числе когда выбранная булева строка уже показывает
ошибку: она не содержит подробностей пары/IP или таймаута. Служебные поля
всегда передаются. Проверено матрицей десяти диагностических профилей;
см. [[36 - Десять диагностических профилей 2026-11-13]].
Если флажок «Выбирать строки отчёта вручную» снят, используются параметры
ноды и прежние поля selftest.
См. [[03 - Работа с приложением#Состав серверного отчёта]].

Вкладка «Переменные» объединяет известные выходы нод и имена переменных,
записанных при запуске профиля. Список обновляется после завершения прогона
и включает имена из аварийных и параллельных ветвей. Значения берутся из
текущего прогона при сборке отчёта. Служебные ключи отчёта недоступны для
повторного добавления. Отмеченная переменная получает тот же текстовый
формат, что в автоматическом режиме, если для неё не задан другой формат.

`BuildTestReportStep` повторяет формат `QTstand_old`:

```text
test_result=true=1
stand_id=true=123
serial_num=true=3200123
session=true=<session-id>
Тип проверки=true=production
самотестирование=true=true
напряжение АКБ=true=24.5
```

`test_result = 1`, только если нет `context.HasCriticalError` и все явные
результаты проверок в отчёте успешны. Ошибка печати или DataTest сохраняется
в результате, даже если граф настроен продолжаться после неё.
`stand_id` читается из `AppSettings.StandId` (дефолт `тест`), а `session` — из первого аргумента
запуска приложения и пропускается, если аргумент отсутствует. В `serial_num`
попадает полный номер из `serialVariableName`. Штатный и аварийный отчёты
8x2Pro из маркера 9 берут его из `SerialNumber`, который записала нода
серверного запроса. Отдельного служебного поля модели в POST нет.

Каждая строка имеет формат `name=true|false=value\r\n`. `SubtestStep` сохраняет
исход составного подтеста в `TestContext.ReportEntries`. Туда же добавляются
скорость/потери каждой пары DataTest, финальные измерения PoE A/B регистров
1402/1403 в цикле устройств и результат печати. `ProductionReportFields`
добавляет выбранные поля свежего selftest по Qt `TestThread::make_report`:
CPU ID, версии, MAC, link, активные PoE A, плату/контроллеры, присутствующие
SFP и напряжение обнаруженного UPS. XML-поля и aliases не дублируются.
Новая загрузка не подменяется старым успешным снимком при ошибке.

`IncludeAllVariables = false` по умолчанию; в PSW-2G6F+ это установлено в
обеих ветках отчёта. В режиме состава по умолчанию при явном включении служебные переменные добавляются
как информация, без вывода годности по суффиксам `.Ok`/`.Success`/`.Passed`.
Например, ошибка очистки ARP не равна браку, если последующее чтение устройства
и проверка MAC успешны. Реальные ошибки правил selftest остаются в отчёте.
Для `/test.shtml` версии `firmvare_vers` и `boot_vers` проверяются как hex
(например, `20d` = 525), как в Qt; исходная строка версии сохраняется.

`BuildTestReportStep` не отправляет отчет и не пишет файл; он только формирует
текст в переменной. Отправка и локальная копия выполняются отдельной нодой
`Send Test Report`.

## Отправка отчета

`SendTestReportStep`:

1. Читает построчный отчет из `ReportVariableName`.
2. Если `SaveLocalCopy = true`, сохраняет копию с замаскированной сессией. Ошибка
   записи видна в `SendReport.LocalCopyError` и не блокирует HTTP-запрос.

```text
{LocalReportsDirectory}/result-yyyyMMdd-HHmmss-fff-<id>.txt
```

3. Строит URL из `ServerBaseUrl` и `Endpoint`. Для штатного `result.json` база
   может оканчиваться на `/api` или `/api/Api.svc`. Отчёт с сессией лаунчера
   отправляется только при совпадении схемы, хоста и порта с сервером из настроек.
4. Делает POST без редиректов с побайтно совместимым multipart-телом `QTstand_old`.

```text
field: action (empty)
field: updatefile; filename: result.json; content-type: application/octet-stream
field: result; filename: result.json (empty)
```

Legacy-тело намеренно сохраняет двойную строку boundary перед полем `result` и
не добавляет стандартный закрывающий суффикс `--`: именно такие байты формирует
старый `MainWindow::set_test_result`. Стандартный `MultipartFormDataContent`
давал тот же набор полей, но сервер фактически отвечал `HTTP 200` с текстом
`error`.

5. Успех: HTTP 2xx и response начинается с `Ok`.
6. При ошибке повторяет запрос по настройке ноды. При потерянном ответе сервер
   мог успеть принять первую отправку.

Во всех вариантах 8x2Pro после успешной сборки штатный и аварийный
отчёты сразу переходят к отправке.
В комплектном профиле PSW+UPS-Box 8x2Pro аварийный отчёт после выключения
стенда использует номер текущего изделия, если тот получен. При сбое до
выдачи номера в полном прогоне, включая его автоматическую подготовку,
отчёт отправляется с результатом отказа и номером `3200001` из карточки
изделия. Причина остановки входит в отчёт. Служебный номер записывается
только в отчёт. Номер из чужого диапазона и несовпадение с выданным
номером блокируют отправку. Локальная копия в `reports` появляется после
входа в ноду отправки.
С 13.11 `FailureReportPolicy` разрешает аварийную отправку при уже выданном
номере и без служебного номера в карточке. Служебный маршрут требуется для
отказа до выдачи. Раньше общий флаг `Execution.SendFailureReport` ошибочно
требовал служебную серию и после успешного получения номера. Частичный
запуск, ручная подготовка и отмена не включают автоматическую отправку;
прежние условия RTL и автоматической подготовки полного теста сохранены.
Для 8x2Pro строка «напряжение АКБ» из подтеста при выключенном AC1 имеет
приоритет над одноимённым полем более позднего снимка.

### Диагностика отчёта под чужим серийным номером

С одного прогона сверяются три источника:

1. Фактически запущенный JSON, версия приложения и выбранная модель. Нужны
   поля `deviceType`, `cpuIdVariableName`, `useFixedSerialNumber` и
   `serialVariableName` обеих ветвей. Одинаковые видимые названия профилей
   не подтверждают совпадение настроек.
2. Журнал `test-run_*.txt`: запрос `getSerialNum` с `devType` и `cpuId`,
   строка `Serial number received`, первая ошибка и строка «Отчёт QTstand
   собран». Это разделяет неверный тип в запросе, неожиданный ответ сервера
   и замену номера на стороне графа.
3. Соответствующая копия `reports/result-*.txt`: `serial_num`, время прогона,
   `stand_id` и итог отправки в журнале. Если номер в копии правильный, а
   сервер показывает другое изделие, нужна запись обработки POST из
   серверного журнала. Ответ `Ok` не содержит номера принятой записи.

В старом профиле без справочника запрос по скопированному типу мог вернуть
номер серии 32, который проходил проверку диапазона. Нода записи MAC в
таком профиле использовала `serialOffset`, `macPrefix` и `boardVersion`
из того же графа.
Для проверки существующих записей предназначен поиск по полному SN или
MAC. Запрос выдачи `getSerialNum` может повлиять на производственные данные.

В производственном журнале от 10.11 профиль PSW+Box 8x2Pro запрашивал
`devType=PSW+UPS-Box 8x2Pro`. Сервер вернул номер серии 32. По этому номеру
граф записал MAC, передал этикетки в очередь печати и сформировал отчёт.
Отправку оператор отменил до POST.

Если у старого профиля выбранное изделие есть в справочнике, нода получения
номера сравнивает свой серверный тип с записью изделия перед запросом.
Выданный или фиксированный отладочный номер сверяется с известным диапазоном.
Для согласования серии, MAC, отчёта и этикетки в профиле включается
«Серийные номера из справочника».

## Печать этикетки

С 2026-11-24 штатный ZPL выводит короткий номер в строке `SN:` и тип +
короткий номер в Code 128: для `3300579` текст `SN: 00579`, код `03300579`.
Прежний формат с полным SN и префиксом комплектации доступен через явные
правила. Шкаф `labelCabinets[код]` выводится рядом с SN, если заполнен;
код комплектации включается в штрихкод только через `{{VariantCode}}`.
Штатный EPL, привязанный к модели с кодом этикетки, также выводит пять цифр
в тексте и тип + номер в коде. Собственные команды могут использовать `{{Serial}}` для полного номера,
`{{ShortSerial}}` для короткого, `{{SerialText}}` для настраиваемой надписи.
EPL без выбранной модели сохраняет полный SN. Явное сохранение шаблона
фиксирует показанные форматы; Apply редактора не подменяется модельным
значением по умолчанию при печати.

Штатный ZPL для TSC TE310 использует ширину 295 и высоту 154 точки при 300 dpi
(25 × 13 мм) и заданный в шаблоне левый край. `{{ZplBarcode}}` задаёт Code 128 C
для пар цифр и переключает на B для последней непарной цифры. `{{BarcodeX}}`
центрирует фактическую ширину, а проверка оставляет с каждой стороны поле
в десять узких полос. Команда с выходом Code 128 за границы не отправляется.
После обрезки текста на контрольном отпечатке восстановлены прежние
координаты и шрифты названия, MAC и серийного номера. Штрихкод начинается
на прежней строке Y=117. Для восьми цифр компактный Code 128 занимает 158
точек при модуле 2; тихие поля добавляют по 20 точек. Общий размер этикетки
и проверка полей сохранены.
`{{FitNameWidth}}` в штатном ZPL уменьшает ширину шрифта только у названия
модели по месту от координаты X до правого края с запасом в 20 точек.
Если даже минимальная ширина не подходит, приложение сообщает об этом до печати.

В профиле со справочником нода печати берёт код модели, диапазон и базу из
той же записи, что и получение номера, расчёт MAC и оба отчёта. Если номер
выдавался в текущем прогоне, ноды сверяют с ним данные. В разделе
«Этикетки» поиск по истории и ручная печать поддерживают модели из
справочника с настроенной серией.

### Инженерная вкладка «Этикетки»

Список «Изделие» строится из `TestViewModel.AllProfiles`, то есть из всей
локальной папки профилей, без фильтра плат/коммутаторов и поискового запроса.
Используется `GraphProfile.DeviceModel`, одинаковые названия объединяются.
Выбор независим от открытого графа и задаёт `{{Name}}` шаблона. Успешный
серверный поиск подставляет изделие найденного шаблона, включая изделие без
локального профиля. Каталог
шаблонов по-прежнему задаёт формат и диапазоны серийных номеров. Произвольные новые
названия не требуют списка моделей в коде. При нескольких изделиях и без
текущего выбора требуется явно выбрать название перед ручной ZPL-печатью.

`PreparedLabel` фиксирует проверенные шаблон, полный SN (с ведущими нулями в EPL),
MAC, имя принтера и количество до обращения к драйверу. `TestContext.LabelPrinting`
хранит отдельный снимок на запуск; параллельные ветви разделяют этот объект.
Cleanup его не заменяет. По завершении полного запуска `LastTestCompleted`
передаёт `LastTestLabelSnapshot` с результатом и ошибкой в `MainWindowViewModel`.
`LastTestLabelStore` атомарно сохраняет `last-test-label.json` рядом с exe;
после перезапуска вкладка восстанавливает этот снимок. Ошибка записи выводится
в лог, при этом данные остаются доступны в памяти. Не сохраняются токены,
сетевые сессии, регистры или полный словарь переменных.

«Печатать из последнего теста» использует снимок независимо от текущего
профиля, выбранного изделия и ручного ввода; принтер и количество берутся из
текущих полей. Ошибка повторной печати не удаляет снимок и не меняет результат
производственного теста. Подготовка профиля, частичный/учебный запуск, кнопки и
ручная печать не публикуют результат полного теста. Новый полный тест без
подготовленной этикетки заменяет прежний результат пустым снимком, поэтому
данные предыдущего изделия нельзя случайно повторить как последнее изделие.
При обновлении старой программы прошлый runtime-контекст не восстанавливается:
сохранение начинается со следующего полного запуска.

Тот же снимок восстанавливается в `TestViewModel` для графов и кнопок профиля.
`TestContext.LastTestLabel` получает отдельную копию при начале выполнения,
в том числе в параллельных ветвях. Нода с `UseLastTestLabel` вызывает обычный
путь RAW-печати с сохранённым шаблоном и идентификаторами; имя текущего профиля
к шаблону не применяется. При повторе очередь выбирается тем же способом,
что при обычной печати. Если имя пустое, используется очередь из снимка.
Число копий задаётся в ноде.
Диагностика `PrintLabel.SerialSource = LastTest`. У кнопки независимый контекст,
поэтому ни успех, ни отказ повторной печати не меняют исходный результат теста.

MainWindow создаёт LabelPrintingViewModel; LabelPrintingView доступен в
инженерном режиме. Выбирается шаблон из редактируемого локального каталога
`AppSettings.LabelTemplates`; исходно есть Pro, PSW-2G6F+ и EPL с серийным номером. Вводятся серийный номер, MAC, принтер Windows и количество
1–100. Используется PrintLabelStep без графа и Modbus. Повтор хранит снимок
последней успешной печати этой вкладки до закрытия приложения; количество
и принтер берутся из текущих полей. Ошибка не заменяет сохранённую этикетку.
Операции отменяемые. `IsLabelToolBusy` блокирует старт теста и подготовки.

Поле «Тестовая этикетка» показывает все шаблоны рабочего места и модели с
кодом этикетки из справочника, включая их комплектации. Для модели без своего
шаблона проба использует стандартный ZPL, для плат RTL — EPL с серийным
номером. Первый пункт использует выбранную карточку. `PrintLabelStep`
отправляет одну этикетку с нулевым SN и, если нужен, MAC `00:00:00:00:00:00`.
Эти данные подставляются локально. Повтор и снимок последнего полного теста
сохраняют данные изделия. Пустое поле «Принтер» берёт `defaultPrinterName`
из настроек в момент запуска печати.

Поле принтера во вкладке «Этикетки» и в ноде `Print Label` (включая мини-графы
кнопок профиля) — общий `PrinterPicker`: редактируемый `AutoCompleteBox`, кнопка открытия
полного списка мышью и «Обновить». `PrinterPickerViewModel` загружает список при
появлении контрола, убирает пустые/повторные имена и сортирует их. Обновление
не меняет привязанное `PrinterName`; ручной ввод, обычная печать и повтор
используют то же поле. Блокировка вкладки или редактирования графа распространяется
на ввод и обе кнопки. В настройках рабочего места тот же контрол задаёт
«Принтер по умолчанию». Ноды с флажком «Принтер из настроек» берут эту очередь
при следующем запуске, в том числе в мини-графе. Пустая настройка оставляет
очередь, сохранённую в `printerName`. Для отдельной очереди снимите флажок.
«Добавить принтер в Windows…» открывает системный раздел «Принтеры и сканеры».
При возврате в окно настроек приложение обновляет список без смены выбранного
имени. Если очередь ещё не появилась, нажмите «Обновить» после завершения
установки. Для каждого принтера можно выбрать подходящий шаблон EPL или ZPL.

`WindowsPrinterCatalog` вызывает `EnumPrintersW`, уровень 4, флаги
`PRINTER_ENUM_LOCAL | PRINTER_ENUM_CONNECTIONS`: установленные локальные очереди
и сетевые подключения текущего пользователя. Это не сканирование всей сети
и не проверка online-состояния. Вызов идёт в `Task.Run`; ожидание ограничено
10 секундами. Если нативный вызов задержался, повторное обновление ждёт тот же
worker вместо создания новых. Контрол отменяет ожидание при выгрузке; поздний
результат не применяется. При ошибке прежний список и введённое имя сохраняются.
На других ОС выводится короткое сообщение, ручное поле остаётся доступным.
Справка API: [Microsoft EnumPrinters](https://learn.microsoft.com/en-us/windows/win32/printdocs/enumprinters).

С 2026-10-30 выбор шаблона — карточки с образцами вместо списка названий.
`LabelPreview` локально разбирает команду, полученную теми же подстановками,
что использует печать. `LabelPrintContent` разделяется с `PrintLabelStep`:
полный/короткий номер, нормализация MAC и смещения EPL остаются общими.
Предпросмотр не вызывает принтер, сервер или браузер. Пустые поля заменяются
примером только в изображении и помечаются; неверные данные показывают ошибку.
Последний предпросмотр строится из `PrintLabel.SingleCommand` после успеха,
поэтому повтор не зависит от изменённых полей или каталога.

`LabelPreviewControl` рисует чёрное содержимое на белой этикетке в обеих темах.
На широком окне изображение справа от полей, на узком — ниже. В редакторе
шаблонов образец обновляется с задержкой 150 мс; закрытие останавливает таймер,
изменения до сохранения остаются черновиком.

Это приблизительное отображение, не эмулятор принтера: ZPL поддерживает `FO`,
`LH`, `A0`, `CF`, `BY`, `BC` (Code128 B/C), `FD`, `FS`, `GB`, `PW`, `LL`;
EPL — неповёрнутые `A` (шрифты 1–5), `B` (Code128 1/1B/1C), `q`, `Q`.
Шрифты заменяются экранными; поворот, QR, графика и прочие неподдерживаемые
команды перечисляются в сообщении. При явном размере видна обрезка за границей.
Размер и левый край берутся из шаблона. Если высота не задана, предпросмотр
показывает высоту содержимого. Общие шаблоны открываются в настройках и во
вкладке «Этикетки». Штатные ноды и тестовая печать моделей из справочника
берут макеты из общих настроек. Явно сохранённый шаблон ноды переносится
с профилем. Точные прежние стандартные команды обновляются при загрузке.

Синтаксис сверялся с [Zebra ZPL Programming Guide](https://docs.zebra.com/us/en/printers/software/zpl-pg/c-zpl-zpl-commands/r-zpl-bc.html)
и [EPL Programming Guide](https://www.zebra.com/content/dam/support-dam/en/documentation/unrestricted/guide/software/epl2-pm-en.pdf).

В psw_stand-dev/Printer/reportprinter.cpp найден read-only запрос
`getdevicehistorylist?findParam=serial&findVal=…`, возвращающий массив с
объектами `device`. `LabelLookupService` принимает настроенный адрес сервера,
каталог API или полный адрес этого метода. Поиск использует один параметр,
полный SN или MAC. Для короткого SN вкладка добавляет смещение выбранного
шаблона, если тот поддерживает поиск по диапазону. При пустом списке интерфейс
сообщает, что изделие не найдено. Данные ответа сверяются с запросом, а шаблон
выбирается по диапазону полного SN. Поиск только заполняет поля.
`LauncherServerClient` отправляет сессию на текущий настроенный origin
без перехода по перенаправлениям. На АПК-03 обе формы запроса получили HTTP 200
с пустым результатом для отладочных идентификаторов. Заполнение из найденной
записи проверено на имитации ответа.

### Производственная нода

`PrintLabelStep` принимает полную копию `LabelTemplateDefinition`, сохранённую
в ноде. «Этикетка ноды…» открывает встроенный редактор шаблона/команды EPL/ZPL,
подстановок, диапазона номера и необходимости MAC. Шаблон имеет приоритет
над legacy-полями и переносится вместе с профилем. Это редактор команд и полей,
не визуальный дизайнер размещения элементов.

Для старых нод **без `labelTemplate`** сохранены два режима. Обычный формат повторяет
алгоритм `RTL_v2`: читает полный номер из переменной `SerialNumber` и печатает
только его Code128-штрихкодом и обычным текстом. Значение по умолчанию — четыре
одинаковые этикетки на `TSC TE310`.

Для автономной перепечатки `UseManualSerialNumber = true` переключает источник
на поле `ManualSerialNumber`. Оно обязано быть непустым и содержать только
ASCII-цифры. Этот режим используется в импортируемом примере
`examples/profiles/manual_label_printing.json`; COM/Modbus-подключение ему не требуется.

Если `UseQtProZplFormat = false`, фактическая команда `RTL_v2` имеет формат EPL
(`N`, `q354`, `B...`, `A...`, `P1,1`) для этикетки 30x10 мм при 300 dpi и не
добавляет MAC, модель или служебные поля.

Если `UseQtProZplFormat = true`, нода воспроизводит общий `print_label` старой
Qt-программы и значения профиля `PSW+UPS-Box 8x2Pro.json`: ZPL для этикетки
25x13 мм, название `PSW+UPS-Box 8x2Pro`, MAC `C0:11:A6:20:HH:LL`, строку
`SN: SSSSS` и Code128 payload `032SSSSS`. В основном производственном профиле
нода не рассчитывает эти значения: читает `SerialNumber`, `SerialShort` и
`Dut.default_mac`, полученные предыдущими шагами. Последний MAC появляется из
post-reboot selftest и до печати сравнивается с `Dut.NewMac`; отсутствие или
несогласованность значений блокирует печать. `SetMac.Timestamp` используется
только bat-командой записи и в этикетку не попадает.

История настройки физического отпечатка до 2026-11-24 (нынешнее
центрирование и данные описаны выше): в ручном мини-профиле полный/короткий
номер и реальный MAC вводились оператором отдельно. ZPL-команда повторяется четыре раза в одном RAW-задании. После первой
физической печати штрихкод сдвинут на 30 точек влево (`^FO480,117`), чтобы
восстановить правое тихое поле; остальные поля тогда не изменялись. По последнему
уточнению оператора 2026-10-30 строка SN начинается на `^FO510,95` — по левому
краю MAC (`^FO510,70`), без центрирования. Штрихкод также
сдвинут вправо: итоговый `^FO510,117` после коррекции оператором на бумаге,
ширина Code128 B из девяти символов — 268 точек. MAC сохраняет координаты.

Legacy-поле `labelModel` хранится в ноде; без него используется Pro.
При выбранном шаблоне модель/команды определяет `labelTemplate`, а не имя профиля.

Для `LabelModel=Psw2G6FPlus` при включённом ZPL используется отдельный Qt-макет
PSW-2G6F+: тип `6`, полный серийный номер `600000..665535`, короткий SN из пяти цифр,
штрихкод `006SSSSS` на `^FO510,117` без `>:`. Старые JSON без `labelModel`
сохраняют макет Pro. Новый профиль печатает MAC из `DutAfterMac.default_mac`
после явного сравнения с рассчитанным. Макет проверен по байтам Qt; физическую
печать PSW-2G6F+ подтвердил оператор 2026-09-28. RAW-печать обоих макетов
реализована через Windows API:

- `OpenPrinter`;
- `StartDocPrinter`;
- `StartPagePrinter`;
- `WritePrinter`;
- `EndPagePrinter`;
- `EndDocPrinter`;
- `ClosePrinter`.

Ограничение: на не-Windows ОС нода возвращает ошибку `RAW-печать поддерживается только в Windows`.
Шаг ждёт ответ spooler до 30 секунд. Вызовы драйвера идут вне UI-потока. Шаг проверяет
offline-атрибут очереди, ошибки принтера, все этапы передачи и число байт.
`StartDocPrinter` возвращает ID задания; `SetJob(RETAIN)` удерживает только
это задание до чтения его финального статуса через `GetJob`.
`PRINTED` даёт `PrintLabel.CompletionStatus=Printed`; `COMPLETE` даёт
`SentToPrinter` и текст «передано принтеру; драйвер не подтверждает физический
выход этикетки». Постановка в очередь сама по себе больше не означает успех.
После завершения удержание снимается. Ошибка/таймаут/отмена вызывают DELETE,
затем RELEASE только для своего задания: на TSC один DELETE оставлял
завершённый retained job в состоянии DELETING. Последовательность проверена
на контрольном job 5, очередь очистилась. После таймаута или отмены результат
имеет статус `Unknown`. Пока вызов драйвера или очистка продолжается, приложение
отклоняет новую печать в ту же очередь. Если удаление задания подтвердить не
удалось, при следующей попытке приложение сперва проверит прежнее задание.
Когда очередь снова доступна, перед повтором всё равно нужно проверить, вышла
ли этикетка. Обработка затрагивает только задания, отправленные приложением.

На APK-03-07 2026-09-28 TSC TE310 вернул `COMPLETE`, без `PRINTED`.
Оператор подтвердил физический выход PSW-2G6F+ с SN 12447. Второй контрольный
запуск завершился успешно, job 6, 180 мс; такой статус подтверждает передачу
через Windows, но не является датчиком физического выхода этикетки.

## Справочник и шкаф на этикетке — 2026-11-11

Поставка `reference/serials/equipment-models.json` включает 79 карточек и
31 предзаполненную серию коммутаторов. Локальные изменения редактора —
`catalog/equipment-models.json` активной папки профилей; пути показаны в
«Справочник изделий». Поиск учитывает трёхзначный код этикетки.
Для PSW-2G8F+Box (`026`) тип `PSW-2G8F+Box`, номера `2600001–2665535`,
база `2600000`, MAC `C0:11:A6:1A`; источники расчёта указаны в `reference/README.md`.
Кнопка «Заполнить из поставки» заполняет только поля серии выбранной карточки.
Она не создаёт тип на сервере и не запрашивает новый номер.

`EquipmentModel.labelCabinets` хранит короткую подпись шкафа по коду
комплектации, отдельно от `labelVariants`. Карточка проверяет наличие
соответствующей комплектации и отсутствие команд принтера в подписи.
`LabelPrintContent.ForModel` берёт подпись в снимок макета; повторная печать
использует сохранённую команду. Тестовая печать вариантов также использует
их собственный код модели и комплектации.

Штатные ZPL добавляют `{{CabinetField}}` и заменяют ширину строки SN на
`{{SerialTextWidth}}`. Без шкафа результат команды совпадает с прежним;
при наличии шкафа место резервируется справа в строке SN. Ширина его поля
`CabinetWidthDots` (84) и высота `CabinetFontHeightDots` (20) редактируются в
общих макетах. Если подпись не помещается при минимальной ширине шрифта,
печать останавливается с указанием исправить подпись или макет.
Координаты и данные штрихкода не меняются. Автообновление касается только
точных штатных команд из списка миграций; собственные команды сохраняются.

Для кириллицы поле шкафа передаётся как UTF-8 hex `^CI28/^FH`, несмотря на
CP1251 транспорта. Основание: [Zebra ^CI](https://docs.zebra.com/us/en/printers/software/zpl-pg/c-zpl-zpl-commands/r-zpl-ci.html)
и [Zebra ^FH](https://docs.zebra.com/us/en/printers/software/zpl-pg/c-zpl-zpl-commands/r-zpl-fh.html).
Предпросмотр разбирает те же байты. Наличие глифов в шрифте принтера и
физическую читаемость следует подтвердить пробой на рабочем принтере.
