## Форматы этикеток и название изделия — 2026-10-30

Во вкладке «Этикетки» два встроенных ZPL-варианта объединены в карточку
«ZPL · Изделие, MAC, SN», EPL остаётся отдельной карточкой полного серийника.
Параметры вариантов (диапазон, префикс, координаты) сохранены в каталоге;
выбор варианта идёт по изделию активного профиля, затем по полному серийнику.
Пользовательские шаблоны остаются отдельными карточками. Редактор шаблонов
по-прежнему позволяет настроить оба варианта отдельно.
Нода имеет выбор ZPL/EPL; переключение заменяет её выбранный шаблон стандартным.
`TestContext.DeviceModel` передаётся в основной запуск, кнопки и параллельные
ветви. Подстановка `{{Name}}` берёт название изделия из профиля; без него
используется имя шаблона. Название проверяется до формирования команд.
Повтор ручной печати хранит снимок названия и макета, смена профиля его не меняет.
JSON профилей и сохранённые шаблоны не переписываются. Физическая печать
на Windows требует проверки на стенде.


# HTTP, сеть, отчеты и печать

## Панель ICMP-пинга — 2026-10-30

`PingMonitorSettings` хранится в профиле и не связан с IP из AppSettings или
нод selftest/DataTest. Пользователь задаёт адрес, период, таймаут и отображение.
Панель не использует TCP/HTTP как замену ICMP и не влияет на результат графа.

`Services/Network/IcmpPingProbe` использует `System.Net.NetworkInformation.Ping`.
DNS-разрешение и ответ ограничены общим таймаутом и токеном отмены.
Успешный ICMP-ответ содержит RTT; отсутствие ответа и ошибка выполнения
(например DNS/разрешений) отображаются раздельно. Для DNS используется первый
разрешённый адрес. Процесс `ping -t` приложение не запускает.

`PingMonitorViewModel` ведёт один последовательный цикл. Период считается между
началами запросов; если запрос длится дольше периода, следующий начинается после
его завершения. Параллельных запросов и очереди пропущенных периодов нет.
При смене адреса/параметров старый цикл отменяется, новый ждёт его завершения.
Номер поколения отбрасывает поздний ответ старого профиля. Показания сбрасываются
при смене профиля, выключении и остановке опроса; изменение только видимости
не прерывает текущий цикл.

Монитор включается жизненным циклом главного окна и выключается при Dispose VM.
Обучение и редакторы графов кнопок не запускают пинг. Опрос не требует COM
и продолжается во время подготовки, теста, паузы и переключения рабочих режимов.
Его результаты не добавляются в поток логов теста.

## Имена и привязки сетевых карт — 2026-10-28

В «Сеть → Названия, порты и пары…» NetworkPlan.Addresses хранит Name, Role,
Pair, TestMbps, IncludeInDataTest вместе с IPv4/временным IPv4. Старые настройки
читаются с пустыми именами и отключённым экспортом в DataTest. Сохранение плана
не меняет ОС или ноды. «Взять пары из плана сети» в Run Data Test явно копирует
выбранные пары; каждая содержит ровно два адреса с одинаковой скоростью 1–1000.
Некорректный план не заменяет параметры ноды. Профиль затем нужно сохранить.

«Сохранить привязки» записывает ID адаптеров без изменения IP. Выбор занятой карты
обменивает две привязки. «Название карты Windows…» вызывает netsh по текущему
имени карты, найденной по ID; IP не меняется. Права администратора нужны для
изменения ОС. Имена линий плана независимы от системных имён карт.

«Определить карту по кабелю» сравнивает два снимка линков по стабильному ID.
При включённом DUT оператор отключает один кабель, сравнивает, сверяет MAC и
подключает обратно. Несколько изменений не дают однозначного соответствия.
Номер физического порта и тип разъёма не выводятся автоматически из IP/скорости.

## Исправление физических образцов этикеток — 2026-10-30

После фото образцов с TSC TE310 в стандартном EPL явно задано `ZB`:
этикетка выходит в том же направлении, что ZPL. `BarcodeType` выбирает
Code128 C для чётного количества цифр и B для нечётного, без изменения
самого номера. `BarcodeX` рассчитывается по фактической ширине символов,
включая старт, контрольную сумму и стоп. Модуль берётся из EPL-команды B;
`TextX` учитывает шрифт A, множитель и `PrinterDpi` (203 или 300, по умолчанию 300).
Эти параметры доступны в редакторе шаблонов. В Pro строка SN выровнена
по центру блока шириной 260 точек с началом X=494 (центр X=624).
Штрихкод Pro перенесён с X=480 на X=501, затем по повторному образцу
оператор попросил ещё немного вправо: X=507 (+6 точек, около 0,5 мм),
затем итоговый X=510 (+3 точки, около 0,25 мм) по образцу SN 00002.
Ширина штрихкода — 246 точек, центр X=633; строка SN остаётся с центром X=624.
Координата — редактируемое значение шаблона, не условие по модели в коде.

Предпросмотр учитывает однострочное выравнивание `^FB` и размеры EPL-шрифтов
при выбранном dpi; этикетка показывается в положении для чтения независимо
от направления подачи ZT/ZB. Автообновление старых стандартных команд задано
в `Assets/label-template-upgrades.json`: при загрузке настроек и снимков в
профилях заменяются только точные совпадения ID, языка и прежней команды.
Имена, размеры и параметры серийников сохраняются; пользовательские команды
не заменяются. Сам файл профиля изменяется только при сохранении пользователем.

Справочники команд: [EPL, A/B/Z](https://cpws.zebra.com/cpws/docs/eltron/epl2/EPL2_Prog.pdf),
[ZPL, Field Block](https://cpws.zebra.com/cpws/docs/zpl/zpl-zbi2-pm-en.pdf).

## Редакторы сетевого плана и этикеток — 2026-10-27

«Сеть → Изменить план сети…»: произвольное число строк, основные
и временные IPv4, общая маска. Проверяются дубликаты, маска, адрес сети и broadcast.
Сохранение плана не меняет ОС; применение — отдельной кнопкой. Привязки хранятся
по ID карт. При переходе на новую подсеть разрешён прежний сохранённый адрес
той же карты; неизвестные служебные адреса блокируются. Автоподбор по схеме
6+2+2 удалён. Адреса в нодах DataTest нужно согласовать с планом вручную.

«Этикетки → Шаблоны этикеток…» позволяет создавать, копировать, удалять и
редактировать шаблоны ZPL/EPL, команду принтера, ширину, код изделия,
диапазон серийников, префикс штрихкода и требование MAC.
Подстановки: Name, Serial, ShortSerial, Mac, Barcode, WidthDots, BarcodeX, TextX, BarcodeType
в двойных фигурных скобках. Пересекающиеся диапазоны поиска запрещены.
Исходные три шаблона — данные Assets/label-templates.json; рабочий каталог
хранится в AppSettings.LabelTemplates. Новые модели не требуют веток в коде.
В ноде «Выбрать / настроить шаблон…» сохраняет независимую копию в профиль.
Повтор последней этикетки использует снимок шаблона и данных последней успешной
печати. Проверка реального сервера, принтера и изменения IP в этом изменении
не выполнялась.


## Надёжность редактора сети — 2026-10-27

`NetworkSetupViewModel` хранит черновик привязок по ID независимо от обновляемых
объектов адаптеров. Очистка строки и отсутствие карты сохраняются при обновлении.
Занятая карта обменивается с прежней картой строки; валидатор проверяет результат
до применения. Взаимная блокировка настройки сети и запуска/подготовки теста
проходит через `TestViewModel.IsNetworkSetupBusy`. Журнал содержит прогресс
применения; после результата обновляется фактическое состояние.
Каждая команда netsh ограничена 30 секундами; при тайм-ауте процесс завершается
и показывается ошибка. Автоматического отката адресов нет: после частичного
сбоя следует обновить состояние и повторить применение сохранённой привязки.

## Обновление 2026-10-14: платы и защита отчётов

Платы используют существующие Build/Send Test Report и серверный клиент TB.
FTServiceUtils не подключён. В новых профилях type серийников RTL-SW/RTL-POE;
производственный сервер с этими параметрами пока не проверен. Серийники не подменяются
выдуманными значениями. Отчёт после отказа отправляется лишь при наличии SerialNumber,
после снятия питания, и не дублирует уже отправленный отчёт. Ранний отказ SW без номера
остаётся в журнале. Измерения диапазонов можно явно включить через ReportName.

Этикетка платы: прежний EPL 30×10 мм/300 dpi, полный serial+Code128, одна копия явно.
В SW включена, в PoE выключена (в исходнике не была обязательным финальным этапом).
Есть отдельный профиль ручной печати. ZPL-макеты коммутаторов сохранены.

Локальная копия отчёта теперь скрывает поле session; исходный wire payload не меняется.
HTTP redirect при отправке выключен, чтобы не перенести сессию на другой адрес.
Из Chrome selftest убраны --no-sandbox и wildcard allowed origins. Локальный TCP CDP
по-прежнему требует отдельного усиления; см. отчёт аудита, не считать это полной защитой.


## Совместимость с лаунчером RTL_v2 (2026-10-01)

Проверены `App.xaml.cs` и `Infrastructure/Firmware/DeviceSerialNumberService.cs`
репозитория [RTL_v2](https://github.com/kotyasmol/RTL_v2): аргументы имеют порядок
`sessionId userName`, запрос серийника использует `User-Agent: ftstand` и
`Cookie: SGUID=session_id=<sessionId>&login=`. Поле login в cookie остаётся пустым,
как в RTL. Имя отображается в окне и доступно в контексте как `OperatorName`.

`LauncherServerClient` добавляет эти заголовки только к `getSerialNum` на origin
настроенного `AppSettings.ServerBaseUrl`; другой адрес в ноде не получает cookie.
Автоматические redirect у этого отдельного клиента отключены. DUT/selftest
сессию не получают. Передача сессии в legacy-отчёте сохраняется без изменения
протокола: строка `session=true=...`. Тестовые значения сессии не зашиты в код.

У лаунчерного контракта из RTL нет роли, endpoint проверки сессии или загрузки
профилей. Эти возможности не имитируются. Реальная выдача номера/приём отчёта
с новой интеграцией требуют отдельной проверки на корпоративном сервере.

Эта страница описывает инфраструктуру, которой пользуются HTTP-, сетевые, отчетные и печатные ноды.

Модели без `Pro` относятся к старым коммутаторам; модели с `Pro` — к новым.
Для `PSW-2G6F+` selftest запрашивается с `/test.shtml`, MAC записывается по
UDP. Для `PSW+UPS-Box 8x2Pro` selftest читается через LuCI `deviceinfo`, а
MAC записывается через WinSCP. Обе страницы находятся на `192.168.0.1`,
поэтому доступность одного только корневого URL не проверяет нужный endpoint.

## HttpRequestService

`HttpRequestService` реализует `IHttpRequestService`:

```csharp
Task<HttpRequestResult> GetAsync(string url, TimeSpan timeout, CancellationToken cancellationToken)
```

Что делает:

1. Проверяет, что URL не пустой.
2. Проверяет, что URL абсолютный и схема `http` или `https`.
3. Создает linked timeout token.
4. Делает GET через `HttpClient`.
5. Возвращает `HttpRequestResult.Success` или `Failure`.

`HttpRequestResult` содержит:

| Поле | Назначение |
|---|---|
| `IsSuccessStatusCode` | HTTP 2xx. |
| `StatusCode` | Код ответа или `null`. |
| `Body` | Тело ответа. |
| `ErrorMessage` | Нормализованная ошибка. |
| `Elapsed` | Время выполнения. |

## Selftest HTTP

`SelfTestCheckStep` имеет особую логику получения страницы:

- до общего timeout раз в `PollIntervalMs` параллельно проверяет ICMP и TCP-порт URL;
- пока DUT не отвечает, Chrome/Edge не запускается;
- после появления DUT запускает одну фоновую browser-попытку с чистым профилем
  и передаёт ей исходный URL прямо в строке запуска;
- ждет завершения загрузки по `document.readyState == complete`, затем полные 10 секунд;
- один раз читает DOM через DevTools Protocol как аналог Selenium `driver.PageSource`
  и закрывает браузер этой попытки;
- если снимок не содержит `<selftest>...</selftest>` или совместимый
  `<settings>...</settings>` с `default_mac`, ждет `PollIntervalMs` и пробует снова.

Каждая browser-попытка намеренно повторяет старую отдельную Selenium-утилиту: один `GoToUrl`,
`Thread.Sleep(10000)`, один `PageSource`. В браузерном режиме нет POST-логина и
обычного HTTP fallback; каждая попытка повторяет именно `Url` ноды. Если
профиль старого коммутатора задал `/test.shtml`, нода открывает его напрямую.
С 2026-10-22 `BrowserAttemptCoordinator` допускает одну браузерную попытку
на всё приложение, включая параллельные графы и повторные запуски. Ожидание
очереди входит в таймаут попытки и отменяется общим токеном.

На Windows `WindowsProcessJob.Start` создаёт Chrome приостановленным, включает
его в Job Object с `KILL_ON_JOB_CLOSE` и только затем продолжает выполнение.
Дочерние процессы принадлежат той же группе. После попытки Chrome получает
`Browser.close` (до 2 секунд), затем оставшиеся процессы группы завершаются
через `TerminateJobObject`; до 3 секунд проверяется `ActiveProcesses == 0`.
Эта проверка выполняется и после выхода главного Chrome. Прежний `taskkill`
по PID родителя удалён: уже вышедший родитель не доказывал завершение детей.
Закрытие job handle также останавливает принадлежащие ему процессы при
закрытии приложения. Посторонние экземпляры браузера не затрагиваются.

Ошибка подтверждения завершения блокирует следующие браузерные запуски
до перезапуска приложения. Отмена тоже ожидает очистку; исключение логгера
не прерывает закрытие. На macOS/Linux сохранено завершение дерева через
`Process.Kill`. Уникальный временный профиль удаляется отдельно в фоне
после очистки. Все браузерные операции идут вне UI.
В логах отдельно отмечаются запуск, DevTools, готовность документа, чтение DOM, выход Chrome
и обнаружение XML; таймаут включает название этапа. Это диагностика Windows-стенда,
а не подтверждение устранения зависания без повторного аппаратного прогона.
Старые сохраненные профили с `TimeoutMs` до `160000` для DUT selftest автоматически получают
эффективный таймаут `180000`. Стартовая проверка рабочего профиля ждёт DUT и
страницу до пяти минут (`300000`), а последующие selftest-проверки — до трёх
минут (`180000`), проверяя готовность каждые пять секунд.
В Windows-комплекте 1.0.0 selftest сначала ищет
`Browser/chrome-win64/chrome.exe` относительно каталога приложения, независимо
от рабочей папки лаунчера. Если встроенного браузера нет, сохраняется поиск
установленных Chrome/Edge. Перемещение папки комплекта не ломает этот поиск.

Для headless Chrome/Edge используется внутреннее чтение DOM через DevTools Protocol после ожидания
загрузки страницы, по смыслу аналогично старому Selenium `driver.PageSource`, но без внешней утилиты.
`PollIntervalMs` задает паузу между полными браузерными попытками.
Извлечение декодирует HTML-, URL- и JS-экранирования, потому что нужный XML может лежать в скрытом DOM/скриптах LuCI.
Проверка `ValidationRules` пишет в лог отдельные строки по каждому параметру и сохраняет
`SelfTest.CheckedRuleCount`, `SelfTest.FailedRuleCount`, `SelfTest.ValidationSummary`.

Операционная причина трёхминутного ожидания, нерабочие альтернативы и порядок диагностики
зафиксированы отдельно: [[18 - Selftest и загрузка DUT]].

До извлечения XML каждая завершённая попытка пишет исходный DOM браузера
(либо тело HTTP-ответа) в обычный журнал на уровне Info: URL, номер попытки,
число символов и полный текст частями по 8192 символа без обрезки.
Пустой ответ отмечается `<empty>`, ошибка чтения выводится отдельно.
Сохраняются также страницы входа, ошибки, скрипты и скрытые элементы,
даже если `selftest`/`settings` отсутствуют. Сообщения входят в файловый
журнал прогона при включённой записи в файл; в UI действует обычное
ограничение истории в 1000 записей.
HTTP-код показывается только если он известен: браузерный DOM не выдаётся за HTTP 200.

Извлечённый XML доступен в `TestContext` текущего запуска как `SelfTestRaw`.
Файл `selftest.txt` больше не создается: он был legacy-артефактом старой консольной утилиты.
Полный перечень исторических XML-полей, формула фактического количества,
legacy-алиасы и служебные ключи описаны в [[19 - Поля тестовой страницы DUT]].

`FailOnError` в selftest-нode не переключает результат на `True`; при ошибке step возвращает `False` всегда. Разница только в том, выставляется ли `context.HasCriticalError`, который потом влияет на поле `test_result` в отчете.

## API устройства

Для новых графов DUT API использует две универсальные ноды:

| Нода | Назначение |
|---|---|
| `Read HTTP Variable` | Один GET, строгий разбор ответа и запись свежего значения. |
| `Wait Variable Until` + `HttpGet` | Повторный GET до совпадения значения или обязательного таймаута. |
| `Wait Variable Until` + `SelftestSnapshot` | Повторный снимок всей тестовой страницы и сравнение целевого поля. |

Обе ноды принимают произвольные `BaseUrl`, `Endpoint`, output variable и
`ResponseType`: `Integer`, `Number`, `Boolean`, `String`. `Endpoint` может быть
относительным путем или полным HTTP/HTTPS URL. Перед запросом старое output
value удаляется, поэтому оставшееся от selftest значение не может пройти как
результат свежего чтения.

Рабочий UPS-алгоритм:

1. На SIMBAT выполняется `slave 17 / 1706 ← 1` с read-back-проверкой.
2. `SelftestSnapshot` ждёт `Dut.akb_voltage` в диапазоне `20..27` В при
   включённом AC1.
3. На PS-3 выполняется `slave 23 / 1200 ← 0` с проверкой: AC1 выключен.
4. Новый снимок снова должен дать `akb_voltage = 20..27` В. Доступная страница
   и нормальное напряжение при выключенном AC1 подтверждают работу от АКБ.
5. AC1 возвращается записью `slave 23 / 1200 ← 1` с проверкой.
6. Третий свежий снимок должен дать `akb_voltage = 20..27` В при работе от сети.
7. Имитатор отключается записью `slave 17 / 1706 ← 0` с read-back-проверкой.

Все три ожидания используют `SelftestSnapshot`, `ComparisonType = Number` и
диапазон `ExpectedValue = 20..27`; request timeout `30000` мс, общий timeout
`160000` мс, интервал `5000` мс и `FailOnTimeout = true`. Фиксированных
задержек нет: старое `Dut.akb_voltage` удаляется, снимается новая страница, а
значение вне диапазона приводит к следующей попытке. После отключения SIMBAT
диапазон не проверяется, потому что требования к напряжению в этом состоянии
не определены.

Предыдущие варианты UPS-графа опирались на артефакты старого оборудования:
тракт PS-3 `1210`, `ups_rez`, `/api/getUpsStatus` и косвенные проверки
`1707/1708`. В актуальном стенде подключением имитатора управляет записываемый
регистр SIMBAT `1706`. Поле `akb_det` на фактической прошивке не меняется при
`1706 = 1`, поэтому признаком исправной батарейной цепи служит
`akb_voltage = 20..27` В. Исторические API-ноды и специализированные poll actions удалены
2026-10-01. Для скалярного API используйте `Read HTTP Variable` или
`Wait Variable Until` + `HttpGet`, явно задавая endpoint и тип ответа.
Автоматического fallback между `/api/isUPS` и `/api/isUps` больше нет;
нужный регистр пути определяется прошивкой DUT. Профили со старыми типами
или режимами отклоняются при импорте без изменения открытого графа.

## Получение серийного номера

`GetSerialNumberFromServerStep` строит URL двумя способами.

Если `ServerBaseUrl` похож на полный endpoint:

```text
https://server/api/api.svc/getSerialNum
```

то добавляется только query:

```text
?devType=...&cpuId=...
```

Если `ServerBaseUrl` - хост или базовый URL:

```text
server.local
http://server
```

то строится:

```text
http://server/api/api.svc/getSerialNum?devType=...&cpuId=...
```

Также можно указать `http://server/api` или `http://server/api/Api.svc`: нода
достроит только недостающую часть пути и не создаст ошибочный `/api/api/api.svc`.

Плейсхолдеры `SERVER_BASE_URL`, `http://SERVER_BASE_URL` и `server-address`
не отправляются в DNS как реальные хосты. При создании step из GUI они заменяются
общей настройкой `Server base URL`; если настройка пустая, нода завершается
понятной ошибкой `ServerBaseUrl не задан`.

Если `CpuIdVariableName` задан, нода требует непустую переменную CPU ID до
сетевого запроса. Имя ищется без учета регистра, чтобы `Dut.cpu_id` работал и с
XML-тегом `CPU_ID`. Запрос без `cpuId` остается доступен только при явно пустом
`CpuIdVariableName`, как в низкоуровневом методе старого Qt-стенда.

Перед запуском ноды прежние `SerialNumber`/`NetTest.SerialNumber` удаляются.
Серийник считается валидным только как положительное целое число в plain text
или JSON scalar; случайная последовательность цифр в HTML/тексте не принимается.
Для диагностики сохраняются URL, CPU ID, число попыток, последний HTTP status,
elapsed, raw response и текст ошибки.

Производственная ветка намеренно повторяет `TestThread::getSerialNumber` и
`MainWindow::get_serial_num` из `psw_stand-dev`: сразу вызывает `getSerialNum`
с `devType` и `cpuId`. Отдельный legacy endpoint `getExistsSerialNum` не является
частью этой цепочки. Стенд показал, что интерпретация его положительного ответа
как серийника коммутатора подставляет CPU ID в `SerialNumber`, поэтому такой
предварительный lookup запрещён.

Для стендовой отладки есть явный режим `UseFixedSerialNumber`. В нём серверный
endpoint не вызывается ни при каких условиях, а в `SerialNumber` и
`NetTest.SerialNumber` записывается `FixedSerialNumber`. В рабочем PSW-профиле
режим выключен и фиксированное значение отсутствует: используется реальный
production-запрос по `Dut.cpu_id`, а источник результата —
`SerialNumberSource = Server`.

## Set Pro MAC

`SetProMacStep` заменяет неподходящую для Pro-коммутаторов legacy UDP-команду.
Он запускает предоставленный рабочий `set_mac_pro.bat` с тремя аргументами:

1. полный MAC из `Dut.NewMac`, нормализованный как `AA:BB:CC:DD:EE:FF`;
2. точное имя модели/`boardversion`, в рабочем профиле `PSW+UPS-Box 8x2Pro`;
3. текущий Unix timestamp в секундах.

Bat-файл через `WinSCP.com` подключается к `192.168.0.1` и выполняет команды
прошивки: `fw_setenv ethaddr`, `fw_setenv boardversion`, `macset.sh` и запись
`RTC_TIMESTAMP`. Секреты подключения остаются внутри поставляемого bat-файла и
не переносятся в C# или JSON-профиль.

Нода работает только в Windows. Относительный `BatchPath` ищется в текущей
папке и рядом с `TestBuilder.exe`; абсолютный путь также поддерживается.
Штатный `TestBuilder/set_mac_pro.bat` включён в проект и копируется рядом с exe
как при сборке, так и при publish. Сам bat ищет `WinSCP.com` в соседней папке
`WinSCP`, в `PATH` и в стандартных папках установки. При отсутствии WinSCP он
завершается с понятной ошибкой без интерактивного `pause`.

В `TestBuilder/WinSCP` поставляется официальный portable WinSCP 6.5.7 вместе
с лицензией. Папка целиком копируется в build/publish, поэтому штатный bat сразу
находит `%~dp0WinSCP\WinSCP.com`; установка WinSCP на стендовый ПК не нужна.

stdout/stderr читаются параллельно в OEM-кодировке, а вызов полностью
асинхронный, поэтому ожидание WinSCP не блокирует UI. По таймауту завершается
всё дерево процессов.

Успешным считается только сочетание exit code `0` и маркера `SUCCESSFUL` в
stdout рабочего bat-файла. Ненулевой код, отсутствие маркера, таймаут или
ошибка запуска ведут по `False` при `FailOnError = true`. Диагностика доступна
в `SetMac.Started`, `SetMac.TimedOut`, `SetMac.ExitCode`, `SetMac.StdOut`,
`SetMac.StdErr` и `SetMac.Error`; фактические аргументы — в `SetMac.Mac`,
`SetMac.BoardVersion`, `SetMac.Timestamp`, `SetMac.BatchPath`.

Успех процесса означает, что WinSCP принял команды, но не доказывает сохранение
MAC. Рабочий граф после этого перезапускает DUT, очищает ARP, получает новый
selftest и сравнивает `Dut.default_mac` с `Dut.NewMac`.

## Clear ARP Cache

`ClearArpCacheStep` очищает ARP-кэш Windows перед сетевыми обращениями к DUT.
Это нужно, когда устройство перезагрузилось, сменило MAC или стенд быстро
переключает платы с одинаковыми IP: Windows может помнить старую связку
`IP -> MAC`, и запросы уйдут не на то устройство.

По умолчанию step запускает поставляемый рядом с exe `arpd.bat`, затем команду
`arp -d *`. Относительный `arpd.bat` ищется также в `AppContext.BaseDirectory`.
Старое значение аргументов `-d` нормализуется в `-d *`.
На Windows перехваченные stdout/stderr читаются в OEM-кодировке текущей
системы, а не как UTF-8; русский stderr `arpd.bat` попадает в лог без mojibake.
Непустой stderr считается ошибкой даже при exit code `0`, поэтому отсутствие
прав администратора больше не сопровождается ложным сообщением об успешной
очистке. При `FailOnError = false` ошибка по-прежнему только диагностическая.

Stdout и stderr читаются одновременно с работой процесса, чтобы заполненный
буфер не блокировал завершение. При отмене или таймауте step завершает дерево
процесса и ограниченно ждёт его выхода и чтения потоков. Отмена пробрасывается
после этой очистки; невозможность завершить процесс считается ошибкой даже
при `FailOnError = false`. Это позволяет дождаться ARP-ветви перед общим
cleanup параллельного графа. Проверки локального процесса — VER-049;
реальный Windows ARP этой проверкой не подтверждён.

## Обновление ПО старого PSW

`UpdatePswFirmwareStep` применяется в профиле PSW-2G6F+ после первой
`/test.shtml`. Сравнивает `Dut.firmvare_vers` с целью `0.2.13` (525);
значение `20c` читается как hex 524 и означает 0.2.12; `208` читается
как hex 520 и означает 0.2.8; целевой код — `20d`. В профиле сейчас
`forceUpdate=false`: версия 0.2.13 или новее пропускает загрузку. При ручном включении этого
параметра разрешается откат с более новой версии; равная всё равно пропускается.
До первого HTTP-запроса проверяются путь, имя и расширение `.img`; SHA-256
по просьбе оператора не проверяется. Затем выполняются
`GET /clear.shtml`, пауза 10 с, multipart POST `/mngt/update.shtml` с полем
`updatefile`, пауза 10 с, `GET /mngt/update.shtml?Update=Update`, пауза 40 с,
повторный selftest и сравнение новой версии с минимумом 0.2.13. При
`forceUpdate=true` требуется точное совпадение. POST использует
multipart-разметку исходного Qt-приложения. При провале шага тест останавливается.
После повторного selftest старая переменная версии удаляется перед чтением,
а фактический код версии записывается в лог.
Ответы загрузки и подтверждения выводятся в `[FW]` с начала и конца HTML:
HTTP 200 без изменения версии не считается успешной прошивкой.
Это протокол старого PSW; к Pro он не применяется. Стендовый лог 2026-09-23
подтвердил установку 0.2.8 (`208`). Подробный порядок и текущий Sensor1:
[[20 - PSW-2G6F+ тестирование]].

## DataTest через SharpPcap

Разбор стендового инцидента и порядок повторной диагностики:
[[22 - Инцидент сетевых карт 2026-09-28]].

Сетевой план рабочего места редактируется во вкладке «Сеть».
Число строк, названия, роли, IPv4, временные адреса, маска, пары и скорости
настраиваются. Исходный план `.2`–`.11` не является обязательным для всех моделей.
Привязка IP → ID адаптера хранится локально; смена имени Windows не меняет ID.

Нода DataTest сама адреса не назначает: использует сохранённую таблицу активных
пар. В интерфейсе ноды можно добавить/исключить пару и задать скорость отдельно.
Копирование из сетевого плана создаёт снимок; последующее изменение плана не
меняет граф. Неактивные пары сохраняются в `DisabledPortsText`.

Назначение IPv4 и переименование адаптеров — отдельные команды интерфейса,
для Windows нужны повышенные права. Перед перестановкой основных IP приложение
применяет уникальные временные адреса из плана. Ошибки показываются с результатом
команды; изменение плана и выбор карты сами по себе не выполняют `netsh`.
Физический линк, кабели и согласованная скорость проверяются отдельно.
Прежнего автоматического правила «шесть 100 Мбит/с + два гигабитных + два резерва»
в текущем редакторе нет. Подробные операции — [[03 - Работа с приложением]].

При DataTest имена, MAC и линк обеих карт выводятся в журнал. Если IP назначен
нескольким картам, тест отказывается выбирать произвольную. Историческая
раскладка APK-03-07 в [[22 - Инцидент сетевых карт 2026-09-28]] описывает тот
прогон и не должна применяться автоматически к другой модели/раскладке.

`RunDataTestStep` делает программный сетевой тест.

Поддерживаемые режимы:

- `SoftwarePcap`;
- `Pcap`;
- `Software`;
- `TYPE_SOFT_GEN`.

Все эти значения ведут в одну текущую реализацию software/pcap. Если указать другой режим, step вернет ошибку с рекомендацией использовать `SoftwarePcap`.

Основные этапы:

1. Получить список `CaptureDeviceList.Instance`.
2. Последовательно, по одной строке `PortsText`, найти receive/send сетевые карты по IP.
3. Получить MAC-адреса адаптеров.
4. Построить Ethernet/IP/UDP packet заданного размера с ID запуска и sequence.
5. Открыть receive в promiscuous с буфером 16 МиБ, read timeout 20 мс и snaplen, равным размеру тестового кадра. В Windows также задать kernel buffer 16 МиБ и MinToCopy 64 КиБ: пакетная доставка уменьшает потери захвата при паузах планировщика. Для Windows выше 100 Мбит/с send открывается с NoCaptureLocal и пустым capture filter; до 100 Мбит/с сохраняется promiscuous/max responsiveness. Таймаут чтения короче окна ожидания хвоста 75 мс.
6. Поставить capture filter:

```text
ether src {OutMac} and ether dst {InMac}
and udp src port {UdpPort} and udp dst port {UdpPort}
and src host {OutIp} and dst host {InIp}
```

7. Сделать warmup с отдельным ID и дождаться очистки хвоста capture.
8. При наличии native send queue до 100 Мбит/с использовать один
   синхронизированный отправитель с частями по 500 мс. В Windows выше
   100 Мбит/с использовать два независимо открытых pcap handle на одной
   карте: каждый отправляет половину кадров несинхронизированными native
   очередями по 100 мс целевой нагрузки. Разные чётные/нечётные sequence
   исключают пересечение потоков. Общие часы ограничивают темп между
   частями и общую длительность; итоговая скорость учитывает реальное
   время обоих отправителей, включая задержки подготовки и драйвера.
   `DataTestSendCoordinator` отменяет соседнюю очередь при ошибке или
   неполной отправке и дожидается обеих до закрытия handle.
   У каждого отправителя максимум две ожидающие части плюс по одной
   активной и подготавливаемой; память ограничена независимо от длительности.
   Если native send queue недоступна, используется paced `SendPacket`.
9. Считать только уникальные sequence текущего ID; отдельно учитывать duplicates,
   unexpected packets и Npcap capture drops.
10. Посчитать RX/TX/loss/tx deficit и скорости на линии с учетом 24 байт overhead
    на кадр: preamble/SFD 8, FCS 4, inter-packet gap 12.
11. Сравнить loss с `AllowedLossPercent`, а deficit генератора — с отдельным
    `AllowedTxDeficitPercent`.
12. При инфраструктурной ошибке генератора/захвата повторить направление один раз.
    Потеря при нормальном TX и без capture drops считается результатом DUT и не
    скрывается retry.
13. Если `Bidirectional = true`, поменять send/receive местами и проверить обратное
    направление. Затем закрыть карты и выдержать `InterPairDelayMs`.

Пары никогда не запускаются параллельно. Глобальный и парный target ограничены
`100 Mbps` по умолчанию; `AllowGigabit=true` разрешает до `1000 Mbps`.
Legacy `1000` без флага при загрузке профиля по-прежнему мигрирует на `100`.
Для кадра 1514 байт target 100 Mbps соответствует примерно 8127 кадрам/с,
а 1000 Mbps — 81274 кадрам/с с учётом физического overhead Ethernet.
Настройки не меняют скорость NIC/SFP: известный линк ниже target блокирует тест.
Реальная способность ПК генерировать/принимать гигабит проверяется метриками
TX deficit и capture drops; программные тесты не подтверждают line rate на стенде.

### Значение метрик

| Метрика | Значение |
|---|---|
| `target` | Требуемая скорость на физической Ethernet-линии. |
| `expected` | Сколько кадров должно пройти за `DurationMs` при target. |
| `TX` | Сколько нумерованных кадров генератор подтвердил как отправленные. |
| `RX` | Сколько уникальных кадров этого запуска поймано на карте назначения. |
| `loss` | `(TX - RX) / TX`; характеризует путь через DUT, если capture drops равны нулю. |
| `tx deficit` | Насколько фактическая TX wire speed ниже target; характеризует генератор/ПК. |
| `tx speed` | Фактическая скорость отправки на линии с Ethernet overhead. |
| `rx speed` | Фактическая скорость уникальных принятых кадров на той же временной базе. |

### Формат PortsText

```text
port0-1,192.168.0.2,192.168.0.3,100
port2-3,192.168.0.4,192.168.0.5,100
port4-5,192.168.0.6,192.168.0.7,100
port6-7,192.168.0.8,192.168.0.9,100
port8-9,192.168.0.10,192.168.0.11,100
```

Поля:

1. Название пары.
2. `InIp` - receive/destination IP.
3. `OutIp` - send/source IP.
4. Опциональный target bandwidth для конкретной пары.

## Сбор отчета

Состав служебных строк и автоматически добавляемых полей selftest задан
в коде; полноценной настройки состава, названий и порядка полей через UI нет.
Проблема отложена для обсуждения, решение не выбрано:
[[15 - Backlog и пожелания#BL-011 — Настройка состава серверного отчёта без изменения кода]].

`BuildTestReportStep` повторяет формат `QTstand_old`:

```text
test_result=true=1
stand_id=true=123
serial_num=true=3200123
session=true=<session-id>
Тип проверки=true=production
самотестирование=true=true
напряжение АКБ=true=24.5
```

`test_result = 1`, только если нет `context.HasCriticalError` и все явные
результаты проверок в отчёте успешны. Ошибка печати или DataTest сохраняется
в результате, даже если граф настроен продолжаться после неё.
`stand_id` читается из `AppSettings.StandId` (дефолт `тест`), а `session` — из первого аргумента
запуска приложения и пропускается, если аргумент отсутствует. `serial_num` —
полный серверный `SerialNumber`, не короткий номер этикетки.

Каждая строка имеет формат `name=true|false=value\r\n`. `SubtestStep` сохраняет
исход составного подтеста в `TestContext.ReportEntries`. Туда же добавляются
скорость/потери каждой пары DataTest, финальные измерения PoE A/B регистров
1402/1403 в цикле устройств и результат печати. `ProductionReportFields`
добавляет выбранные поля свежего selftest по Qt `TestThread::make_report`:
CPU ID, версии, MAC, link, активные PoE A, плату/контроллеры, присутствующие
SFP и напряжение обнаруженного UPS. XML-поля и aliases не дублируются.
Новая загрузка не подменяется старым успешным снимком при ошибке.

`IncludeAllVariables = false` по умолчанию; в PSW-2G6F+ это установлено в
обеих ветках отчёта. При явном включении служебные переменные добавляются
как информация, без вывода годности по суффиксам `.Ok`/`.Success`/`.Passed`.
Например, ошибка очистки ARP не равна браку, если последующее чтение устройства
и проверка MAC успешны. Реальные ошибки правил selftest остаются в отчёте.
Для `/test.shtml` версии `firmvare_vers` и `boot_vers` проверяются как hex
(например, `20d` = 525), как в Qt; исходная строка версии сохраняется.

`BuildTestReportStep` не отправляет отчет и не пишет файл; он только формирует
текст в переменной. Отправка и локальная копия выполняются отдельной нодой
`Send Test Report`.

## Отправка отчета

`SendTestReportStep`:

1. Читает построчный отчет из `ReportVariableName`.
2. Строит URL `ServerBaseUrl + Endpoint`.
3. Если `SaveLocalCopy = true`, пишет файл:

```text
{LocalReportsDirectory}/result-yyyyMMdd-HHmmss-fff.txt
```

4. Делает POST с побайтно совместимым multipart-телом `QTstand_old`:

```text
field: action (empty)
field: updatefile; filename: result.json; content-type: application/octet-stream
field: result; filename: result.json (empty)
```

Legacy-тело намеренно сохраняет двойную строку boundary перед полем `result` и
не добавляет стандартный закрывающий суффикс `--`: именно такие байты формирует
старый `MainWindow::set_test_result`. Стандартный `MultipartFormDataContent`
давал тот же набор полей, но сервер фактически отвечал `HTTP 200` с текстом
`error`.

5. Успех: HTTP 2xx и response начинается с `Ok`.
6. При ошибке делает retry.

В рабочем PSW-профиле непосредственно перед штатной и аварийной отправкой
открывается обязательный операторский диалог. Он подставляет и показывает
полный `SerialNumber`, фактический `Dut.default_mac` и рассчитанный `Dut.NewMac`.
`Продолжить` ведёт в `Send Test Report`, `Отмена` — сразу в `End` без POST.
Аварийная ветка перед сборкой отчёта допускает только серийник в диапазоне
`3200000..3299999`; CPU ID или отсутствующее значение отчёт не отправляют.

## Печать этикетки

### Инженерная вкладка «Этикетки»

Список «Изделие» строится из `TestViewModel.AllProfiles`, то есть из всей
локальной папки профилей, без фильтра плат/коммутаторов и поискового запроса.
Используется `GraphProfile.DeviceModel`, одинаковые названия объединяются.
Выбор независим от открытого графа; он задаёт `{{Name}}` шаблона. Каталог
шаблонов по-прежнему задаёт формат и диапазоны серийников. Произвольные новые
названия не требуют списка моделей в коде. При нескольких изделиях и без
текущего выбора требуется явно выбрать название перед ручной ZPL-печатью.

`PreparedLabel` фиксирует проверенные шаблон, полный SN (с ведущими нулями в EPL),
MAC, имя принтера и количество до обращения к драйверу. `TestContext.LabelPrinting`
хранит отдельный снимок на запуск; параллельные ветви разделяют этот объект.
Cleanup его не заменяет. По завершении полного запуска `LastTestCompleted`
передаёт `LastTestLabelSnapshot` с результатом и ошибкой в `MainWindowViewModel`.
`LastTestLabelStore` атомарно сохраняет `last-test-label.json` рядом с exe;
после перезапуска вкладка восстанавливает этот снимок. Ошибка записи выводится
в лог, при этом данные остаются доступны в памяти. Не сохраняются токены,
сетевые сессии, регистры или полный словарь переменных.

«Печатать из последнего теста» использует снимок независимо от текущего
профиля, выбранного изделия и ручного ввода; принтер и количество берутся из
текущих полей. Ошибка повторной печати не удаляет снимок и не меняет результат
производственного теста. Подготовка профиля, частичный/учебный запуск, кнопки и
ручная печать не публикуют результат полного теста. Новый полный тест без
подготовленной этикетки заменяет прежний результат пустым снимком, поэтому
данные предыдущего изделия нельзя случайно повторить как последнее изделие.
При обновлении старой программы прошлый runtime-контекст не восстанавливается:
сохранение начинается со следующего полного запуска.

Тот же снимок восстанавливается в `TestViewModel` для графов и кнопок профиля.
`TestContext.LastTestLabel` получает отдельную копию при начале выполнения,
в том числе в параллельных ветвях. Нода с `UseLastTestLabel` вызывает обычный
путь RAW-печати с сохранённым шаблоном и идентификаторами; имя текущего профиля
к шаблону не применяется. Принтер можно переопределить в ноде либо оставить
пустым для использования сохранённого, число копий задаётся в ноде.
Диагностика `PrintLabel.SerialSource = LastTest`. У кнопки независимый контекст,
поэтому ни успех, ни отказ повторной печати не меняют исходный результат теста.

MainWindow создаёт LabelPrintingViewModel; LabelPrintingView доступен в
инженерном режиме. Выбирается шаблон из редактируемого локального каталога
`AppSettings.LabelTemplates`; исходно есть Pro, PSW-2G6F+ и EPL с серийником. Вводятся серийник, MAC, принтер Windows и количество
1–100. Используется PrintLabelStep без графа и Modbus. Повтор хранит снимок
последней успешной печати этой вкладки до закрытия приложения; количество
и принтер берутся из текущих полей. Ошибка не заменяет сохранённую этикетку.
Операции отменяемые; IsLabelToolBusy блокирует старт теста и подготовки.

Поле принтера во вкладке «Этикетки» и в ноде `Print Label` (включая мини-графы
кнопок профиля) — общий `PrinterPicker`: редактируемый `AutoCompleteBox`, кнопка открытия
полного списка мышью и «Обновить». `PrinterPickerViewModel` загружает список при
появлении контрола, убирает пустые/повторные имена и сортирует их. Обновление
не меняет привязанное `PrinterName`; ручной ввод, обычная печать и повтор
используют то же поле. Блокировка вкладки или редактирования графа распространяется
на ввод и обе кнопки. Нода сохраняет выбор в существующем `printerName`;
пустое поле для источника «Из последнего теста» сохраняет принтер из снимка.

`WindowsPrinterCatalog` вызывает `EnumPrintersW`, уровень 4, флаги
`PRINTER_ENUM_LOCAL | PRINTER_ENUM_CONNECTIONS`: установленные локальные очереди
и сетевые подключения текущего пользователя. Это не сканирование всей сети
и не проверка online-состояния. Вызов идёт в `Task.Run`; ожидание ограничено
10 секундами. Если нативный вызов задержался, повторное обновление ждёт тот же
worker вместо создания новых. Контрол отменяет ожидание при выгрузке; поздний
результат не применяется. При ошибке прежний список и введённое имя сохраняются.
На других ОС выводится короткое сообщение, ручное поле остаётся доступным.
Справка API: [Microsoft EnumPrinters](https://learn.microsoft.com/en-us/windows/win32/printdocs/enumprinters).

С 2026-10-30 выбор шаблона — карточки с образцами вместо списка названий.
`LabelPreview` локально разбирает команду, полученную теми же подстановками,
что использует печать. `LabelPrintContent` разделяется с `PrintLabelStep`:
полный/короткий номер, нормализация MAC и смещения EPL остаются общими.
Предпросмотр не вызывает принтер, сервер или браузер. Пустые поля заменяются
примером только в изображении и помечаются; неверные данные показывают ошибку.
Последний предпросмотр строится из `PrintLabel.SingleCommand` после успеха,
поэтому повтор не зависит от изменённых полей или каталога.

`LabelPreviewControl` рисует чёрное содержимое на белой этикетке в обеих темах.
На широком окне изображение справа от полей, на узком — ниже. В редакторе
шаблонов образец обновляется с задержкой 150 мс; закрытие останавливает таймер,
изменения до сохранения остаются черновиком.

Это приблизительное отображение, не эмулятор принтера: ZPL поддерживает `FO`,
`LH`, `A0`, `CF`, `BY`, `BC` (Code128 B/C), `FD`, `FS`, `GB`, `PW`, `LL`;
EPL — неповёрнутые `A` (шрифты 1–5), `B` (Code128 1/1B/1C), `q`, `Q`.
Шрифты заменяются экранными; поворот, QR, графика и прочие неподдерживаемые
команды перечисляются в сообщении. При явном размере видна обрезка за границей.
Если размер не задан в команде, изображение вмещает содержимое с сохранением
взаимных координат: внешнее смещение печатающей головки старых шаблонов
не создаёт большое пустое поле. Точные размеры бумаги/dpi в JSON не добавлялись.
Ограничения: команда до 100000 символов, до 500 элементов, поля до 256 символов.
Они ограничивают только предпросмотр; RAW-команда печати не переписывается.

Синтаксис сверялся с [Zebra ZPL Programming Guide](https://docs.zebra.com/us/en/printers/software/zpl-pg/c-zpl-zpl-commands/r-zpl-bc.html)
и [EPL Programming Guide](https://www.zebra.com/content/dam/support-dam/en/documentation/unrestricted/guide/software/epl2-pm-en.pdf).

В psw_stand-dev/Printer/reportprinter.cpp найден read-only запрос
`getdevicehistorylist?findParam=serial&findVal=…`, возвращающий массив с
объектами `device`. LabelLookupService заполняет поля без автоматической
печати. **Живой контракт пока не подтверждён:** вариант `findParam=mac` и
поля серийника/MAC реализованы предположительно и проверены на синтетических
ответах. Неполные, несовпадающие и неоднозначные данные отклоняются. MAC не
вычисляется вместо серверного; выдача нового номера getSerialNum не вызывается.
LauncherServerClient передаёт сессию этому endpoint только на исходном origin,
без redirect. Для проверки сервера требуется доступное удалённое подключение.

### Производственная нода

`PrintLabelStep` принимает полную копию `LabelTemplateDefinition`, сохранённую
в ноде. «Выбрать / настроить шаблон…» открывает редактор команд EPL/ZPL,
подстановок, диапазона номера и необходимости MAC. Шаблон имеет приоритет
над legacy-полями и переносится вместе с профилем. Это редактор команд и полей,
не визуальный дизайнер размещения элементов.

Для старых нод **без `labelTemplate`** сохранены два режима. Обычный формат повторяет
алгоритм `RTL_v2`: читает полный номер из переменной `SerialNumber` и печатает
только его Code128-штрихкодом и обычным текстом. Значение по умолчанию — четыре
одинаковые этикетки на `TSC TE310`.

Для автономной перепечатки `UseManualSerialNumber = true` переключает источник
на поле `ManualSerialNumber`. Оно обязано быть непустым и содержать только
ASCII-цифры. Этот режим используется в импортируемом примере
`examples/profiles/manual_label_printing.json`; COM/Modbus-подключение ему не требуется.

Если `UseQtProZplFormat = false`, фактическая команда `RTL_v2` имеет формат EPL
(`N`, `q354`, `B...`, `A...`, `P1,1`) для этикетки 30x10 мм при 300 dpi и не
добавляет MAC, модель или служебные поля.

Если `UseQtProZplFormat = true`, нода воспроизводит общий `print_label` старой
Qt-программы и значения профиля `PSW+UPS-Box 8x2Pro.json`: ZPL для этикетки
25x13 мм, название `PSW+UPS-Box 8x2Pro`, MAC `C0:11:A6:20:HH:LL`, строку
`SN: SSSSS` и Code128 payload `032SSSSS`. В основном производственном профиле
нода не рассчитывает эти значения: читает `SerialNumber`, `SerialShort` и
`Dut.default_mac`, полученные предыдущими шагами. Последний MAC появляется из
post-reboot selftest и до печати сравнивается с `Dut.NewMac`; отсутствие или
несогласованность значений блокирует печать. `SetMac.Timestamp` используется
только bat-командой записи и в этикетку не попадает.

В ручном мини-профиле полный/короткий номер и реальный MAC вводятся оператором
отдельно. ZPL-команда повторяется четыре раза в одном RAW-задании. После первой
физической печати штрихкод сдвинут на 30 точек влево (`^FO480,117`), чтобы
восстановить правое тихое поле; остальные поля тогда не изменялись. По последнему
уточнению оператора 2026-10-30 строка SN начинается на `^FO510,95` — по левому
краю MAC (`^FO510,70`), без центрирования. Штрихкод также
сдвинут вправо: итоговый `^FO510,117` после коррекции оператором на бумаге,
ширина Code128 B из восьми символов — 246 точек. MAC сохраняет координаты.

Legacy-поле `labelModel` хранится в ноде; без него используется Pro.
При выбранном шаблоне модель/команды определяет `labelTemplate`, а не имя профиля.

Для `LabelModel=Psw2G6FPlus` при включённом ZPL используется отдельный Qt-макет
PSW-2G6F+: тип `6`, полный серийник `600000..665535`, короткий SN из пяти цифр,
штрихкод `006SSSSS` на `^FO510,117` без `>:`. Старые JSON без `labelModel`
сохраняют макет Pro. Новый профиль печатает MAC из `DutAfterMac.default_mac`
после явного сравнения с рассчитанным. Макет проверен по байтам Qt; физическую
печать PSW-2G6F+ подтвердил оператор 2026-09-28. RAW-печать обоих макетов
реализована через Windows API:

- `OpenPrinter`;
- `StartDocPrinter`;
- `StartPagePrinter`;
- `WritePrinter`;
- `EndPagePrinter`;
- `EndDocPrinter`;
- `ClosePrinter`.

Ограничение: на не-Windows ОС нода возвращает ошибку `RAW-печать поддерживается только в Windows`.
Вызов spooler вынесен с UI-потока и ограничен 30 секундами. Шаг проверяет
offline-атрибут очереди, ошибки принтера, все этапы передачи и число байт.
`StartDocPrinter` возвращает ID задания; `SetJob(RETAIN)` удерживает только
это задание до чтения его финального статуса через `GetJob`.
`PRINTED` даёт `PrintLabel.CompletionStatus=Printed`; `COMPLETE` даёт
`SentToPrinter` и текст «передано принтеру; драйвер не подтверждает физический
выход этикетки». Постановка в очередь сама по себе больше не означает успех.
После завершения удержание снимается. Ошибка/таймаут/отмена вызывают DELETE,
затем RELEASE только для своего задания: на TSC один DELETE оставлял
завершённый retained job в состоянии DELETING. Последовательность проверена
на контрольном job 5, очередь очистилась. Зависший native-вызов может
задержать отмену.
Остальные задания очереди не затрагиваются.

На APK-03-07 2026-09-28 TSC TE310 вернул `COMPLETE`, без `PRINTED`.
Оператор подтвердил физический выход PSW-2G6F+ с SN 12447. Второй контрольный
запуск завершился успешно, job 6, 180 мс; такой статус подтверждает передачу
через Windows, но не является датчиком физического выхода этикетки.

## Типичные цепочки

### Selftest и проверки

```text
Selftest Check
  -> Check Variable Equality (Dut.init_ok == 1)
  -> Check Variable Range (Dut.akb_voltage 12..27)
```

### Серийник, MAC, установка MAC

```text
Get Serial Number
  -> Build MAC From Serial
  -> Set Pro MAC
  -> Delay
  -> Clear ARP Cache
  -> Selftest Check
  -> Compare Variables (Dut.default_mac == Dut.NewMac)
```

### Отчет и отправка

```text
Build Test Report
  -> Send Test Report
```
