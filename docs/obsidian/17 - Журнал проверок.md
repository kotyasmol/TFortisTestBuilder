# Журнал проверок

Запись в журнале фиксирует выполненную проверку и её границы. «Пройдено»
означает только результат указанной команды или сценария, а не отсутствие
ошибок во всём продукте.

## Правило ведения

Для существенного изменения записывать дату, область, команду или сценарий,
результат, известные предупреждения и непроверенные границы. После проверки на
реальном оборудовании добавлять конфигурацию стенда без паролей, IP-адресов и
других секретов.

## Проверка 2026-09-11: VER-036 — четыре этикетки с серийником

Алгоритм печати сверен с `RTL_v2` commit
`86f7dbd7cadf4c72f7a3e0763ce0fc4d72123687` и реализацией
`FTServiceUtils.ZebraLabel`. Несмотря на имя класса, библиотека генерирует EPL:
для одной этикетки 30x10 мм/300 dpi передаются `N`, `q354`, Code128-команда
`B`, текстовая команда `A` и `P1,1`. Текущая нода повторяет этот layout, но по
требованию печатает только полный `SerialNumber`, без MAC, названия устройства
и equipment-суффиксов. Команда повторяется четыре раза в одном RAW-задании на
принтер `TSC TE310`.

Целевые тесты проверили точные байты для номера `3200428`, четыре экземпляра,
отсутствующий серийник, ошибку spooler и таймаут без блокировки вызывающего
потока: 4/4. Полный прогон — 123/123, сборка — без ошибок, JSON рабочего
профиля валиден. Известно предупреждение совместимости `NModbus4` (`NU1701`).
Физический принтер не вызывался; окончательная проверка — один прогон на
Windows-стенде с установленным в системе принтером под именем `TSC TE310`.

## Проверка 2026-09-11: VER-035 — WinSCP входит в приложение

`WinSCP.com`, `WinSCP.exe`, `readme.txt` и `license.txt`. SHA-256 загруженного
архива — `cbe76fc80695ac34d14e4ba81f7ff564beeb3f2033dae7490092e269016d7959` —
совпал с контрольной суммой на winscp.net. Проект копирует папку `WinSCP`
целиком в build и publish, где `set_mac_pro.bat` находит console executable по
соседнему пути без установки и без ручных действий оператора.

Проверены Debug build и отдельный publish: оба WinSCP executable и bat

## Проверка 2026-09-09: VER-026 — ошибка Windows при ожидании MAC

На пользовательском скриншоте selftest прошёл (82 поля, прошивка 1119),
использован фиксированный серийник `3200428`, пакет UDP передан сокету. Сразу
при ожидании ответа появилась ошибка «Удалённый хост принудительно разорвал
существующее подключение», и граф остановился до повторов и reboot/read-back.
Сообщение соответствует `WSAECONNRESET`; для UDP это уведомление ICMP о
недоступном порте. В скриншоте нет числового кода/сетевого захвата, а причина
недоступности обработчика записи MAC пока не установлена. Отчёт об этом
неуспешном тесте приложение пользователя отправило успешно.

Исправлено разделение ошибок: `ConnectionReset`/`ConnectionRefused` при приёме
завершают попытку с диагностикой и допускают повтор; отсутствие `mr` после
отправки позволяет дойти до reboot/read-back без ложного успеха. Ошибки
bind/отправки и другие ошибки приёма сохраняют прежнюю политику.

Проверки: `dotnet test TestBuilder.Tests/TestBuilder.Tests.csproj --no-restore
--filter FullyQualifiedName~SendUdpSetMacPacketStepTests` (сборка успешна,
локальные сокеты VSTest потребовали повторного запуска вне sandbox);
целевой повтор `--no-build --no-restore` — 19/19, полный прогон — 125/125;
`git diff --check` — без ошибок. Сохранены известные предупреждения сборки.
Новые тесты используют реальные UDP-пакеты на loopback и внедрённую ошибку
приёма для воспроизведения Windows-сценария на macOS. Проверены исчерпание
попыток, успешный ACK после ошибки, прочие socket errors, отмена и сброс
диагностики. Агент не обращался к DUT или производственному серверу.
Фактическая запись MAC на Windows после исправления ещё не проверена.

## Проверка 2026-09-09: VER-027 — зависание UI при повторном selftest

По полному стендовому логу начальный selftest успешно получил данные после
11 попыток. Все три UDP-команды MAC получили `ConnectionReset`, native 10054;
затем прошли перезапуск питания и очистка ARP. На шестой браузерной попытке
после перезапуска зависло всё окно. Пользователь подтвердил, что процесс
завершила кнопкой Stop Debugging; `0xffffffff` не классифицируется как
самопроизвольное падение. Строки `TaskCanceledException` без стека не являются
доказательством необработанного исключения. MAC после перезапуска не прочитан.

В коде браузерные `Process.Start`, `Kill` дерева и рекурсивное удаление своего
временного профиля выполнялись на потоке UI; запуск и cleanup не были полностью
охвачены внутренним токеном timeout. Введён `HeadlessBrowserAttemptRunner`:
весь жизненный цикл в worker, независимый предел ожидания/отмена, наблюдение
позднего завершения и запрет дополнительных браузеров этой нодой до окончания
предыдущей попытки. Логи показывают текущий этап. Native-операция, которая
блокируется внутри ОС, может продолжить завершение в фоне; возвращается
управление UI/исполнителю, а не обещание принудительно прервать такой вызов.

Сборка и проверки: целевые
`dotnet test TestBuilder.Tests/TestBuilder.Tests.csproj --no-restore --filter
'FullyQualifiedName~HeadlessBrowserAttemptRunnerTests|FullyQualifiedName~SelfTestCheckStepTests'`
(после sandbox-запрета канала VSTest повтор с `--no-build`) — 18/18;
финальный `dotnet test TestBuilder.Tests/TestBuilder.Tests.csproj --no-restore`
— 132/132, `git diff --check` — без ошибок. Есть прежние предупреждения сборки.
Семь новых случаев проверяют блокирующий запуск/cleanup, поток UI, предел
ожидания, отсутствие перекрывающихся браузеров, остановку, ошибку запуска
и отмену до запуска. Реальный Chrome/Edge на Windows и физический DUT при
проверке не использовались; окончательная проверка зависания остаётся стендовой.
Профиль, fixed serial `3200428`, протокол MAC и настройки сервера не менялись.

Этот вариант отменён в VER-029 после обратной связи пользователя: запрет новой
попытки при незавершённом worker оказался регрессией. `SelfTestCheckStep`
возвращён к версии до `c847bd2`; история VER-027 оставлена как постмортем.
