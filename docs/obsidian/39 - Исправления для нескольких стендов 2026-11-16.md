# Исправления для нескольких стендов

Продолжение [[38 - Разбор сбоев нескольких стендов 2026-11-16]]. Изменения
внесены в исходники и проверяются без доступа к оборудованию. Пользователь
сообщила, что сможет включить стенды только завтра. Windows-прогон, физическая
печать, приём новых отчётов сервером и публикация обновления не выполнялись.

## Производственный профиль и диагностика

`profilePurpose` в JSON: `production` либо `diagnostic`. В редакторе:
**Ещё → Диагностический профиль**, затем сохранение. Смена назначения
поддерживает отмену. Ноды и связи при этом не перестраиваются.

Если поля нет, профиль с исключительно диагностическими нодами формирования
отчёта определяется по `testType=diagnostic`, включая вложенные тела.
Это распознаёт уже разошедшиеся файлы 13.11 без проверки имени или списка
моделей. Остальные старые файлы считаются производственными. Явное поле имеет
приоритет; неизвестное значение не принимается молча как production.

«Актуальный» теперь выбирается среди производственных профилей одной модели.
Если их нет, показывается свежая диагностика с подписью «Диагностика».
Диагностический файл в раскрытой группе имеет отдельную подпись. Таким
образом, новый диагностический 8x2Pro больше не скрывает производственный 11.11.

## Печать и отчёт

В десяти примерах порядок последних этапов: `08` необязательная печать →
`09` выключение → `10` итоговый отчёт. Ошибка включённой печати возникает до
обычного POST и попадает в аварийный отчёт. Диагностика по-прежнему не
прошивает MAC и не заменяет полную производственную методику.

Компилятор отклоняет последовательный путь от отправки отчёта коммутатора
к включённой печати, в том числе через подтесты. Ошибка показывается до
автоматической подготовки. Выключенная печать не блокирует пуск.
Независимые параллельные ветви эта проверка не запрещает.

Исключение определяется протоколом: `SendTestResultUniverse` для RTL выдаёт
серийный номер в ответе на POST. Печать платы после него разрешена. Политика
повторной отправки серверных отчётов не менялась.

## DataTest и перенос между ПК

- До подготовки проверяются активные пары: формат, два разных IPv4, наличие
  адресов на этом ПК, отсутствие неоднозначной привязки и наличие pcap-карт.
  Один адаптер под двумя IP не принимается за две физические карты.
  Линк и скорость проверяются позже, когда граф уже включил DUT.
- Pcap-интерфейс выбирается сначала по ID ОС, затем по единственному MAC.
  Два интерфейса с одним MAC без точного ID больше не выбираются произвольно.
- Native-очереди всегда синхронизируют отдельные кадры. Части ограничены
  50 мс до 100 Мбит/с и 20 мс выше; прежних несинхронизированных пачек
  по 100 мс нет. Память по-прежнему ограничена каналом подготовки.
- На прогреве сначала проверяется один отправитель. В Windows выше
  100 Мбит/с при его отказе/недостаточной скорости проверяются два
  синхронизированных отправителя. Основное измерение использует подтверждённый
  вариант. Неудачный прогрев не считается измеренной потерей DUT.
- Для native-очереди неполный/некорректный результат — явная ошибка с числом
  кадров, байтов, номером отправителя и native LastError. Для программного
  paced fallback применяется заданный допуск дефицита фактической скорости.
- Хвост RX ожидается до получения всех отправленных проб либо 200 мс
  тишины, максимум 2 секунды. Устранено прежнее завершение после 75 мс,
  которое могло не дождаться задержанной пачки захвата.
- В журнале есть доступность статистики Npcap, её received/dropped,
  ошибки/отбрасывания NIC, первый/последний отсутствующий sequence и самая
  длинная дыра. Ошибки NIC и потери при недоступной статистике захвата
  помечаются как недостоверное измерение стенда. Допуск потерь не увеличен.
- Записываются управляемая библиотека и фактически загруженные Windows
  `wpcap.dll`/`Packet.dll` с версиями и путями.

IP не переназначаются по названию карты или её скорости. Сетевой план
рабочего места остаётся явной настройкой; импорт плана в ноду создаёт снимок.
Это предотвращает молчаливое переключение теста на другой физический порт.

## Запись Modbus

`RegisterDefinition.RetryWriteOnMismatch` — необязательный флаг карты
оборудования, по умолчанию false. В редакторе оборудования — колонка
**Повтор состояния**, с пояснением в подсказке. При несовпадении контрольного
чтения разрешено повторить ту же запись; всего максимум три записи/чтения.
Для неизвестных и командных регистров поведение остаётся консервативным:
одна запись и повторные чтения. Устойчивое несовпадение завершает тест ошибкой.

В двух базовых PSW-профилях и справочнике оборудования флаг включён только
у EL60v5 1420/1421 — установки состояния автозапуска A/B. 1430 очистки
статистики не изменён. В пользовательских JSON без флага повторные записи
не включаются автоматически: это требует явной настройки карты.

**Все ноды, связи, координаты, кнопки, индикаторы и составы отчётов четырёх
производственных профилей совпадают с предыдущим коммитом.** Изменены только
эти флаги оборудования у двух PSW. Поэтому полные хеши двух файлов изменились;
старые SHA-256 в расследовании 38 относятся к состоянию до этой правки.

## Журнал запуска

Перед действиями записываются имя ПК, ОС/архитектура/.NET, информационная
версия сборки, Stand ID, назначение профиля, путь и SHA-256 файла и
сериализованного графа в памяти. Содержимое JSON и сессия для вычисления
хеша в журнал не выводятся. Хеш файла и хеш сериализованного графа считаются
для разных представлений и не обязаны совпадать между собой; сравнивать
нужно одноимённые показатели разных прогонов. Ошибка записи диагностических данных не
прерывает запуск. Исходный Stand ID `тест` сопровождается предупреждением;
зарегистрированный серверный идентификатор автоматически не подменяется.

## Проверка завтра

1. Обновить основную рабочую копию АПК‑03 и запустить отладку Visual Studio
   из `C:\Users\АПК-03-07\Documents\GitHub\TFortisTestBuilder`.
   До обновления сохранить местные правки и пользовательские профили.
   Другие копии приложения на АПК‑03 не создавать.
2. Убедиться по журналу в сборке и пути выбранного файла. У 8x2Pro выбрать
   производственный эталон 11.11; диагностика 13.11 имеет отдельную отметку.
3. На каждом рабочем месте сверить пары IP с кабелями и местным планом,
   индивидуальный Stand ID, COM и состав оборудования. Не заменять рабочие
   локальные пары `.2/.3` и `.8/.9` одной раскладкой для всех ПК.
4. Выполнить полный эталон: параллельная загрузка/нагреватели, DataTest,
   остальные аппаратные проверки, MAC после перезапуска, этикетки и отчёт.
   Проверить полный номер, реальный MAC и итог в сохранённом отчёте.
5. При повторе TB1503 сохранить журнал с фазой и native-ошибкой. При TB1504
   сравнить пропуски sequence, счётчики и результат того же DUT на рабочем
   стенде. При TB1106 проверить тип/прошивку и 1421 платы 7.

Эти исправления устраняют найденные программные причины и добавляют контроль
непригодного измерения. Они не подтверждают физическую исправность всех
компьютеров, карт, плат и изделий без прогона.

## Программная проверка

Заключительные отдельные наборы: **345/345** проверок исполнения, каталога,
отчётов, копирования и оборудования; **45/45** обязательных UI/локализации/
режима DataTest. После проверки отклонения неизвестного назначения до
замены открытого графа также прошли 37 проверок импорта/копирования; это
пересекающийся набор, к 390 уникальным случаям его не прибавляем.

В промежуточном совмещённом запуске было 367/368: один сбой создания
Inter glyphTypeface в headless Avalonia. Повтор UI в свежем процессе прошёл
45/45, затем заключительные отдельные наборы выше тоже прошли. Полный
набор всего репозитория не запускался и не объявляется успешным.

Генератор выполнил `ProfileLayout --write`, затем отдельный `--check` для
всех десяти примеров: 130 графов, 621 нода, 0 конфликтов в повторной проверке.
Просмотрен снимок корневого графа Pro. Проверка четырёх ручных базовых файлов
нашла прежние геометрические замечания: 102/85/95/151. На выгрузке файлов
предыдущего коммита получен побайтно тот же диагностический вывод. Узлы
производственных графов не передвигались; эти замечания не объявляются
исправленными в рамках функциональной правки.
