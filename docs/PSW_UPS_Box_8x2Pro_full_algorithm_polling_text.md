# PSW+UPS-Box 8x2Pro — текстовая расшифровка рабочего графа


## 1. Как читать запись

- `slave 23, 1200 ← 1` — записать значение `1` в holding-регистр `1200`
  Modbus-устройства с адресом `23`.
- `с проверкой` — после записи до трех раз прочитать регистр и сравнить значение;
  перед второй и третьей попытками есть паузы по `300 мс`.
- `без проверки` — считать шаг успешным сразу после успешной команды записи, не
  подтверждая состояние обратным чтением.
- `live-read` — непосредственно перед проверкой прочитать регистр по Modbus, а не
  использовать старое значение фонового мониторинга.
- Все диапазоны в профиле включают обе границы.

Профиль фактически предполагает такую адресацию стенда:

| Slave ID | Предполагаемое устройство | Почему |
| `23` | PS-3 | Используются регистры `1200..1221`, включая второй нагреватель `1220/1221`. |
| `17` | SIMBAT 24/48 | Используются ключи и измерения `1700`, `1706..1708`. |
| `1, 3, 5, 7, 9, 11, 13, 15` | восемь EL60v5 | На каждом используются два канала A/B, то есть суммарно 16 PoE-линий. |


## 2. Штатный порядок выполнения

В этой расшифровке корневой граф последовательно выполняет все подтесты

|---:|---|---|

| 02 | Сброс PoE-нагрузок EL60v5 | выполняется |
| 03 | Подключение оператора | выполняется; длительность зависит от оператора |
| 04 | Настройка PoE-нагрузок EL60v5 | выполняется |
| 05 | Подача питания DUT | выполняется |
| 06 | Ожидание загрузки DUT и selftest | выполняется |
| 07 | Проверка selftest DUT | выполняется |
| 08 | Проверка нагревателя 1 | выполняется |
| 09 | Проверка нагревателя 2 | выполняется |
| 10 | DataTest портов 0..9 | выполняется |
| 11 | UPS: подготовка и детекция | выполняется |
| 12 | UPS: переход на АКБ | выполняется |
| 13 | UPS: подтверждение питания от АКБ | выполняется |
| 14 | UPS: возврат на AC1 | выполняется |
| 15 | Получение серийника и запись MAC | выполняется |
| 16 | Печать этикеток | выполняется |

## 3. Общие тайминги

Во всей основной цепочке явно задано `94,7 с` обычных нод `Delay`:

| Подтест | Сумма фиксированных задержек |
|---|---:|
| 02. Сброс PoE-нагрузок | `32,0 с` |
| 03. Подключение оператора | фиксированного времени нет |
| 04. Настройка PoE-нагрузок | `5,6 с` |
| 05. Подача питания | `1,0 с` |
| 06. Загрузка и selftest | `7,0 с` |
| 08. Нагреватель 1 | `7,0 с` |
| 09. Нагреватель 2 | `5,0 с` |
| 11. UPS: подготовка | `15,0 с` |
| 12. Переход на АКБ | `2,0 с` |
| 14. Возврат на AC1 | `3,0 с` |
| 15. Серийник и MAC | `17,1 с` |

Кроме них есть:

- DataTest: `50 с` непосредственно измеряемого трафика, `5 с` warmup суммарно для
  десяти направлений и `20 с` пауз между пятью парами, а также внутренние паузы
  запуска/осушения capture;
- пять отдельных `Selftest Check`, каждый с общим таймаутом `300 с` и интервалом
  повторов `5 с`;
- два ожидания `Wait Variable Until`, каждое с внешним таймаутом `300 с`;
- внутри каждой браузерной selftest-попытки после загрузки страницы всегда есть
  дополнительное ожидание `10 с` перед чтением DOM;
- одна браузерная попытка ограничена `30 с` в обычной ноде `Selftest Check`;
- очистка ARP имеет таймаут процесса `5 с`;
- запрос серийного номера: максимум две попытки по `30 с`, между ними `1 с`;
- отправка отчета: максимум две попытки по `10 с`, между ними `1 с`;
- запись Modbus с проверкой может делать до трех чтений с двумя паузами по `300 мс`.

## 4. Полный граф по шагам

### 01. Подготовка стенда

Описание в профиле: «Сброс питания/ключей/нагревателей, очистка ARP, фиксация
параметров профиля».

Выполняется:

1. Записать в лог метку:
   `Профиль: PSW+UPS-Box 8x2Pro; start_delay=160s; AC1=true; AC2=false; PoE lines 0..15; data ports 0..9; UPS=true; heaters=true; print labels=4`.
2. `slave 23, 1200 ← 0`, с проверкой — выключить AC1.
3. `slave 23, 1201 ← 0`, с проверкой — выключить AC2.
4. `slave 23, 1204 ← 0`, с проверкой — выключить ключ зарядки.
5. `slave 23, 1210 ← 0`, с проверкой — выключить ключ разрядки.
6. `slave 23, 1215 ← 0`, с проверкой — выключить реле нагревателя 1.
7. `slave 23, 1220 ← 0`, с проверкой — выключить реле нагревателя 2.
8. `slave 17, 1700 ← 0`, с проверкой — выключить ключ зарядки SIMBAT.
9. Очистить ARP-кэш:
   - сначала запустить `arpd.bat`;
   - затем выполнить `arp -d *`;
   - таймаут каждого процесса `5000 мс`;
   - ошибка не проваливает шаг (`failOnError=false`).

### 02. Сброс PoE-нагрузок EL60v5

Описание: «Безопасно выключить нагрузку на EL60v5 перед стартом».

Цикл идет по slave ID `1, 3, 5, 7, 9, 11, 13, 15`. Для каждого из восьми
устройств последовательно:

1. `1420 ← 0`, с проверкой — выключить автоматическое включение нагрузки канала A.
2. `1421 ← 0`, с проверкой — выключить автоматическое включение нагрузки канала B.
3. Ждать `1000 мс`.
4. `1414 ← 0`, с проверкой — выключить нагрузку канала A.
5. `1415 ← 0`, с проверкой — выключить нагрузку канала B.
6. `1412 ← 0`, с проверкой — установить нагрузку канала A в `0 мВт`.
7. `1413 ← 0`, с проверкой — установить нагрузку канала B в `0 мВт`.
8. `1430 ← 1`, с проверкой — подать команду очистки статистики.
9. Ждать `1000 мс`.
10. `1430 ← 0`, с проверкой — снять команду очистки статистики.
11. Ждать `2000 мс`.

Фиксированная пауза — `4 с` на один EL60v5, всего `32 с` на восемь устройств,
плюс время Modbus-записей и их подтверждения. Ошибка на любом устройстве прекращает
цикл (`stopOnError=true`).

### 03. Подключение оператора

Показывается диалог:

> Подключите разъемы DUT, PoE-нагрузки, АКБ/БП. После проверки нажмите Продолжить.

Кнопка «Продолжить» завершает подтест успешно. Выход «Отмена» никуда не подключен и
завершает граф ошибкой.

### 04. Настройка PoE-нагрузок EL60v5

Цикл идет по slave ID `1, 3, 5, 7, 9, 11, 13, 15`. Для каждого EL60v5:

1. `1412 ← 15000`, с проверкой — мощность канала A `15000 мВт`.
2. Ждать `100 мс`.
3. `1413 ← 15000`, с проверкой — мощность канала B `15000 мВт`.
4. Ждать `100 мс`.
5. `1414 ← 1`, с проверкой — включить нагрузку канала A.
6. Ждать `100 мс`.
7. `1415 ← 1`, с проверкой — включить нагрузку канала B.
8. Ждать `400 мс`.


### 05. Подача питания DUT

1. `slave 17, 1706 ← 1`, **без проверки** — включить ключ разрядки SIMBAT.
2. `slave 23, 1210 ← 1`, с проверкой — включить ключ разрядки стендового PS-3.
3. Ждать `300 мс`.
4. Ждать еще `500 мс` — между двумя задержками нет другой операции; суммарно
   получается `800 мс`.
5. `slave 23, 1200 ← 1`, с проверкой — включить AC1.
6. `slave 23, 1201 ← 0`, с проверкой — выключить AC2.
7. Ждать `200 мс`.

Общая явная задержка — `1 с`.

### 06. Ожидание загрузки DUT и selftest

1. Ждать `5000 мс` после подачи питания.
2. Очистить ARP через `arpd.bat` и `arp -d *`; таймаут процесса `5000 мс`, ошибка
   игнорируется.
3. Запустить `Selftest Check`:
   - URL:
     `http://192.168.0.1/cgi-bin/luci/admin/statistics/deviceinfo?luci_username=admin&luci_password=admin`;
   - общий таймаут `300000 мс`;
   - пауза между полными браузерными попытками `5000 мс`;
   - результат записывается в переменные с префиксом `Dut`;
   - `validationRules` в JSON пуст, поэтому runtime подставляет стандартные правила:
     `init_ok=1..1`, `dev_type=0..65535`, `firmvare_vers=0..65535`,
     `boot_vers=0..65535`;
   - окончательная ошибка обязательная (`failOnError=true`).
4. После успешного selftest ждать `2000 мс`.


### 07. Проверка selftest DUT

1. Повторно полностью выполнить `Selftest Check` по тому же URL:
   - таймаут `300000 мс`;
   - интервал `5000 мс`;
   - префикс `Dut`;
   - правила `init_ok=1..1`, `dev_type=0..65535`,
     `firmvare_vers=0..65535`, `boot_vers=0..65535`;
   - ошибка обязательная.
2. Проверить `Dut.init_ok == 1` как число.
3. Проверить `Dut.dev_type == 0` как число. Текст ошибки при этом говорит:
   «Тип устройства должен быть 32 для PSW+UPS-Box 8x2Pro».
4. Проверить `Dut.firmvare_vers == 1119` с типом сравнения `Version`. Runtime
   трактует строку `1119` как версию `1119.0.0.0`; текст ошибки говорит о версии
   `1.1.0`.
5. Проверить `Dut.ups_det == 1` — UPS/АКБ обнаружен.
6. Проверить `Dut.ups_rez == 0` — DUT работает от сети до UPS-теста.
7. Проверить `Dut.akb_voltage` в диапазоне `0..100`. Текст ошибки при этом говорит
   о диапазоне `12..27 В`.

Дополнительной проверки PoE-линий, Ethernet-портов, температур или иных распарсенных
selftest-полей в этом подтесте нет.

### 08. Проверка нагревателя 1

Описание: ток до включения `0..50 мА`, после включения `150..1000 мА`.

Фактически выполняется:

1. Live-read `slave 23, 1216`; проверить ток нагревателя 1 в диапазоне `0..50 мА`.
2. `1215 ← 0`, с проверкой — выключить реле нагревателя 1.
3. Сразу, без задержки, `1215 ← 1`, с проверкой — включить реле нагревателя 1.
4. Ждать `5000 мс`.
5. Live-read `1216`; проверить ток в диапазоне **`0..1500 мА`**.
6. `1215 ← 0`, с проверкой — выключить реле.
7. Ждать `2000 мс`.

Вторая фактическая проверка допускает нулевой ток и не совпадает с описанием
`150..1000 мА`.

### 09. Проверка нагревателя 2

1. Live-read `slave 23, 1221`; проверить ток нагревателя 2 в диапазоне `0..50 мА`.
2. `1220 ← 0`, с проверкой — выключить реле нагревателя 2.
3. Сразу, без задержки, `1220 ← 1`, с проверкой — включить реле нагревателя 2.
4. Ждать `3000 мс`.
5. Live-read `1221`; проверить ток в диапазоне `150..1000 мА`.
6. `1220 ← 0`, с проверкой — выключить реле.
7. Ждать `2000 мс`.

### 10. DataTest портов 0..9

Одна нода `Run Data Test` последовательно проверяет пять пар в обоих направлениях:

| Пара | Принимающая карта | Передающая карта | Target |
|---|---|---|---:|
| port0-1 | `192.168.0.2` | `192.168.0.3` | `100 Mbps` |
| port2-3 | `192.168.0.4` | `192.168.0.5` | `100 Mbps` |
| port4-5 | `192.168.0.6` | `192.168.0.7` | `100 Mbps` |
| port6-7 | `192.168.0.8` | `192.168.0.9` | `100 Mbps` |
| port8-9 | `192.168.0.10` | `192.168.0.11` | `100 Mbps` |

Параметры:

- режим `SoftwarePcap`;
- размер кадра `1514 байт`;
- UDP-порт `43962`;
- измерение `5000 мс` на направление;
- warmup `500 мс` на направление;
- после запуска capture перед warmup ждать `100 мс`;
- после warmup ждать еще `100 мс` для очистки хвоста;
- после основного трафика ждать тишины capture не менее `75 мс`, но не более
  `500 мс`;
- перед обратным направлением дополнительно ждать `100 мс`;
- оба направления (`bidirectional=true`);
- пауза между парами `5000 мс`, то есть четыре паузы суммарно `20 с`;
- максимальное время теста порта `15000 мс`;
- допустимая потеря `1%`;
- допустимый дефицит TX относительно target `2%`;
- при инфраструктурной ошибке направление повторяется один раз; перед повтором
  ждать `100 мс`;
- `expectedPackets=10000` сохранено в профиле, но фактическое ожидаемое количество
  кадров runtime рассчитывает из target, размера кадра и длительности;
- результат пишется под префиксом `DataTest`;
- ошибка обязательная.

Сетевые карты должны быть заранее вручную настроены на указанные IP; профиль их не
конфигурирует.

### 11. UPS: подготовка и детекция

1. `slave 23, 1219 ← 1`, **без проверки** — команда очистки статистики. Обратной
   записи `1219 ← 0` в графе нет.
2. `slave 23, 1215 ← 1`, с проверкой — включить нагреватель 1.
3. Ждать `15000 мс`.
4. Выполнить свежий `Selftest Check` по основному URL:
   - таймаут `300000 мс`;
   - интервал `5000 мс`;
   - префикс `Dut`;
   - пустые правила в JSON превращаются в четыре стандартных правила;
   - ошибка обязательная.
5. Проверить `Dut.ups_det == 1`.
6. Проверить `Dut.akb_voltage` в диапазоне `12..27`.
7. Проверить `Dut.ups_rez == 0` перед отключением AC.

Нагреватель 1 остается включенным на все время ожидания selftest и выключается только
в следующем подтесте.

### 12. UPS: переход на АКБ

1. `slave 23, 1204 ← 0`, с проверкой — выключить ключ зарядки.
2. `slave 23, 1200 ← 0`, с проверкой — отключить AC1.
3. `slave 23, 1215 ← 0`, с проверкой — выключить нагреватель 1.
4. `slave 23, 1220 ← 0`, с проверкой — выключить нагреватель 2.
5. Ждать `2000 мс` для стабилизации.

Ключи разрядки `slave 17:1706` и `slave 23:1210` остаются включенными с подтеста 05.

### 13. UPS: подтверждение питания от АКБ


1. Live-read `slave 17, 1707` — напряжение разрядки SIMBAT; фактический допустимый
   диапазон в JSON **`0..65535 мВ`**.
2. Live-read `slave 17, 1708` — ток разрядки SIMBAT; фактический допустимый диапазон
   **`0..65535 мА`**.
3. Ждать переменную `Dut.ups_rez == 1`:
   - режим `SelftestSnapshot` — каждая попытка заново открывает всю selftest-страницу
     браузером и переписывает переменные `Dut.*`;
   - URL собирается из `http://192.168.0.1` и
     `/cgi-bin/luci/admin/statistics/deviceinfo?luci_username=admin&luci_password=admin`;
   - тип сравнения `Number`;
   - тип HTTP-ответа в JSON `String`;
   - вложенный selftest также применяет четыре стандартных validation rules;
   - внешний таймаут `300000 мс`;
   - таймаут вложенного selftest-снимка также `300000 мс`;
   - интервал `5000 мс`;
   - таймаут обязательный (`failOnTimeout=true`).

Оба диапазона Modbus охватывают весь возможный `ushort`, поэтому при успешном чтении
они не доказывают наличие требуемого напряжения или ненулевого тока.

### 14. UPS: возврат на AC1

Фактический порядок переключения:

1. `slave 17, 1706 ← 0`, с проверкой — **сначала отключить разряд SIMBAT**.
2. `slave 23, 1200 ← 1`, с проверкой — **после этого включить AC1**.
3. Ждать `3000 мс`.
4. Ждать `Dut.ups_rez == 0` через новый `SelftestSnapshot`:
   - тот же URL;
   - внешний таймаут `300000 мс`;
   - таймаут одного вложенного selftest `300000 мс`;
   - интервал `5000 мс`;
   - сравнение как числа;
   - вложенный selftest также применяет четыре стандартных validation rules;
   - ошибка по таймауту обязательная.
5. `slave 23, 1210 ← 0`, с проверкой — выключить ключ разрядки стенда.
6. `slave 23, 1204 ← 0`, с проверкой — оставить ключ зарядки выключенным.


### 15. Получение серийника и запись MAC

1. Получить серийный номер с сервера:
   - в профиле `serverBaseUrl=http://SERVER_BASE_URL`; placeholder заменяется
     значением `Server base URL` из настроек приложения;
   - endpoint при базовом URL:
     `/api/api.svc/getSerialNum?devType=PSW%2BUPS-Box%208x2Pro&cpuId=<Dut.cpu_id>`;
   - CPU ID берется из `Dut.cpu_id`;
   - таймаут одной попытки `30000 мс`;
   - `retryCount=1`, то есть максимум две попытки;
   - пауза перед второй попыткой `1000 мс`;
   - сохранить результат в `SerialNumber`;
   - ошибка обязательная.
2. Проверить `SerialNumber` в диапазоне `3200000..3299999`.
3. Вычислить:
   - `SerialShort = SerialNumber - 3200000`;
   - `Dut.NewMac = C0:11:A6:20:HH:LL`, где `HH:LL` — два байта
     `SerialShort`;
   - допустимый для вычисления диапазон `SerialShort` в runtime — `0..65535`.
4. Один раз отправить UDP set-MAC пакет:
   - адрес `192.168.0.1`;
   - порт `43962`;
   - MAC из `Dut.NewMac`;
   - `repeatCount=1`;
   - `delayBetweenRepeatsMs=200` сохранен, но при одном пакете не применяется;
   - send timeout сокета `1000 мс`;
   - ошибка обязательная.
5. Ждать `7000 мс` после отправки set-MAC.
6. `slave 23, 1200 ← 0`, с проверкой — выключить AC1.
7. `slave 23, 1210 ← 0`, с проверкой — выключить ключ разрядки.
8. Ждать `10000 мс` при снятом питании.
9. `slave 23, 1200 ← 1`, с проверкой — снова включить AC1.
10. Ждать `100 мс`.
11. Очистить ARP; таймаут `5000 мс`, ошибка игнорируется.
12. Выполнить `Selftest Check` после перезапуска:
    - таймаут `300000 мс`;
    - интервал `5000 мс`;
    - префикс `Dut`;
    - пустые правила заменяются стандартными;
    - ошибка обязательная.
13. Сравнить `Dut.default_mac` и `Dut.NewMac` как нормализованные MAC-адреса.

Проверка диапазона шага 2 допускает значения до `3299999`, но вычисление MAC шага 3
работает только до `3200000 + 65535 = 3265535`. Серийники `3265536..3299999` пройдут
первую проверку и затем провалятся при вычислении MAC.

### 16. Печать этикеток

Отправить на RAW-принтер `Zebra` четыре одинаковые ZPL-этикетки:

- имя устройства `PSW+UPS-Box 8x2Pro`;
- числовой тип устройства `32`;
- печатаемый SN берется из `SerialShort`, а не из полного `SerialNumber`;
- MAC берется из `Dut.NewMac` и печатается;
- поле оборудования выключено (`equipmentFieldUse=false`);
- ошибка печати обязательная.

Печать выполняется до финального selftest и формирования отчета.

### 17. Финальная статистика и отчет

1. Выполнить финальный `Selftest Check`:
   - URL тот же;
   - таймаут `300000 мс`;
   - интервал `5000 мс`;
   - результат сохранить под новым префиксом `DutFinal`;
   - пустые правила снова превращаются в четыре стандартных;
   - `failOnError=false` не выставляет критическую ошибку, но сама нода все равно
     возвращает `False` при неуспехе. Поскольку выход `False` не подключен, отчет в
     этом случае не строится.
2. Собрать JSON в переменную `TestReportJson`:
   - `device_name=PSW+UPS-Box 8x2Pro`;
   - `device_type=32`;
   - `serial_num` из `SerialShort`;
   - `mac` из `Dut.NewMac`;
   - включить в отчет все переменные контекста (`includeAllVariables=true`).
3. Сохранить локальную копию в каталог `reports` и отправить отчет:
   - в профиле `serverBaseUrl=http://SERVER_BASE_URL`, фактический адрес берется из
     настроек приложения;
   - endpoint `/api/Api.svc/result.json`;
   - multipart-поле `file`, имя `result.json`;
   - успехом считается HTTP 2xx и ответ, начинающийся с `Ok`;
   - максимум две попытки по `10000 мс`;
   - пауза между попытками `1000 мс`;
   - `failOnError=false`, поэтому ошибка отправки не мешает перейти к выключению
     стенда;
   - локальная копия создается до сетевой отправки.

### 18. Безопасное выключение стенда

1. `slave 23, 1200 ← 0`, с проверкой — AC1 off.
2. `slave 23, 1210 ← 0`, с проверкой — ключ разрядки off.
3. `slave 23, 1204 ← 0`, с проверкой — ключ зарядки off.
4. `slave 23, 1215 ← 0`, с проверкой — нагреватель 1 off.
5. `slave 23, 1220 ← 0`, с проверкой — нагреватель 2 off.

Явных задержек нет. В этом штатном shutdown отсутствуют команды `1201 ← 0` для AC2,
`1700 ← 0`/`1706 ← 0` для SIMBAT и отключение EL60v5. Алгоритм полагается на то,
что AC2 уже был выключен в подтесте 05, а SIMBAT был выключен в подтесте 14.

Параметр подтеста `stopOnError=false`, но у отдельных записей подключены только
успешные выходы. Поэтому ошибка ранней записи все равно не дает выполнить оставшиеся
команды этого shutdown.

### Аварийное выключение стенда — только при ошибке/Stop

Подтест не соединен с основной цепочкой. Приложение запускает его отдельно после
провала, исключения или ручного Stop. Общий timeout всех cleanup-подтестов — `60 с`.
Пауза приложения во время cleanup игнорируется.

Последовательность:

1. Записать в лог метку об аварийном выключении.
2. `slave 23, 1200 ← 0`, без проверки — AC1 off.
3. `slave 23, 1210 ← 0`, без проверки — ключ разрядки off.
4. `slave 23, 1204 ← 0`, без проверки — ключ зарядки off.
5. `slave 23, 1215 ← 0`, без проверки — нагреватель 1 off.
6. `slave 23, 1220 ← 0`, без проверки — нагреватель 2 off.
7. Для slave `1, 3, 5, 7, 9, 11, 13, 15` выполнить без проверки:
   - `1414 ← 0` — нагрузка A off;
   - `1415 ← 0` — нагрузка B off;
   - `1412 ← 0` — мощность A `0 мВт`;
   - `1413 ← 0` — мощность B `0 мВт`.

В аварийном cleanup нет команд для SIMBAT `1700/1706` и AC2 `1201`.

Если одна из линейных записей slave 23 завершится ошибкой, последующие команды не
выполнятся, потому что выходы `False` не подключены. Внутри цикла EL60v5 установлен
`stopOnError=false`: после провала тела цикл перейдет к следующему slave, но
оставшиеся команды для уже провалившегося slave будут пропущены.

## 5. Что особенно важно проверить по железу

Ниже не исправления, а вопросы, прямо следующие из текущего профиля.

1. **Начальное безопасное состояние.** Подтест 01 сбрасывает AC, заряд, разряд и
   нагреватели PS-3, но не выключает ключ разрядки SIMBAT `1706`. Нужно ли добавить
   `slave 17, 1706 ← 0` до подключения оператора и последующей подачи питания?
2. **Порядок возврата питания.** В подтесте 14 сначала выполняется `SIMBAT 1706 ← 0`,
   и только затем `AC1 1200 ← 1`. Нужно ли поменять порядок: сначала надежно подать
   и подтвердить AC1, затем отключить батарейную цепь?
3. **Аварийное выключение SIMBAT.** Cleanup не выключает `1706` и `1700`. Если тест
   упадет между подтестами 05 и 14, разряд SIMBAT останется включенным.
5. **Проверки разряда.** В подтесте 13 диапазоны `1707=0..65535 мВ` и
   `1708=0..65535 мА` пропускают любое успешно прочитанное значение, включая нули.
   Какие должны быть реальные пороги напряжения и тока?
6. **Источник статуса UPS.** Текущий JSON ждет `ups_rez` через повторный
   `SelftestSnapshot` до 300 секунд. В журнале стендовых проверок уже зафиксировано,
   что после перехода на АКБ страница 300 секунд не отдавала XML. Код и unit-тест
   текущего commit ожидают другой вариант: `1707=12000..27000`, `1708>0` и проверку
   HTTP-доступности DUT до 160 секунд, но профиль этому не соответствует.
7. **Нагреватель 1.** Описание требует `150..1000 мА`, фактическая проверка после
   включения — `0..1500 мА`, то есть допускает неработающий нагреватель.
8. **Реле нагревателей.** В обоих тестах сначала записывается off, затем сразу on без
   паузы. Нужна ли задержка на отпускание/срабатывание реле?
9. **Нагреватель во время selftest.** В подтесте 11 нагреватель 1 включается на
   `15 с`, затем остается включенным до завершения selftest, которое может ждать до
   `300 с`. Допустимо ли такое максимальное время включения?
10. **Очистка статистики PS-3.** В `1219` пишется `1`, но обратного `0` нет. Это
    импульсная команда с автосбросом или уровень, который нужно снять?
12. **Проверка PoE.** Подтест 04 только включает нагрузки. В графе нет проверок
    фактического напряжения/тока всех 16 PoE-линий.
